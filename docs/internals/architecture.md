# Architecture internals

Companion to `CLAUDE.md`; read before adding a package or changing responsibilities between existing ones.

Layered packages, each with a focused responsibility. Commands compose primitives from the lower layers — keep the boundaries clean rather than reaching across them.

- `cmd/bn/main.go` — thin entrypoint, delegates to `internal/cli.Execute`.
- `internal/cli` — Cobra command tree. `root.go` wires persistent flags and uses `PersistentPreRunE` to load config into the command context (extract with `ConfigFromContext`). Each subcommand lives in its own file; `related.go` owns ranking/output/interactive selection, `related_feedback.go` owns explicit sidecar writes, and `context.go` owns deterministic bundle export plus optional agent execution. `target_resolution.go` is the shared NFC-aware single-note resolver for links/backlinks/related/context. `recall_corpus.go` is the one place a recall-reading command pins its clock (`recallNow`, threaded into both `recall.WithClock` and `RankOptions.Now`), wraps the state store as the read-only `recall.RecallSignalSource`, and extracts the corpus/graph/ranker triple, so `related`, `context`, and `find --sort relevance` cannot build different corpora from the same vault; `find_sort.go` is the caller-side ordering layer for `--sort`/`--relative-to`, since `queryexpr` parses a `SortSpec` but never ranks. `notes.go` centralizes multi-note positional handling: it resolves paths from args, globs, or stdin (`-` triggers stdin; `-0` toggles NUL separation) and enforces in-vault containment. `findflags.go` owns the shared filter surface and is the **single execution path** for it: `register` binds the find flags plus `--query`/`-q` and `--view`, `compile(env)` folds all three sources into one `*queryexpr.Plan` whose `Expr` is their AND, and `selectNotes` builds the link graph only when `needsGraph(plan)` says so and then runs one `Evaluator.Evaluate`. Every flag-scoped command routes through it — `find`, `search`, `graph`, `lint`, and the four scoped mutators via `collectReplaceCandidates` — so a filter cannot mean one thing to `bn find` and another to `bn replace`. The two text sources are compiled separately rather than concatenated, because a `*queryexpr.ParseError` renders carets against the source it was parsed from. `queryFlagNames` in `replace.go` must list every one of these flags, `--query` and `--view` included, or the note-args/find-flags mutual-exclusion check silently stops firing; `RenderError` in `root.go` is the one place an error is printed and the one place that upgrades a `*ParseError` from its one-line `Error` to the caret block `Render` draws. The **shape** every command in this package is written in — a thin `New*Cmd` holding only help text and flags, an `<cmd>Options` struct replacing the captured locals, one `validate()` owning the flag mutual-exclusion matrix, one named function per behaviour mode in `<cmd>_run.go`, and rendering in `<cmd>_output.go` — is `docs/internals/cli-command-shape.md`, worked through `set.go`/`set_run.go` and `search.go`/`search_run.go`/`search_output.go`. Read it before adding a subcommand or decomposing one; it also records which orderings in `search` are behaviour rather than incident. `config_scriptable.go` and `config_migrate.go` are the writable half of `bn config`. Both route by **ownership, not provenance**: `resolveConfigTarget` asks `cfg.OwnerPath`/`config.KeyLayer` which file owns the key and writes there, so the same command does not land in a different file on a different machine, while `refuseShadowedWrite` uses `cfg.SourceOf` to refuse a portable write the overlay would shadow — a correct file and no change in behaviour is the worst shape a configuration command can have. Every write reads *both* layers, patches one, and pins both in the transaction: the target with `ExpectHash` (or `ExpectMissing`, when it is an overlay being created), and the untouched layer through `otherExpectation`, since the decision to write these bytes at all was made by reading the pair. An absent overlay is pinned *as absent*, so one appearing mid-command is a refusal rather than a silent no-op. `bn config migrate` is the repair path for the state `refuseShadowedWrite` sends users to, and it is the only command carrying the `skipConfigLoad` annotation: a vault whose keys are misplaced is one the loader refuses once enrolled, so the fix cannot sit behind the fault. It applies `config.PlanMigration`'s two file rewrites under **one** `vault.FileTxn` and one `noteops` operation, so there is no window where one file is migrated and the other is not, and an interruption past the fsynced intent is rolled forward by `internal/vault`'s recovery pass like any other transaction. `views.go` is the read-only `bn views`/`show`/`check` tree: all three go through one `resolveConfigViews` helper that builds an `Env` from `config` alone, so listing views never walks the vault and never builds a graph, and every one of them honours the disabled-not-dropped contract — `views` prints a `STATUS` column, `show` returns the view's own error so `RenderError` draws its carets, and `check` exits non-zero so it is usable as a config health gate.
- `internal/config` — TOML loader for the vault-local configuration: the portable `brainnotes.toml` plus the optional machine-local `brainnotes.local.toml` overlay beside it. `brainnotes.toml` is the vault-root marker — the overlay never is — so resolving the vault root and locating the config are the same operation: `--vault` → `$BNOTES_VAULT` → an upward search from the working directory, each of which requires the directory to actually contain `brainnotes.toml`. `LoadOptions` injects the flag, working directory, and environment lookup so precedence is testable without touching real process state. `Vault`, `SourcePath`, `LocalSourcePath`, `VaultOrigin`, `Provenance`, `Fingerprint`, and `Enrollment` are runtime-only fields (`toml:"-"`); there is no `vault` key. **`DecodeSources` is the single load path** and `Load`/`Decode` are thin wrappers around it, so no entry point can apply a different set of layering, ownership, defaults, and validation rules — in particular `Decode`, which takes candidate `brainnotes.toml` bytes, still reads the overlay from the vault, because a caller holding those bytes is asking what the vault would load from them and the vault includes its overlay.
  - `ownership.go` is the **ownership table**: every decodable key exactly once, with the file that owns it, and a `copy` closure that carries its decoded value from one `Config` into another. A key is local when its value names something that exists only on this machine — a binary to execute, an address to bind, or the arguments and timeout that go with one of those (`fzf.args`, `open.editor`, `serve.addr`, `serve.open_browser`, `agent.*`, `cockpit.agent_*`); everything else is portable, `autosave.min_interval` included, since that is a policy about the vault's own safety history and nothing in it identifies a machine — which is also what routes `bn config set`, whose destination is the table's owner rather than the file the value currently comes from, to the portable file for the only key it accepts. Two reflection tests over `Config`'s own toml tags prove the table names every decodable key and no others and that each `copy` touches exactly the field its key names, so a new field cannot be added without deciding its owner. A spec whose value is a table or array of tables (`frontmatter.properties`, `new.routes`, `views`) governs everything nested under it and is overlaid **whole**, so the merged configuration always says exactly what one of the two files says.
  - **Ownership is enforced only on an enrolled vault** (`VaultEnrollment` stats `.bnotes/sync/enrollment.json` and reads nothing — the marker's contents belong to the synchronization work), and that gate is the point rather than a softening of it. Misplacement is a *synchronization* fault: a portable key parked in the overlay never reaches the peer, and a local key left in the portable file does reach it and overwrites the peer's own editor, address, or agent command. An unenrolled vault synchronizes nothing, so neither failure exists — and every legacy single-file configuration is precisely a portable file carrying local keys, so enforcing there would break every vault in existence.
  - **An absent overlay and an empty one are different answers**, carried from `Sources.Local` (nil versus non-nil empty) all the way into `Fingerprint`. `Fingerprint.Composite` is the value a caller compares to decide whether the configuration changed: it covers both layers' digests *and* the overlay's presence under a version tag, so creating an empty `brainnotes.local.toml`, filling it in, and deleting it again are three distinct fingerprints. An unreadable overlay is an error rather than an absent one, for the same reason. `hashSource` restates `vault.HashBytes` rather than sharing it because `vault` imports `config`. The composite covers **bytes and nothing else**: enrolling a vault can turn a loading configuration into a refused one with neither file edited, so a caller may skip its *publication* on an unchanged composite but never the load itself. `cmd/bn-vault-guard`'s `policySource` is the first caller — it fingerprints before it decodes, so an overlay that fails to parse is still reported once per broken version rather than once per poll.
  - **`assignedFields` distinguishes a header from a value**, and that is what makes the overlay safe to copy a template into. `[serve]` with nothing under it was always harmless, but `[frontmatter.properties]` with every example block commented out decodes to an empty map, and overlaying *that* would erase the vault's declarations — `bn set` silently stops splitting lists, `bn lint` silently stops flagging required properties, and the configuration still loads. So a key whose TOML type is `Hash` or `ArrayHash` is skipped: `views.name` assigns `views`, a bare `[[views]]` assigns nothing. An inline `frontmatter.properties = {}` is the same type and the same answer, so the rule is the strong one — a table-valued key can be **replaced but never emptied** from the overlay, in any spelling. An array is not a table, so `views = []` still clears.
  - `Config.SourceOf(key)` reports which file assigned a key, and "no file did" — that key holds its default. `SourceOf`, `KeyLayer`, and `OwnerPath` are what route a scriptable CLI write: `internal/cli`'s `resolveConfigTarget` asks `OwnerPath`/`KeyLayer` where the key *belongs* and `refuseShadowedWrite` asks `SourceOf` whether the overlay would shadow the answer. The two questions are deliberately different — routing by provenance would make the same command write a different file on a different machine, while ignoring provenance would let a portable write report success under an overlay that outranks it. `Provenance`, `LayerKeys`, `LocalSourcePath`, and `Enrollment` still **have no production caller** and are deliberately ahead of the synchronization work that will decide what may travel between vaults; expect to be their first caller. `EnrollmentMarker` no longer belongs on that list — `internal/vaultsync` derives both the enrollment record's path and the private-path rule covering it from that one constant, so the file the configuration loader stats and the file the protocol refuses to send cannot drift apart. A post-merge *validation* failure (`validate.go`) names the key but not the layer, because provenance is not threaded into it.
  - `migrate.go` is the **repair path for a misplaced configuration**, and it is the one place the ownership table is read as an instruction rather than a check. `PlanMigration` routes every assignment sitting in the file that does not own it into the file that does, in *both* directions, and returns a previewable `MigrationPlan` that writes nothing — so `--dry-run` and the apply are one computation and cannot disagree. Three properties are load-bearing. It plans with **ownership suspended** (`decodeSourcesAs(..., EnrollmentNone)`), because an enrolled vault whose keys are misplaced is exactly the vault the loader refuses, and requiring a loading configuration would put the only fix behind the fault it fixes; every other way of being invalid still fails. Assignments move as **bytes** — the source lines are cut and inserted unchanged, with only a dotted key respelled bare for its new table — so quoting, spacing, and trailing comments survive and a value this package never decodes cannot be re-rendered wrongly; comments on the lines *above* an assignment stay put, since nothing in TOML says which key a free-standing comment documents. And the result is **verified before it is returned**: the migrated pair must load and `sameEffectiveConfig` must find every `fieldSpecs` key holding the value it held before, so a migration that would change what the vault does is refused rather than written — driven from the same table as the merge, which is what keeps a newly added field covered without anyone remembering to. A key both files assign is the one lossy case, and it is lossy only on paper: the overlay already won, so the portable copy is dead text, and `resolveShadowedMove` keeps the value in force and drops the other. Refusing there is not available — `bn config set` refuses a shadowed write and sends the user here, so a migration that also refused would strand the vault. Planning twice is the normal outcome and the second plan moves nothing, which is where idempotence comes from.
  - `internal/vaultgit`'s `InScope` excludes `brainnotes.local.toml` **at the vault root only** — a note filed under that name deeper in the tree is ordinary content. Committing the overlay would push one machine's editor, listen address, and agent command to the private remote and hand them to whatever restores from it, which is the failure the overlay exists to prevent. That narrowing is safe by `InScope`'s own contract: anything already tracked in HEAD stays in scope, so an overlay a user committed before does not silently fall out of their history. `DefaultIgnore` (`.git`, `.obsidian`, `Attachments`, `Archive`, `Trash`) is always merged in. `[related]` controls only the metadata property list; fixed ranking weights are not configuration. Top-level `[agent]` is a literal argv plus timeout shared by context research and, when no legacy cockpit override is set, daily review. Saved views live in a `[[views]]` **array of tables** decoded into `Config.Views []SavedView{Name, Query, Sort, RelativeTo, Limit, Description}` — an array rather than `[views.<name>]` tables because the list is ordered, and `bn views` and the web nav present views in file order. Validation of a view is deliberately **shape-only** (name pattern, case-insensitive uniqueness, non-empty query, `limit >= 0`): `config` is the bottom of the layering, so importing `internal/queryexpr` to check that `Query` parses would close a cycle, exactly like the documented `pins`/`noteops` edge. The load-bearing consequence is that a view whose expression rotted still loads — one stale view must never make a vault unopenable — and every layer above is required to render it as a **disabled entry carrying its parse error**, never dropped and never a 500. `queryexpr.ResolveViews` is the single place that resolution happens (see below), and `bn views check` is the user-facing answer. `patch_views.go` is the comment-preserving TOML patcher for that section: it reuses `splitConfigLines`/`joinConfigLines`/`diffLines`/`quoteTOMLString` from `patch.go` and adds the array-of-table header parser in its own file rather than widening `parseTableHeader`, which explicitly treats `[[` as "not a header". A view block runs from its `[[views]]` header to the next table header (so deletion cannot glue two sections together), a rename rewrites only the `name` line, and an upsert replaces the whole block — which is why `PatchResult.Diff` is a mandatory preview rather than a courtesy: `brainnotes.toml` is the vault-root marker and a mangled patch is a vault-wide failure.
- `internal/vault` — `Vault` is a root path + config. `Walk` skips hidden dirs, configured ignores, and the templates dir automatically (template files contain unrendered placeholders that are not valid YAML, so they must never be walked). `Notes()` loads everything in memory — fine for the documented working size (~300 notes); switch to streaming `Walk` if scaling beyond a few thousand. `WalkExclusion` is that pruning rule stated as a predicate, so a writer choosing a destination can refuse the locations `Walk` would never visit — a note created under an ignored, hidden, or template path exists on disk yet is invisible to every query. It is the rule **plus a fold**: both configured exclusions are compared case-insensitively, which makes it deliberately stricter than `Walk` on a case-sensitive filesystem, because `Walk` prunes by the name it finds on disk and a create of `archive/Old.md` against an ignored `Archive/` lands inside that real directory on a case-insensitive one. The asymmetry and its price are stated on the function. `ResolveByTitle` does case-insensitive stem lookup and returns an ambiguity error listing all candidates. It also owns locking and `FileTxn`, whose write contract — including the fsynced recovery intent under `<vault>/.bnotes/txn/` that lets a *killed* process's transaction be finished on the next open or the next mutation — is in `docs/internals/locking.md`. `Vault.Open` runs that recovery pass best-effort and ignores its result so read-only commands are never refused; `acquirePathLocks` runs the same pass and returns its error, so every write fails closed. `SyncDir` is exported from here for the one package that keeps durable state outside the vault tree (`internal/vaultgit`, under `.git`) rather than duplicating its per-platform build tags.
- `internal/frontmatter` — parse/rewrite YAML frontmatter. `Map` preserves insertion order during parse but `Marshal` **always emits keys alphabetically sorted** — this is intentional and load-bearing for stable diffs. Values are Go-native types (string, int, float64, bool, time.Time, []any, map[string]any). Wikilink-typed properties are auto-wrapped in `[[ ]]` on write.
- `internal/wikilink` — Obsidian-style `[[Target#Heading|Alias]]` parsing and rewriting. **Code-block aware**: links inside fenced, indented, or inline code are masked out so rewrites never touch documentation samples or code snippets. Used by `rename` (rewrite all forms when title changes) and `move` (rewrite folder-prefixed forms only — bare `[[Title]]` links resolve by title alone in Obsidian and are deliberately left untouched).
- `internal/query` — composable `Predicate` functions over `*vault.Note` for the `find` command's frontmatter dimensions (tag/category/status/type/has/missing/folder/age/orphan), plus the path-aware wikilink graph reused by recall ranking. `And` is the identity-with-no-args combinator; queries with no flags match everything. The graph contract is no longer only orphan detection: `graph_metrics.go` derives `GraphMetrics` from a built `Graph` by inverting `Forward` into sorted out/in/both adjacency, and answers **bounded graph traversal** — `Degree` (the *undirected* distinct-neighbour count), undirected connected `Components`/`ComponentSize`, and `Distances`/`Distance` BFS under a `maxHops` bound where a negative bound means unbounded, plus `ShortestPath`, which computes distances *towards* the target and steps greedily to the smallest neighbour one closer, yielding the lexicographically smallest shortest path without enumerating paths. `filter_graph_ops.go` turns that into the six graph predicates `queryexpr` lowers onto (`LinksTo`, `LinkedFrom`, `Near`, `PathTo`, `Degree`, `ClusterSize`), each of which resolves its target **once at build time** into a key set or a reachable set, so a term costs one traversal per scan rather than one per note. Direction on `Near`/`PathTo` is anchored at the **candidate note**, not the target: `DirOut` means "the note reaches the target by its own outgoing links", implemented as one BFS out of the target along `dir.reverse()`. Every one of them ends in `Reachable(g, keys)`, the exported membership test, which is why the memoized `queryexpr` path runs literally these predicates rather than a reimplementation. Two keyspaces coexist and must not be confused: `GraphMetrics` takes a **note key** (`areas/foo`), while `Graph.OutDegree`/`InDegree` take a **title** — resolve through `Graph.KeyForNote` or `Graph.ResolveTarget` first. An isolated note is a component of size 1 with degree 0, so `cluster-size:1` and `degree=0` both mean "unlinked note"; membership is gated on `GraphMetrics.has` so a note absent from the graph never matches at all.
- `internal/queryexpr` — the vault query expression language: the surface syntax users type into `bn find`, the library query bar, and the graph filter, lexed and parsed into one shared AST (`And`/`Or`/`Not`/`Term`, precedence `not` > `and` > `or`, juxtaposition meaning AND). It is deliberately a sibling of `internal/query` rather than files inside it: `query` is imported by `recall`, `noteops`, `cockpit`, `web`, and `brief`, and typed comparison needs `config` and `schema`, so folding the language into `query` would widen that contract for every existing consumer. The dependency therefore runs one way — `queryexpr` may import `query`, `config`, `schema`, `frontmatter`, `vault`, `wikilink`, and `textnorm`, and **must never** import `recall`, `cli`, `web`, `noteops`, `properties`, or `cockpit`; `layering_test.go` parses the package's own imports and fails on a violation. `Expr.String()` re-renders canonical source and round-trips through `Parse`, so it is what a saved view prints and what the web layer normalizes an `expr=` parameter to; canonicalization is idempotent rather than byte-preserving, because atom text is NFC-normalized through `internal/textnorm` on the way in. Every failure is a `*ParseError` carrying the source, the byte span, a **rune-based** column, and did-you-mean candidates — `Render` draws a caret line padded by rune count, since accented text in a query is exactly what byte columns get wrong. `Compile` lowers a parsed `Expr` onto `internal/query` predicates through the reserved-field table in `fields.go`, and returns a `Plan` — the validated expression plus the caller-supplied `SortSpec` and `Limit`, which are *not* expression syntax. Compilation needs no link graph: `Plan.NeedsGraph` reports whether one is worth building (staying compatible with `findFlags.needsGraph`) and `Plan.Predicate` builds the closures against whatever `Env` the caller finally assembles, deriving `GraphMetrics` from the graph when a caller supplies only the graph. A plan whose `Env` lacks that state fails with a `*MissingStateError` rather than silently matching nothing. `Evaluator` runs a plan against a corpus; `NewMemoryEvaluator` scans an already-loaded `[]*vault.Note`, builds the graph lazily, and rejects an ordering it cannot honour instead of quietly ignoring it. `typed.go` compares a frontmatter property according to its **declared** `[frontmatter.properties]` type and nothing else — there is no key-name special-casing anywhere in it, and it reuses `schema.CheckScalar`/`schema.TryCoerce` for kind checking rather than re-deriving it, adding only literal parsing and the comparison operators on top. The declared type decides which operators are legal (`string`, `wikilink`, and `bool` define only `:`/`=`/`!=`; `date`, `datetime`, `int`, and `float` define ordering too; a list defines only `:`, meaning contains-any with each element parsed as its declared `items` kind), and ordering an unordered kind is a compile error naming the declaration rather than a silent miss. An **undeclared** key is still queryable, but through `prop:<name>` rather than bare — a bare unknown name has to stay an unknown-field error or did-you-mean has nothing to be wrong about — and there it falls back to the same stringify-and-fold comparison `Tag` and `Status` use, with ordering operators requiring the stored value to really be an `int`, a `float64`, or a `time.Time` and skipping the note when it is not. A property's `allowed` list is deliberately **not** enforced on queries: finding the notes that violate your own schema is the point. Relative literals (`today`, `now`, `+30d`, `"-7d"` — quoted, because a leading `-` lexes as negation) resolve against `Env.Now`, which is what makes a date query testable without depending on the day the suite runs. `graph_terms.go` holds the six fields that read link structure (`links-to`, `linked-from`, `near`, `path-to`, `degree`, `cluster-size`) and is merged into the reserved table by `withGraphFields`, because those fields need two things no other field does. They name a **note**, so a target can be spelled correctly and still refer to nothing: every target is resolved through `Graph.ResolveTarget` before its predicate is built, and an unresolvable one is a `*ParseError` with did-you-mean candidates rendered from `Graph.OriginalTitles` (never the folded `NoteKeysByTitle` keys, which are not copy-pasteable back into a query) — an empty result set would otherwise be indistinguishable from a correct empty result set. Resolution needs the graph, so it runs at compile time when `Env` already carries one and inside the builder otherwise, making the diagnostic later but never absent. And they are the only fields whose cost is a traversal: `near` and `path-to` are both reachability, so they share one BFS memo that lives for exactly one `Plan.Predicate` call, holds **unbounded** distance maps keyed by anchor and direction (so every hop bound is a filter over one traversal), and is consulted only while predicates are being built — never during the scan. The memo is deliberately not on `GraphMetrics`: that value is built once per command run or web snapshot and read by concurrent requests, so a cache hung off it would need a mutex on the hot path or would be a data race. Both traversal terms lower onto `query.Reachable`, the exported membership test `Near`/`PathTo`/`LinkedFrom` themselves end in. `flags.go` bridges the older flag surface: `queryexpr.FromFlags(query.Flags) (Expr, error)` lowers the flattened `bn find` flag set onto the same AST, preserving the asymmetric activation rules (`MinBacklinks > 0` activates, `MaxBacklinks >= 0` activates, because a minimum of 0 filters nothing while a maximum of 0 is the meaningful "nothing links here" filter). It is knowingly a **second** implementation of `query.FromFlags`, which stays exactly as it is: `internal/query` cannot import `internal/queryexpr` without a cycle, and `query.FromFlags` has eight callers with a test surface that predates this package. `flags_equivalence_test.go` is what makes the duplication acceptable and is the deliverable of the bridge — it runs the flag matrix through both paths against one fixture vault, rendering the expression to canonical text and recompiling it, and requires byte-identical sorted path lists (or agreement that the value is rejected). If that test ever becomes hard to keep green, that is the signal to merge the two packages and accept the `config` import, not to loosen the test. Two divergences are accepted and documented on `FromFlags`: error text differs, and a missing graph or root fails at `Plan.Predicate` with a `*MissingStateError` rather than at `FromFlags`, because that state arrives through `Env` rather than through `Flags`. `sort.go` holds `SortSpec{Key, Descending, RelativeTo}` and `ParseSort` over `path` (the default), `title`, `modified`, `created`, `backlinks`, `degree`, `pinned`, and `relevance`, accepting a direction as either a sign prefix (`-modified`) or a suffix (`modified:desc`) but never both. **`queryexpr` never ranks** — a `SortSpec` is a declarative spec and nothing more, which is what keeps the recall sidecar's read/write boundary out of a package whose job is compiling text; `ParseSort` never sets `RelativeTo`, since that names a note and binds to its own flag. `sortNotes` in the memory evaluator distinguishes an unknown key (a bad spec `ParseSort` would have rejected) from a valid key it does not order by (the caller's job), so a caller can tell which mistake it made. `views.go` is where a `config.SavedView` becomes runnable: `ResolveViews` returns one `View{Saved, Plan, Err}` per saved view, in file order, always — a query that no longer compiles comes back with its `*ParseError` on `Err` and a nil `Plan` instead of being omitted or raised, which is what makes "disabled, with its error" the default rendering everywhere. `RelativeTo` is read from its own config field rather than from the sort text, because `SortSpec.String()` deliberately drops it. `completion.go` is the editor-facing introspection surface — `Fields`/`IsReservedField` expose the reserved vocabulary with a one-line hint per name, `FieldsUsed` reports the fields a parsed expression names, and `CompletionAt(src, pos)` answers what is being typed at a caret. It is deliberately a **backwards scanner rather than a parse**, because the moments a completion is wanted (`tag:`, `near:[[Deep`) are exactly the moments the expression does not parse; it reuses the lexer's own `isWordRune` so a completion token can never disagree with the token the parser would cut. It reports syntax only — which field, which argument, which prefix, which byte span a candidate replaces, and whether the caret sits inside a quote or a `[[` — and never values, since sourcing those needs `properties` and the facets machinery that this package must not import. One rule is load-bearing and tested: an operator must be **adjacent** to the caret's token for a value position, so `tag:wi` completes values while `tag: ` (with a space) is a fresh field position.
- `internal/recall` — deterministic contextual retrieval with no persistent index. Extraction preserves exact note bodies/source spans while building NFC-normalized weighted title/heading/prose fields and configured metadata pairs. `BuildRanker` combines fixed text/graph/metadata/recall weights and returns stable reasons/mode filters. `BuildContextBundle` keeps the source body complete, admits ranked related excerpts under one selection shared by Markdown and JSON, and enforces the byte cap against both renderers. `Ranker.RankSelected` and `BuildCuratedContextBundle` are the explicit-selection pair: selection is authoritative, so caller order is preserved and recall dismissal/snooze suppression and mode eligibility never drop a chosen note. Every curated supporter contributes at least one exact excerpt — a supporter with no extractable body block is rejected rather than reduced to an identity — and curated `MaxBytes` is a starting budget rather than a cap: it grows only as far as the mandatory anchor body and one excerpt per supporter require, never past `MaxCuratedBundleBytes` (1 MiB). `StandardPurpose` owns the shared synthesis/contradictions/questions definitions so no caller can present different instructions under one purpose name. `StateStore` owns flock serialization for `<vault>/.bnotes/recall.json` and holds the sidecar path lock across every fresh read-modify-write; read-only queries stay lazy, explicit writes prune stale records, and corrupt/invalid/symlinked state fails closed.
- `internal/agent` — shared argv-only process runner. Callers own context timeouts; stdin/stdout remain byte-exact; diagnostics are bounded and sanitized. There is no shell, provider SDK, persistence, or implicit network behavior. `bn context --agent` sends its canonical Markdown preview, while the web daily-review path sends only its separately redacted review payload.
- `internal/template` — discovery and rendering for `bn new`. Template lookup is case-insensitive and tries `<name>`, `<name>.md`, `<name> Template.md`. Render helpers: `now`, `today`, `dateFormat`, `slug`, `title`, `lower`/`upper`, `default`, `env`, `wikilink`. The `.Vars` map holds repeatable `--var key=value` pairs.
- `internal/web` — the HTTP server, its page handlers, and its mutating APIs. Its one cross-cutting invariant is the **serving-mode capability table** in `capabilities.go`: `NewServer` derives a `Mode` (`local`, `read-only`, `hosted`) once from `Options` and everything downstream asks `s.caps` rather than re-deriving a deployment from a flag. - `internal/noteops` — the shared note-mutation layer used by both CLI commands and the web APIs. `preview.go` defines the canonical `NotePreview`/`PreviewChange` model that every mutating command's `--dry-run` and every web preview render through, so the two views can never drift. `capture.go` holds the quick-capture primitive behind `bn capture` and the web quick-capture box: `PreviewCapture`/`ApplyCapture` append one fixed-format `- YYYY-MM-DD HH:MM <text>` bullet to the configured inbox note under the configured heading, splicing bytes (never re-marshaling frontmatter) so every pre-existing byte survives — the write is strictly additive, so even the heading-absent path only appends a separator, the heading, and the bullet rather than collapsing trailing blank lines — bootstrapping the note inline when it is absent, and — uniquely among noteops writes — re-reading and re-planning up to 3 times on a `vault` transaction conflict before returning `CodeConflict`, which is safe only because an append is commutative. `capture_heading.go` owns the single line-oriented heading scanner and exports `CountSectionBullets` so `internal/cockpit` counts exactly the section the writer would append to; its `containsATXHeading` is what makes the synthesis draft's reserved `## Sources` heading detectable without matching fenced-code samples. `synthesis.go` is the create-only pair behind the synthesis workbench: `PlanSynthesisNote` resolves the destination, validates the draft, and returns the exact bytes plus every read-only expectation, and `ApplySynthesisNote` writes those exact bytes rather than rebuilding them, so what a user previewed is what lands. A synthesis plan always carries `ExpectMissing` — V1 creates new notes only and `ApplySynthesisNote` refuses any other expectation — and its `Requirements` pin every ordered source (and, when the caller supplies it, `brainnotes.toml`) through `FileTxn.Require`, so a source edited between preview and apply is a `CodeConflict` with no note and no journal entry. Plan-time verification through `vault.VerifyState` is a courtesy that refuses a doomed plan early; only the transaction's own recheck makes the write safe. `source.go` + `source_save.go` + `source_ledger.go` are the raw-Markdown pair behind the web editor, and the one noteops write whose unit is the **whole file**: `ReadSource` hands out the bytes on disk and their **revision** (`vault.HashBytes` of exactly those bytes), and `SaveSource` writes the submitted bytes back verbatim under `ExpectHash(revision)`. Verbatim is the load-bearing word — the content never round-trips through `frontmatter.Marshal`, which always sorts keys, so a save would otherwise silently reorder frontmatter nobody touched; `ValidateSource` therefore *parses* the frontmatter to refuse what could not be stored (a properties block that is opened **and closed** whose YAML does not parse, a NUL byte, over `MaxSourceBytes`) and then throws the parse away — and it refuses nothing else, so a `---` line with no closing delimiter is stored verbatim, because `frontmatter.Parse` reads that as a body beginning with a horizontal rule and a surface that refused it would be the only one in the vault unable to save a note the vault itself serves. `resolveSourceDestination` takes the `*config.Config` as an explicit second positional parameter for the same reason `PlanSynthesisNote` does, and owes the same four refusals its synthesis sibling owes: containment, the `.md` extension, no symlink, and `vault.WalkExclusion` — a destination `Walk` would never visit (any hidden component, the templates directory, the configured ignores) is `CodeForbidden`, because a note written there is on disk and in no index, no graph, no search and no query, and under `.bnotes/` it is also outside `vaultgit.InScope`, where the journaled write commits *nothing* while the answer reports a revision and a success. It is the deliberate inverse of `capture.go`: an append is commutative and may replan, a whole-file write is not and never does, so a conflict comes back as a typed `*SourceRevisionError` for a person to resolve rather than as a retry that would overwrite the other writer. The four remaining ways submitted bytes could vanish are each an answer rather than an error — a duplicate or a lost response replays a per-`save_id` record, a note that already holds the bytes converges to a success that changed nothing (which is also how a repeated create answers), and a snapshot failure returns a non-nil `*SaveSourceResult` **beside** the error, because the bytes are on disk and a caller told only "failed" would resubmit against a revision this save already replaced. The record lives under `.bnotes/source-saves/`, written inside the same transaction and journaled with the note so an undone save is re-submittable, and that path is deliberately outside `vaultgit.InScope` so an idempotency key never becomes commit content; `pruneSourceSaveLedger`'s expiry sweep is the single direct `os.Remove` on the surface and carries its marker. `journal.go` is the seam every mutating operation begins and ends through, and its two halves are the whole write-safety contract stated as code. `BeginOperation(vaultRoot, operation, command, targets, opts...)` runs both refusals **before** the operation may create anything — `vault.GuardMutation` over the vault root plus every target the caller can name yet, then the `internal/vaultgit` preflight, which is what catches a vault left blocked by an earlier failure or holding a deletion nothing explains — and only then returns a `*Journal` whose recorder is created lazily on the first `Capture`. Putting both ahead of recorder creation, lock acquisition, directory creation, and temp files *is* the point: those artifacts are exactly what a refusal exists to prevent from existing. Targets that cannot be known yet are not a gap, because the same location policy is enforced again underneath every individual write; naming what is known only makes the refusal earlier. `Journal.Finalize` inverts the order deliberately — the undo manifest is written and made durable **first**, because an uncommitted finalized record is the only thing that authorizes committing a deletion (`internal/vaultgit` invariant 1), and the snapshot is taken **second**, staging exactly the paths that manifest names. An operation is a success only when both have happened, so a snapshot that fails after the bytes have landed is returned as a `*SnapshotError` (an alias for `vaultgit.SnapshotError`; `IsSnapshotFailure`, `CodeSnapshotFailed`, which `HTTPStatusForError` renders as a **distinct 500**) whose message states that the change is on disk and that further writes are blocked, and which **never claims a rollback** — nothing was rolled back, and inviting a retry of a write that already happened is how one capture becomes two bullets. A no-op captures nothing, finalizes nothing, and commits nothing, which is what keeps an empty commit off a clean vault. `operation` is a fixed token chosen by the code and is the only part of this that reaches a commit message; `command` carries the full `bn` invocation, note names and property values included, and never leaves the local journal. Two operator-authorized restores sit beside the ordinary mutations and go through the same begin/finalize pair: `undo.go`'s `Undo` replays a journal entry, and `backup_restore.go`'s `RestoreBackup` preflights, extracts, and then calls `Safety.CommitRestore` — the single **wholesale** snapshot in the system, justified only because the operator asked for the entire tree rather than for a set of paths, and therefore the one place where "an unrelated working-tree edit is not swept in" deliberately does not hold. `--wipe` empties the vault first, and what it skips is exactly what `internal/backup` excluded from the archive — `backups/` and `.git/`. That is not tidiness: neither is ever inside an archive, so removing either would destroy the only copy of something no restore could put back, and for `.git/` that copy is the history this very operation is about to commit into, plus every version the wipe just discarded.
- `internal/properties` — the reusable property index behind the web workbench. `typed.go` defines `TypedValue`, the transport form a caller sends when it wants a value written under a declared kind. `value.go` classifies a frontmatter value into a discriminated `Value` (`kind`/`text`/`value`/`items`/`supported`); anything YAML can hold but frontmatter text cannot safely reproduce (null, mapping, nested list) becomes `KindUnsupported` with a label and no reproducible text. `index.go` walks notes once to build per-property coverage, observed kinds, distinct logical values, note rows, and `internal/schema` violation counts, counting each logical value at most once per note so repeated list items never inflate statistics. `infer.go` proposes a `[frontmatter.properties.<key>]` block only for an unconfigured property whose observed values unanimously support one kind, and never infers `required` or `allowed`. The package deliberately does not depend on `internal/web`.
- `internal/pins` — the shared pinned-list core behind `bn pin`/`bn unpin`, `bn find --pinned`, `query.Pinned()`, the `/pinned` page, and the web pin endpoints. `Classify` maps a raw `pinned` value onto `NotPinned`/`Ranked`/`Unranked`: only an absent key and the YAML boolean `false` are unpinned, so a hand-written `pinned: true` or `pinned: "high"` is a pin carrying no rank that sorts after every ranked pin. `List` orders a vault's pins and silently skips a note it cannot read, cannot parse, or that falls outside the root, so one hostile note cannot hide the whole list. `PlanAppend`/`PlanMove` return `Assignment`s only — the package never writes — and fall back to a whole-list renormalize (`Plan.Renormalized`) when the float gap between two ranks is exhausted; `midpoint` and `nextRank` stay unexported so no caller can bypass that fallback. In `internal/web`, note-pin identifiers are `notePin*`/`pinnedNotes*` because `pinnedConfig`/`configPin` already mean *configuration* pinning there.
- `internal/index` — a persistent cache of note bytes keyed by the revision they were read at, so a repeated vault load pays a stat per note instead of a read per note. **It saves the read and not the parse**: every `Load` parses a fresh `*vault.Note` out of each walked note's bytes whether they were just read or served from the cache, so a warm load still runs `frontmatter.Parse` once per note. `BenchmarkDirectLoad`/`BenchmarkColdIndexLoad`/`BenchmarkWarmIndexLoad` time the three paths over a 500-note vault and `TestLoadCostsAreOneReadPerMissAndOneParsePerNote` counts what each performs — reads through the `WithReader` seam, parses through the unexported `Index.parseNote` field that exists for exactly that count. It is a **leaf package**: it may import `vault`, `config` and `frontmatter`, it consumes a `*vault.Vault` and produces `[]*vault.Note`, and it stops there — the same one-way contract `internal/properties` holds by deliberately not depending on `internal/web`. It must never import `query`, `queryexpr`, `properties`, `schema`, `noteops`, `cockpit` or `web`, all of which are consumers of the note slice it returns; `TestPackageLayering` pins that over non-test files, and `parity_test.go` reaches up into `queryexpr` on purpose to evaluate real queries against both load paths. `Load` runs `v.Walk(vault.WalkFilter{}, ...)` and nothing else, because `Walk` is the sole encoding of hidden-directory pruning, the ignore list, the templates directory, and symlink rejection — a hand-rolled `filepath.WalkDir` here would fork all four. Per file it stats, treats the cached entry as clean only when size *and* mtime match *and* that mtime is older than a **2s non-configurable `staleWindow`**, and otherwise re-reads and re-hashes; entries the walk did not visit are dropped, and `Result.Changed` reports whether note contents differ from the previous observation. The stale window is the package's sharpest edge: `vault.Note` carries a `SourceHash` precisely so a concurrent external edit is rejected rather than silently overwritten, but size+mtime cannot see an edit that lands inside one mtime tick while preserving byte length — which is exactly `sed -i s/draft/done/` on a filesystem with one-second mtime granularity. Every snapshot parses a **fresh `*vault.Note`** from the immutable cached `[]byte` rather than sharing a `Note`, because a `Note` is mutable and callers treat a returned snapshot as immutable. State lives in `<vault>/.bnotes/index/` and the locking contract is in `docs/internals/locking.md`. It **self-heals silently**, deliberately inverting `internal/recall`'s fail-closed state store: `recall.json` holds irrecoverable user intent, the index holds none — every byte is a pure function of the vault — so a missing, unreadable, non-regular, undecodable, wrong-version, wrong-root or internally inconsistent state file is discarded and rebuilt. Two hard rules follow: an index failure is **never** a request error (degrade to a direct load, log once per failure class per process), and disk-write failures are ignored entirely. A cached entry records `len(data)`, **not** the size the preceding `os.Stat` reported: the two differ only when a writer lands between the stat and the read, and taking the stat's value there both writes an entry `validEntry` rejects and can pair the new file's size and mtime with the old file's bytes — the stale read `clean` exists to prevent. Its only production caller is `internal/web`'s `noteSource` (`internal/web/state.go`): `newVaultState` defaults to `indexNoteSource` and falls back to `directNoteSource` if the index cannot even be constructed, the index reads through a reader that keeps `internal/web`'s bounded-read and quarantine rules, and a note quarantined *after* it was cached is re-checked at the source because a cache-served entry is never read. A test that injects a `noteLoader` gets the direct path by construction, since the index reads bytes itself and would silently ignore the loader. `bn index --status` / `--rebuild` (`internal/cli/index.go`, `index.Stat`, `Index.Reset`) is the whole user-facing surface, and `--status` never rebuilds.
- `internal/vaultgit` — the internal Git safety engine: it snapshots the vault into a local Git history after every change so that every version of every note stays recoverable, and pushes that history to a private remote. It exists for the same incident `docs/internals/locking.md` opens with — a note lost when a write vacated its destination and synchronizing storage propagated the vacancy back as a deletion — and it is the layer *below* that refusal, the one that survives whatever a write, a filesystem, or an external tool does that nobody anticipated. It is **not a Git porcelain and has no user-facing surface**: nothing in it reads or writes a note, it stages exact paths, builds a tree, writes a commit, and moves one ref. `Open(ctx, vaultRoot, Options)` returns `ErrUnmanaged` for a vault that is not the top level of its own repository — a vault with no `.git`, a `.git` *file* (a worktree or submodule), or a vault nested inside a larger repository, all of which the engine leaves entirely alone rather than half-managing. Everything else is a typed `*SafetyError` carrying a `Kind`, the operation, the paths, and object names but **never note contents**, and `Kind.blocking()` is the single place that decides which failures latch. Six invariants govern it and `doc.go` states them in full:
  1. **A deletion is never committed unless something proves it was intended.** An addition or a modification only ever adds content to the history and needs no proof; a deletion removes the last copy from the tip and needs one — an *uncommitted* finalized `internal/journal` record whose `Before` hash and size equal what HEAD holds for the path and whose `After` is `missing`. Only uncommitted records count, and that restriction is the whole design: a record already in the history describes a transition that already happened, so honouring it would let delete-recreate-delete-by-hand pass as intended. Binding the proof to the same pending change set puts the record and the deletion it explains in one commit, so the history always carries its own justification. Classification is deliberately coarse and refuses what it does not recognize (`classify.go`): a type change, a rename pair, an unmerged entry, or a status code the parser does not know refuses the **whole** pass rather than the one path, because a wrong guess here is how a note stops being in the history. A rename needs no special case — the delete side is an ordinary proven deletion and the new path an ordinary addition — which is why `git status` is run with `--no-renames` against an index seeded fresh from HEAD.
  2. **A local safety failure is durable and fails closed.** An unexplained deletion, a classification ambiguity, a ref compare-and-swap that cannot be retried safely, or a failed local commit writes `blocked.json` and `Preflight` refuses every later mutation until `ClearBlock` (or a person) removes it. **The marker is an optimization for reporting, never the mechanism**: if writing it fails, the condition is still on disk and the next preflight re-derives the same verdict from the working tree. A marker that is corrupt, truncated, or carries an unknown version keeps refusing rather than silently re-enabling mutations — the deliberate inverse of `internal/index`'s self-healing, and the same fail-closed posture as `internal/recall`'s state store, for the same reason: this file records something that cannot be re-derived cheaply and must not be discarded on doubt.
  3. **Remote availability is not a correctness input.** A push failure is retried with backoff (30s doubling to a 5min cap) and recorded in `push.json`; it never writes `blocked.json` and never prevents a local commit, because a vault that stops accepting edits when the remote is down is a worse vault. Conversely `Push` is never called from the immediate mutation path — a note save must not wait on a network round trip. `push` is run with `--porcelain --atomic` and **never** `--force`.
  4. **The user's index is theirs.** Every operation stages into a private `GIT_INDEX_FILE` seeded from HEAD and deleted afterwards, so a snapshot can never absorb what the user had staged and a `git add` they ran by hand is never committed by us. The seeded index also has no stat cache, which is what makes classification a full content comparison and therefore deterministic. After a successful commit the real index is refreshed for the exact committed paths and only where its entry still matched the *old* HEAD; that refresh is cosmetic (it keeps `git status` from showing our own commit as a staged revert) and its failure is never an operation failure.
  5. **No note *content* reaches a command line, a commit message, or a log, and a note *path* reaches one only where it cannot be read as syntax.** Git is invoked as an argv array with a controlled environment and never through a shell — the same argv-only posture as `internal/agent`. `stageAdd`/`stageRemove` hand `update-index` their paths NUL-delimited on stdin, so a leading dash, a newline, or a comma in a note name is data rather than syntax there. Four call sites do put a path on argv, and each disarms it differently rather than by exclusion: `ls-tree` and `ls-files` take pathspecs after `--` under `GIT_LITERAL_PATHSPECS`, `hash-object` takes a file operand after `--`, and `setIndexEntry` uses `update-index --cacheinfo`'s three-argument form, whose operands are consumed positionally — the newer `<mode>,<oid>,<path>` form splits on commas and would silently record a truncated path for a note whose name contains one. Local plumbing runs hermetically (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_LITERAL_PATHSPECS`, `LC_ALL=C`, `TZ=UTC`) because a global `core.excludesFile` would change what `status` reports; a push deliberately keeps the user's global config and `SSH_AUTH_SOCK`, since that is where an SSH command or a URL rewrite lives. Commit messages are the fixed shapes `brainnotes: <operation> [<journal-id>]` and `brainnotes: autosave <RFC3339 UTC>`, with the operation reduced to a bounded `[a-z0-9-]` token rather than escaped. In particular **`journal.Entry.Command` holds the full `bn` invocation, including note names and property values, and must never be used to build a message.**
  6. **An interrupted snapshot is distinguishable from one that never started.** Invariant 2 covers failures the engine *observed*; a process that is killed observes nothing and writes nothing, and what it leaves behind would otherwise look like a healthy vault. So every snapshot writes and fsyncs `intent.json` (`intent.go`, `state.go`) before its first index write, rewrites it with the new commit's object name **before** `update-ref` is attempted, and removes it only after the ref has moved and the directory naming it is durable — which is also why `writeAtomic` now fsyncs the state directory after every rename, so a marker or a record cannot vanish in a crash and be read as "nothing was wrong". The record carries the operation, an operation ID, the phase, the observation time, the ref, old/new object identifiers, and the paths (capped at 256 with an untruncated `path_count`), plus manual recovery steps — **never note contents**. A record found at startup means an operation began and never finished, and mutations stay refused until recovery proves the recorded commit is *reachable* from the branch (`git merge-base --is-ancestor`; reachability rather than equality, so another writer committing on top does not un-land the snapshot underneath) or a person clears it — `ClearBlock` clears the marker and the record together, because that is one act. An unreadable or unknown-version record refuses rather than self-heals, and for a sharper reason than the marker's: proving a snapshot landed *requires* the object name those bytes were supposed to hold. This is what covers the one case invariant 2 cannot: a local commit failure whose `blocked.json` write **also** fails leaves the record standing, and the vault stays refused across a restart on a spotless working tree. Conversely, a failure to *create* the record prevents the snapshot attempt entirely and is deliberately **not** a block — nothing was written, so the next mutation may retry. `Open` reads the record (one failed file open on a healthy vault) and takes `safety.lock` only to adjudicate one it finds; a busy lock means the record belongs to a live operation, so it is left alone.

  `InScope` (`scope.go`) is a fixed in-code policy, not a read of `.gitignore`, deciding which vault-relative paths BrainNotes may *add*: Markdown, attachments, `brainnotes.toml`, `.bnotes/journal/**`, and the `brief`/`cockpit`/`recall` sidecars, excluding `backups/`, `.codegraph/`, `.vault-cache/`, `.bnotes/index/**`, `.bnotes/locks/**`, and the `.note-*.tmp`/`.txn-*.tmp` scratch names `internal/vault` stages through. Anything already tracked in HEAD is in scope regardless of the policy, in both directions: a tracked file whose modification we skipped would drift out of the history silently, and a tracked file whose deletion we skipped would leave an unexplained deletion pending forever. Two consequences of the proof rule are subtle enough to be tested by name. An unreadable note is a reported `SkippedPath` rather than a block **only on the external-change scan** (`CommitPending`), which offers to record whatever the working tree happens to hold, so leaving one path out costs the history nothing it held a moment ago; every other entry point is a caller naming exact paths, and there an unstaged required path is a `KindCommitFailed` block rather than a success that quietly omits it, with `CommitResult.Unrecorded()` letting the caller confirm that for itself. A path the engine can read that Git still refuses to stage is neither case — it is the repository failing, it would hit the rest of the pass too, and it is fatal everywhere including the external scan, which is what keeps an unwritable index from looking like an empty vault. Skipping is otherwise purely additive — but a skip in a pass that also holds removals **defers every removal in that pass *and* unstages the journal records that prove them**, since a proof counts only while uncommitted and committing the record without its deletion would leave the next pass with an unexplained deletion the engine had already approved. And a ref that moves between planning and landing is retried, never forced: the commit is landed with `update-ref <ref> <new> <old>`, and a failure is re-read to distinguish a genuine compare-and-swap loss (retry, up to 3 attempts) from a ref that did not move (a real commit failure, which latches). Operational state lives under `<git-dir>/brainnotes-safety/` — inside `.git`, so it is never tracked and never walked by `vault.Walk` — and the locking contract is in `docs/internals/locking.md`.

  `OpenHistory(ctx, vaultRoot, HistoryOptions)` (`history.go`) is the package's **read-only second door**, added for `internal/vaultexport` and deliberately not a `Manager`. Opening a `Manager` is a *writing* act: it takes the vault lock, recovers an interrupted intent, and publishes the autosave policy into `watch.json`, which is the record that decides when the next external-edit autosave is due. A reader that acquired one would be an observation with the power to disturb what it observes — asking what there is to export would move somebody's next save. A `History` takes no lock, writes nothing, and never reads the working tree: `Tip`, `Contains`, `CommitsAfter`, `Inspect`, `Changes`, `Tree`, `Blobs`, `BlobDigest`, and `EntryKinds` all read committed objects, so an uncommitted edit is invisible **by construction** rather than by a filter a caller has to remember. `HistoryOptions` is not `Options` for the same reason: an author identity, a remote, and an autosave policy are all inputs to writing, and accepting them would invite a caller to believe they meant something. The two doors share `openWorkingTree` and `resolveGitDir` so they cannot disagree about what a managed vault is, and both refuse a detached HEAD — a reader has no stable thing to record a cursor against. Three details are load-bearing and tested by name: `CommitsAfter` is **oldest-first and unbounded**, because `rev-list -n` selects *before* `--reverse` reverses and a bounded query would hand back the newest few in oldest-first order, which reads as correct and replays a history backwards from the middle; rename detection is **off** in `Changes`, because a rename reported as a pair would let a deletion travel on an addition's evidence when each side has to be authorized on its own terms; and every object name a caller supplies goes through `checkObjectNames` first, so a corrupt cursor read back off a disk fails as a corrupt cursor rather than reaching `rev-list` as `--all` or as a range of its own devising. `ErrUnbornBranch` keeps "this vault has no history yet" — an ordinary state, meaning there is nothing to export — apart from "this repository is broken".
- `internal/vaultstate` — the one write path for durable sidecar state: `<vault>/.bnotes/brief.json`, `cockpit.json`, and `recall.json`. Those files are not notes, but losing one loses a person's work all the same — a snooze, a dismissal, a day's brief selection — so `Save(vaultRoot, operation, path, data, perm)` gives them the three guarantees a note write gets, in one place rather than three times over in three packages that had each grown their own temp-file-and-rename: the location policy refuses before the state directory exists, the replacement is the path-continuous one from `internal/vault`, and the result is snapshotted staging **that exact path and nothing else**. `operation` is a fixed token the calling package chooses (`brief-state`, `cockpit-state`, `recall-state`), never anything derived from user input or from the state's own contents. A vault with no content history (`ErrUnmanaged`) keeps the write and skips the snapshot — an un-initialized vault, a fixture, or a copy is a normal thing to run against, and refusing to remember a snooze there would be a worse answer than not versioning it — while a snapshot that fails *after* the bytes landed is a `*vaultgit.SnapshotError`, for the same reason `noteops.Finalize` reports one. `prepareDir` judges only the **last** component of the state directory and the state file, refusing a symlink there because that is how a write the location policy just approved gets redirected somewhere it did not approve; an ancestor symlink is fine and must be, since `/var` is one on macOS and every `t.TempDir` lives under it. Deliberately **not** here: the generated index under `.bnotes/index` and the lock files under `.bnotes/locks`. Both are derived state a vault rebuilds on demand, neither carries user intent, and committing either would put a commit on every read-shaped operation — they stay out by path, which `vaultgit.InScope` enforces rather than convention here.
- `internal/vaultsync` — the versioned wire protocol and enrollment state for two-way synchronization between two replicas of one vault, and **nothing else**: no transport, no application, no conflict resolution, no authentication. It decides what a package *is*, who a vault will accept one from, and what a receipt means; moving bytes is Syncthing's job and writing them into a live vault belongs above this. It is a **leaf package** — its production files import `config`, `vault`, and `textnorm` and must not import `vaultgit`, `journal`, `index`, or `noteops`, because deciding what a package may *contain* must not depend on what the content history happens to track. Its *tests* do import `vaultgit`, and only to pin the divergence described next.
  - **The portable scope is deliberately narrower than the Git scope** (`portable.go`), and that divergence is the package's sharpest edge rather than an oversight. `vaultgit.InScope` tracks `.bnotes/brief.json`, `cockpit.json`, `recall.json`, and `.bnotes/journal/**` on purpose: they are this machine's work and they belong in this machine's recoverable history. None of them may travel — a peer that received another device's undo journal would be handed a recovery history describing files it never had, and a peer that received `recall.json` would be handed the other device's reading activity. So `Classify` excludes `.bnotes` **wholesale**, with no allowlist and no journal exception, alongside `.git`, `backups/`, `.codegraph/`, `.vault-cache/`, the root-level `brainnotes.local.toml`, `.DS_Store`, and the `.note-*`/`.txn-*` scratch names. `TestPortableScopeIsNarrowerThanTheGitScope` asserts both directions — each machine-local path **is** `vaultgit.InScope` and **is not** `Portable` — so implementing the transport allowlist by calling `InScope` fails loudly and names the file it would have sent. The third class is `ClassMalformed`: an empty, absolute, drive-rooted, backslash-rooted, NUL-carrying, or unnormalized path (anything where `rel != path.Clean(rel)`, which covers `..`, `.`, `//`, and a trailing slash) is a path this vault will not interpret at all, and it is refused as `ErrPathTraversal` rather than quietly cleaned.
  - **Case and normalization collisions are a protocol-level refusal, not an apply-time surprise.** The two devices are macOS (case-insensitive APFS, which stores NFD and answers an NFC lookup with it) and Linux (case-sensitive ext4, byte-exact), so `Notes/Alpha.md` and `notes/alpha.md` are two files on one side and one file on the other. `CollisionKey` folds a path to what the *receiving* vault would resolve it to — NFC, then **case-fold**, then **NFC again**. Each step earns its place. The fold is a real Unicode case fold rather than `strings.ToLower`, because the two disagree exactly where a filesystem does not: `ToLower` maps `U+1E9E` (capital sharp s) to `U+00DF`, so `Strasse.md` and the `U+1E9E` spelling of it would get two keys where a case-insensitive volume holds one file, while full folding sends both — and `U+00DF` itself — to `ss`. The trailing normalization earns its place twice, and the *leading* one covers neither job — it only makes the caller's choice of spelling irrelevant, on both sides, before the fold runs. First, folding does not preserve NFC: 24 already-NFC code points fold to a sequence that is not, `U+0390` among them (its fold is `U+03B9 U+0308 U+0301`, which NFC composes straight back), so a fold-and-stop key would be neither idempotent nor comparable against the NFC paths every other layer holds — `TestCollisionKeyIsIdempotent` pins that with one code point. Second, it decides collisions, which takes two: folding `U+017F` (long s) to `s` puts a base in front of a following acute that has a precomposed form with it, so `U+017F U+0301` and `U+015A` reach one key only after the third step. `TestCollisionKeyMergesAFoldThatComposesWithTheNextMark` pins that, and both tests assert the inverse too, so neither can pass once the step stops mattering. `Validate` refuses a package whose changes collide under that key, across operation boundaries as well as within one, so the ambiguity is a `ErrPathCollision` at the producer rather than one file silently overwriting another at the receiver.
  - **Enrollment is the identity layer** (`enrollment.go`, `enrollment_store.go`). A vault holds one `.bnotes/sync/enrollment.json` — the same path `config.VaultEnrollment` stats to decide whether the ownership rules apply, derived here from `config.EnrollmentMarker` so the two cannot drift — carrying a vault identity shared by both replicas, a per-device identity, an epoch, and the peer list. Acceptance is **symmetric**: `Establish` mints the baseline, `Join` adopts the invited vault identity and records its inviter, and the inviter must `RecordPeer` in turn, so a one-sided enrollment is a vault that sends and is never answered. The baseline is *verified* rather than assumed — the record is read back and compared field by field, and a mismatch is `ErrUnverifiedEnrollment` — because every later exchange is addressed by these bytes. The three load failures stay distinct all the way out (`ErrNotEnrolled` for an ordinary unenrolled vault, `ErrCorruptState` for undecodable or self-contradictory bytes, `ErrUnsupportedVersion` for a newer build's record), since collapsing them would make "does not synchronize" and "identity is damaged" look the same to the layer deciding whether to offer enrolling. Writes take `vault.LockPaths` around the whole read-modify-write and go through `vault.GuardMutation` + `vault.WriteStateFile` rather than `vaultstate.Save`: Save's third guarantee is a snapshot into the content history, and this path is outside `vaultgit`'s allowlist by design. Save would not *refuse* it — `CommitPaths` drops an out-of-scope path and returns an empty result, so `Save` would run a preflight and then report success with its third guarantee silently inapplicable, which is a worse failure than a refusal because a caller reading Save's contract would believe the record was snapshotted. The two guarantees that *do* apply are taken here rather than skipped.
  - **The epoch is the restore-from-backup answer.** A vault restored from a backup has a history its peer's channel no longer describes, and applying a package whose expected content hashes name notes it no longer holds would report success while writing the wrong bytes. `AdvanceEpoch` makes every in-flight package `ErrStaleEpoch` instead. The refusal is symmetric: a package from a *later* epoch is `ErrEpochAhead`, because a vault that has not learned of a re-enrollment is not entitled to an opinion about what that package assumes.
  - **A package is immutable, and the manifest is the commit point** (`protocol.go`, `publish.go`). `Manifest` carries the format token, the package and vault identities, the origin device, the epoch, the origin's own `Sequence` (per-origin, since the two devices publish concurrently and never coordinate a counter), the `Requires` dependencies, the preserved multi-file `Operations`, and the `Payloads` inventory. `CreatedAt` is descriptive and **nothing orders on it** — two devices' clocks disagree, and ordering that trusted them would be a lottery, which is what `Sequence` and per-path `Predecessors` replace. A delete is an `ActionDelete` **tombstone** carrying the same identity, predecessors, and expected prior state a write does, so a deletion is causally ordered against a concurrent edit and can lose a conflict instead of silently winning one; a package with no tombstone for a path says nothing about that path. `Publish` validates, checks the supplied bytes against the inventory, then creates the package directory with an **exclusive `os.Mkdir`** — that is the immutability guarantee and it is atomic — writes and fsyncs every payload, and writes the manifest **last**. Bytes before the record naming them, the same ordering `internal/vault` uses for its transaction intent: a directory with no manifest is a publication in progress, and `ReadManifest` reports exactly that. The fsyncs run at **every level**, which is the part that is easy to stop one short of — a name is durable only once the directory holding it has been fsynced, so the payload files are committed by fsyncing `payloads/`, `payloads/` itself by fsyncing the package directory (before the manifest is linked, or the manifest could outlive the directory it names), the manifest by fsyncing the package directory again, the package by fsyncing the channel, and the channel, on a first publication that had to create it, by fsyncing the *parent* of every directory `ensureChannel` had to bring into existence — fsyncing the created directories themselves would commit nothing, since a name lives in the directory above it. `TestPublishWritesEveryPayloadBeforeTheManifestThatNamesThem` pins the *order* by comparing the modification times the filesystem recorded, because the concurrent reader test cannot: a manifest linked before its payloads is answered with `ErrIncompletePackage`, which a polling reader correctly treats as "still arriving". The nine `//bn:direct-write` markers in that file are every *direct* write this package makes: no other file here calls an `os` write function at all. Receipts reach the disk too, but through `publish.go`'s own `publishOnce`, so the nine cover them; the only writing that leaves this file is the enrollment record, and it goes through `vault.WriteStateFile` and `vault.LockPaths`, which carry their own guarantees and need no marker. Each of the nine names the guarantee already in force.
  - **Three separate questions, in a fixed order** (`accept.go`), because their remedies differ: `Validate` says the bytes are a package at all (`ErrUnsupportedFormat` checked **first and alone** — a manifest from a format this build does not know may mean anything by the fields it shares with this one), `CheckEnrollment` says it is this vault's to judge (`ErrWrongVault`, `ErrUnknownPeer` — including a package claiming to originate from this device, which means a transport is delivering a channel back to its owner — `ErrStaleEpoch`, `ErrEpochAhead`), and only then `VerifyPayloads` hashes megabytes. A misrouted package must not cost a full verification. Every payload failure is `ErrIncompletePackage`, **including an unlisted extra file**: a transfer in progress leaves both shapes behind — a payload not yet copied, and the transport's own temporary file beside the ones that arrived — and both mean *wait*. Payloads are `Lstat`ed and required to be regular files, since a symlink in a package directory is a path chosen by the producer and resolved on the consumer. `ReadPayload` re-verifies rather than trusting an `Accept` that ran a moment ago, because the transport is still running.
  - **A receipt is the only statement that a change landed** (`receipt.go`). A completed file transfer says bytes reached a disk; a package directory appearing says a publication finished; neither says a note in a live vault changed, and the producer must not drop its own copy on either. `Acknowledge` refuses the three ways a receipt would be a lie the peer acts on: a package this vault could not have accepted, an application with no local recovery-history entry behind it (`ErrNoRecoveryEntry` — the identity of the entry that can *undo* it is what makes the claim answerable by an operator and by the layer owning the recovery history, though not by this package, which cannot import `internal/journal` and so checks only that an entry is named), and an application that does not cover every path the package changed with the bytes the package said those paths would hold (`ErrIncompleteApplication`). `VerifyAgainst` is the producer's side, and it **re-runs the coverage check** rather than trusting that the minting side did: `Acknowledge` ran it on the applying device against an in-memory `Application`, which says nothing about a receipt that arrived as a file over a transport, possibly from another build. It fails safe by construction: an unrecognized receipt costs a redundant re-send, an accepted wrong one costs a change nobody has.
  - `Builder` assembles a manifest and its payloads together so the coupling between a change's resulting hash, its payload name, and the inventory entry cannot be right on the producer and wrong on a retry; payloads are **content-addressed** (`<sha256>.bin`), so a rename that writes one body at a new path carries it once. `sequence` is the caller's to choose and persist — nothing here remembers an export cursor. A payload name is a single path component with no directory structure at all, which is what makes "write the payload" incapable of writing anywhere but inside the package: the containment is in the format rather than in each reader's care. This package's tests are the first consumer of `internal/vaultfixture`'s `Pair` and `Clock`, which were built ahead of this work and used unchanged.
- `internal/vaultexport` — the **producer side** of synchronization: it turns this vault's committed Git history into `vaultsync` packages and remembers, durably, how far it got. It is the one place `vaultgit` and `vaultsync` meet, which is exactly why neither of them may import it — `vaultsync` is a leaf by design and `vaultgit` knows nothing about what travels. `Export(ctx, Options)` is safe to call repeatedly and safe to interrupt; `LoadState`, `RecordImport`, and `Reset` are the rest of the surface. What it is **not**: a transport (Syncthing moves the channel), an applier (that is the consumer side, and it calls `RecordImport`), and a conflict resolver.
  - **A commit is an operation, and only a committed one.** Every package is built from `vaultgit.History`, so a half-typed note is invisible by construction and an uncommitted edit stays pending until the autosave that already exists commits it — the export changes *nothing* about when that happens. One commit becomes one `vaultsync` operation whose identity is `vaultsync.DeriveOperationID(vaultID, commit)`: a **derived** identity, the single deliberate exception to `NewOperationID`'s "never re-derived" rule, because a pass that published a package and died before recording it must re-derive the same name rather than mint a second identity for a change the peer may already hold. A merge commit halts (`ErrUnsupportedHistory`) — a linear replay cannot express one — and so does a symlink or a submodule entry (`ErrUnsupportedEntry`), because the protocol describes file bytes and silently dropping an entry would tell the peer a tree it does not have.
  - **The cursor is one file, written once per package** (`state.go`). `.bnotes/sync/export.json` — inside the directory `vaultsync.Portable` excludes wholesale, and its path is *derived* from `vaultsync.StateDir` so moving the state directory cannot leave a file naming every path in the vault behind as portable content. Cursor, sequence, path ledger, and import ledger are one record rather than four files because advancing past a commit and consuming the import records that commit used are **the same decision**; a crash between two files would either replay an operation or lose the provenance that stops it echoing. It goes through `vault.GuardMutation` + `vault.WriteStateFile` rather than `vaultstate.Save`, for the reason the enrollment record gives — Save's third guarantee is a snapshot, and this path is outside the content history by design — and that is what keeps this package **out of `internal/audit`'s `approvedPackages`**: no production file here opens, creates, renames, or removes anything.
  - **A reservation is what makes an interrupted publication recoverable rather than ambiguous** (`publish.go`). The sequence number and package identity are durable *before* `vaultsync.Publish` is called, so the next pass finds exactly one of three states and each has a different right answer: no directory means the number was never spent and is reused; a directory with a valid manifest means the publication **landed** — the manifest is the commit point and the peer may already hold it — so it is adopted, the ledger rebuilt from the manifest itself, and nothing sent twice; a directory *without* a manifest is inert forever, so the sequence is burned, reported in `Result.BurnedSequences` rather than swallowed, and the commit re-exported under a fresh identity. A reserved directory carrying another producer's package is `ErrChannelConflict`: continuing would interleave two writers' sequences under one device identity.
  - **A first export is pinned, not re-read** (`baseline.go`). The baseline describes the whole portable tree and may span several packages, and `State.Baseline` pins the commit it is describing. Resuming against a newer tip would skip every path an earlier slice already carried — the path ledger doubles as the progress record — so an edit to one of those paths made in between would never travel at all. Pinned, the baseline finishes describing the vault as it was, sets the cursor to that commit, and the edit travels afterwards as the commit it actually was. The cursor stays empty until the last slice lands, because a partially-sent commit is not accounted for.
  - **A deletion travels only on proof** (`authority.go`), which is `vaultgit`'s first invariant restated for the wire rather than loosened. A tombstone is the one change a peer cannot undo by re-reading its own copy, so it requires an `internal/journal` undo manifest **in the same commit** describing the exact bytes being removed — hash and size both. A record merely present in the history proves a transition that already happened and must not explain a different commit's deletion. `Options.AuthorizeDeletions` is the counterpart of `vaultgit.CommitRestore`'s exception — a restore commits deletions on a person's authority rather than a journal's — and is **never persisted**: the approval is that caller's, for that pass. Removing private state needs no authority, because no peer is being told anything.
  - **Imported operations do not echo.** The applier calls `RecordImport(root, journalEntryID, Import{...})` *before* the applying operation's journal entry is finalized and committed — one-directional and load-bearing: recorded after, a crash in between leaves a commit the exporter cannot recognize as the peer's and publishes the peer's own change back under this device's identity, which the peer applies, commits, and (having no record either) returns. Recorded before, the failure is a ledger entry for a journal entry that never commits, which costs one stale map entry and changes nothing.
  - **Two paths that are one name on the peer never both travel** (`checkPathCollisions` in `publish.go`, `collision.go`). `vaultsync`'s `manifestScan` refuses two things *within* one manifest — a `CollisionKey` clash between two paths, and a path whose folded name is a directory another path needs — and that is everything a receiver can check for itself. It is not everything there is, because this producer emits **one package per commit** and a baseline in several slices. `Archive/Notes.md` sent last year and `archive/notes.md` sent today are two manifests that each validate and one file on a case-folding or normalizing replica, where the second silently overwrites the first and every receipt says the transfer succeeded; a file `Archive` sent last year and `archive/notes.md` sent today share no key at all and are still one name the replica cannot make both a file and a directory. Only the producer holds both halves, and it holds them in the path ledger, so `collisionIndex` restates **both** of `manifestScan`'s refusals over that ledger — `files` keyed on a sent path's folded name, `dirs` keyed on each folded directory a sent path needs — and reuses `vaultsync.ErrPathCollision` rather than minting a second name for one condition. The **liveness gate** is what keeps it from refusing the legitimate case: a ledger entry survives its own deletion (a resurrection must name its tombstone), so a note removed and later recreated under a different fold — or replaced by a directory of the same folded name — is a ledger clash and not a real one, because the peer applies the tombstone, then the write. `vaultgit.History.EntryKinds` asks the commit what it holds under each rival, and **every** indexed rival is asked in one batched question, not the first: the recreate case is exactly what puts two names under one key legitimately, and checking one of them arbitrarily makes a later real clash publish or halt at random. It asks for the object *kind* rather than for a yes or no because a name that was a file and is now a directory is occupied and holds no file: a `rivalAncestor` — a sent file under a name the outgoing path needs as a directory — whose name now holds a tree is precisely the legitimate replacement, and a gate that could only learn "occupied" would refuse it forever. `EntryKinds` resolves `<commit>:<path>` through `cat-file --batch-check` rather than passing the names to `ls-tree`, and that is load-bearing here rather than an optimization: `ls-tree` operands are pathspecs, so asking it about `archive` and `archive/notes.md` together makes it descend *through* the directory instead of reporting it, and this gate's whole job is to compare a name against the names underneath it — the dropped entry would read as "that name is free". A name holding a newline or a carriage return cannot be framed on that stdin — Git reads the first as two records and eats the second — so those fall back to one single-operand `ls-tree` each, where there is nothing deeper alongside to descend through; `entryKindOfMode` and `normalizeEntryKind` fold the two roads' vocabularies together so a gitlink is not `commit` on one and `submodule` on the other. A name holding a NUL gets no answer at all — it can be framed on neither the stdin nor an argv, and a truncated name Git answers *confidently* about is worse than an error. The batch's *first* question is the commit's own tree, because `cat-file` answers `missing` for every path of a commit that does not exist and exits zero — and "the tree holds none of these names" is the answer that publishes, so a wrong cursor must not be able to read as a clean one. This halt is the one no edit at the tip clears — the clash is in a commit that already happened — so it names both paths and asks for a rename. `Reset` does drop the path ledger along with the cursor, but it re-baselines from the current tree: if both names are still live there the baseline refuses in turn (`TestBaselineSlicesCollideWithEachOther`), and if they are not, the peer keeps whatever this device sent it under the older name, which is the state the ledger existed to remember.
  - **Five halts are refusals of the *record*, not faults**, and each says which record is wrong: `ErrHistoryRewritten` (a cursor the branch no longer contains — rebased, amended, or reset out from under the reader), `ErrEpochChanged`, `ErrBranchChanged`, `ErrIdentityChanged` (a state file copied from the other replica), and `ErrCorruptState`/`ErrUnsupportedVersion` on the record itself. `Reset` is the remedy for the first two: it re-baselines, keeping the identity, the sequence — a peer that saw the old stream must see the new one as later — and the import ledger, whose entries are still true and whose loss would make the next baseline claim the peer's own content as this device's.
- `internal/vaultimport` — the **consumer side** of synchronization, and the mirror of `internal/vaultexport`: that package turns this vault's committed history into packages, this one turns a peer's package into this vault's own history. `Drain(root, Options) (*Drained, error)` is the door a synchronization command calls — the whole incoming channel, in causal order, with what it held back and why — and `Apply(root, packageDir, Options) (*Result, error)` is the single-package primitive underneath it, which stays exported because one package is still the unit everything else is said about. `Recover(root, Options) (*Recovery, error)` completes the automatic surface, and `Apply` and `Drain` both run it themselves, so a caller never needs it. `Preview(root, packageID string, Choices) (*Plan, error)` and `Resolve(root, packageDir string, *Plan, Options) (*Resolution, error)` are the two doors a *person* comes through, and they are separate for the reason a dry run is: what a decision changes has to be sayable before it is made. It re-answers none of `vaultsync`'s questions and writes no byte that did not go through `vault.FileTxn`, `noteops.BeginOperation`/`Finalize`, and `vaultgit`'s snapshot — so it sits above all three and nothing imports it. What it is **not**: a transport, and a *merge algorithm* — it detects a conflict, says which of six kinds it is, keeps the remote branch, the local branch and the baseline, holds the operation, and then carries out whichever of four decisions a person made about it; choosing is still a person's act, and `ManualMerge` takes the reconciled bytes rather than computing them. It **is** idempotent, across both a redelivery and an interruption, and the sub-bullets at the end of this entry are how.
  - **Nothing is applied that was not accepted, and the bytes are checked twice.** `Apply` begins at `vaultsync.Accept`, so a malformed manifest, a package addressed to another vault, one from an unenrolled device, one from another epoch, and one whose payloads have not all arrived are each refused before any of this vault's content is touched — and those refusals are returned **unwrapped**, under `vaultsync`'s own sentinels, because the remedy is the same wherever the condition is noticed and a second name would make one problem look like two. Every payload is then re-verified by `vaultsync.ReadPayload` as it is read, and all of them are read *before* the transaction is planned: the transport is still writing into that directory while this code runs, and "checked a moment ago" is not "checked". Two things do run ahead of `Accept`, and both are about earlier runs rather than this package: the import guard is taken, so a package delivered while another import is running is `ErrImportBusy` before it is looked at, and an interrupted attempt is resolved, so the paths this package is about are settled before its preconditions are checked.
  - **One package is one local operation.** A package carrying two operation boundaries is `ErrMultipleOperations` rather than applied in pieces, and the reason is structural rather than a simplification deferred: a receipt names exactly one recovery entry, and `vaultexport`'s import ledger maps one journal entry to one peer operation and refuses a commit carrying two. `vaultexport` publishes one operation per package, so the refusal cannot fire against a package this project produces.
  - **A precondition failure leaves the contested content alone.** Each change's `ExpectExists`/`ExpectSHA256` becomes a `vault.FileExpectation` verified under that path's own lock, and `FileTxn` stages every replacement and checks every precondition *before* it touches a single destination, capturing the journal only once staging succeeds. So a package this disk disagrees with leaves the contested content exactly as it was, with no partial write, no journal entry, no commit, no receipt, and the package still in the channel — reported as `ErrConflict`, which is a fact about two devices rather than a fault. The peer, having had no receipt, still holds its own copy, which is what lets a later layer present both branches instead of losing one. The **qualification** is where the disagreement is noticed: `FileTxn` re-verifies its read-only requirements again around each individual change, so a configuration pin that fails mid-commit raises the same sentinel *after* the journal was captured — the content is compensated back, and the un-finalized entry directory it leaves is removed by `applier.unwind`, which runs the interruption resolution in-process on every failure path of an application and then returns the original cause unchanged. Such an entry has no manifest, so nothing undoes it, `journal.ListEntries` skips it and `journal.Prune` will never collect it, and its snapshots sit inside the content history's scope as pending additions forever — leaving one is residue nothing in the vault could account for. Using one code path for a conflict and a power cut is the point: they leave states that differ only in whether anybody is still there to look.
  - **The configuration is pinned for the whole commit**, which is session 3's composite pin applied to an import. `brainnotes.toml` is required unchanged unless the package is itself changing it (a transaction cannot both write a path and require it unchanged — and "the same path" is decided by `vaultsync.CollisionKey`, because a package naming `BrainNotes.toml` is writing the pinned file on the case-folding half of a Mac/Pi pair, where a literal comparison would make the transaction both write it and require it unchanged and refuse that package forever — the key is folded rather than resolved, so on a case-sensitive replica the same package drops a pin it could have kept, which weakens one import instead of breaking every one of them), and `brainnotes.local.toml` unconditionally — *including its absence*, since an overlay created mid-import would take effect over notes planned without it. This package supplies the pins; **`internal/vault` decides when they are checked**, and checks them at staging and again before and after every individual change. The first is the door these pins are refused at in practice and it costs nothing, because staging precedes every destination; the later re-checks are what make a mid-commit edit a rollback rather than a half-governed vault, and they are `vault`'s guarantee rather than something arranged here.
  - **Provenance is durable before the commit that needs it**, and the ordering is forced from both ends. `vaultexport.RecordImport` must land before the snapshot, or a crash in between leaves a commit the exporter reads as this device's own work and publishes straight back to the peer that sent it; and `Journal.EntryID()` answers the empty string until the first `Capture` — `noteops` creates the recorder lazily, so a refused operation leaves no entry directory — which makes reading it after `Commit` the proof that there is an entry to record *against*. `Commit` → `Journal.EntryID()` → `RecordImport` → `Finalize` is therefore the only correct order, and `EntryID` was added to `journal.Recorder` and `noteops.Journal` for exactly this — it is a promise about naming, never about existence. The identity itself is knowable earlier here, and deliberately so: `apply` mints it with `journal.NewEntryID` and pins it onto the recorder through `WithIDGenerator` (appended last, so it overrules a generator a caller supplied) *before* `BeginOperation`, because the attempt record has to name the entry before the first byte moves. That pin is the one place this package overrules its own `Options`: a recorder that minted a different identity would build an entry the recovery record cannot name, which is the exact state the record exists to prevent. When the ledger write itself *fails* there is no ordering left to choose: the peer's bytes are already on this disk, so the entry is finalized and snapshotted anyway (an applied change outside the recovery history is the worse failure) and both problems are reported together, with no receipt minted. That vault has an undoable commit the ledger does not recognize as imported, so the exporter will echo it once; the error therefore names the entry, the operation and the origin device — every argument the repairing `RecordImport` call needs.
  - **An acknowledgment is only minted for a durable, undoable change.** `vaultsync` documents that a receipt means durable application backed by a named local recovery entry, and that it can only check the entry is *named* — it is a leaf and cannot import `internal/journal`. This is the layer that can, so `journal.LoadEntry` reads the entry back off the disk before the receipt exists; mostly that is defence in depth, since a successful snapshot already loaded the entry to learn what to stage, and it is strictly load-bearing only in a vault with no content history, where there is no safety manager and `noteops` snapshots nothing. Every acknowledged hash is computed from what this disk holds now rather than copied from the change that asked for it, or the comparison `vaultsync.Acknowledge` makes would be the package against itself; a tombstone is `Lstat`ed, because a dangling symlink left at the name is still something occupying it. Failing to mint or publish a receipt does not unmake the change it would have described, so `Apply` returns the `Result` **alongside** the error there — journal entry named, `Receipt` nil. It is the one case where those two are not alternatives, and it is the *last* step rather than any post-commit step: a provenance record that could not be written and a snapshot that did not happen both return a nil `Result`, because each names the entry in the error itself (`recordProvenance` names entry + operation + origin; `*noteops.SnapshotError` names the entry and says the change is on disk). `finalize`'s remaining failures — nothing captured, a manifest the journal could not write — name a path or nothing, and are the defensive ones: reaching them means the recovery history is itself failing, which is exactly what a `Result` would have pointed at.
  - **A cleanup failure is not a failed import**, and this is the one place in the repository that treats `*vault.TxnCleanupError` as success. It means every destination durably holds what the package asked for and a scratch file beside one of them could not be unlinked. The interactive callers of `Commit` report that as a failed mutation, which is right for a command a person reruns; here, stopping would leave the peer's bytes on disk with no undo manifest, no snapshot and no provenance — the one state this package exists to make impossible — over a file that is safe to delete. It is carried out to the caller as `Result.Cleanup` instead. Classification is an **ordering** rather than a set (`classifyCommit`, tested directly because provoking five filesystem failures through a live `FileTxn` is not a test anyone would trust): `*TxnRollbackError` wraps the commit failure and `*TxnRecoveryError` wraps a join containing it, so the `errors.As`-based `IsTxnConflict` answers yes to both — asking the broad question first would report a half-applied package whose rollback failed as "nothing changed".
  - **One import at a time, decided by a wait-free guard that is also a liveness test.** `import.lock` lives in `vaultsync.StateDir()` — beside the record it guards, in the directory this package already owns and the content history already excludes — and is taken through `vault.TryLockPath`, **never** `vault.LockPaths`: that call takes the shared vault guard, and a large package's transaction escalates to the *exclusive* guard, so the import would deadlock against itself. Wait-free rather than queuing, because whoever holds it may be halfway through an application and a waiter would come out of its wait holding a package it read against a state file that has since changed; a second import is refused as `ErrImportBusy` before the package is read, having touched nothing. The second property is why the guard is a lock rather than a flag: an unresolved attempt in the state file cannot say whether the process that wrote it is still running — that is exactly what a crash makes unknowable — and a flock is the one signal an operating system withdraws when a process dies. Held guard means a live import and the attempt is none of our business; **free** guard beside a pending attempt means the writer is gone and the attempt is ours to resolve. Disjoint paths therefore buy no concurrency, which is the deliberate price: per-path concurrency would make that question unanswerable, and a retry is cheap next to a rollback over somebody's newer edit. The guard sits *upstream* of `vaultgit`'s safety lock, whose preflight takes it, checks, and **releases it before returning** — so the two remaining `vaultgit` fates are reachable only when something outside this package holds that lock: refused as `vaultgit.KindBusy` before any artifact existed, or **landed but not snapshotted**, where `FileTxn` committed the bytes, `RecordImport` recorded them, and the snapshot found the lock busy. The second is a `*vaultgit.SnapshotError`, and because that type unwraps to the engine refusal it carries, `IsBusy` is true of it too — so a caller distinguishing "nothing started" from "on disk, undoable, uncommitted" must ask `IsSnapshotFailure` **first**, the same ordering trap as the transaction sentinels above. Two packages describing *one* path are refused at the guard like any other pair, and retrying the loser afterwards reaches `ErrConflict` — it stages against what the winner committed, and the note now holds content its producer never saw. That is the same refusal a second delivery would have met with no race at all, which is the point: serializing the two changes *when* the conflict is found, never *whether*.
  - **An interruption converges on "never happened" or "happened completely", and the undo manifest is what decides which.** An import is six durable events — the peer's bytes, the provenance record, the manifest, the commit, the receipt, and the memory of all of it — and no two can be made one, so a process that dies in between leaves a vault that is perfectly consistent and completely unexplained. `apply` mints the recovery entry's identity and **declares the attempt before the first byte moves** — everything up to that point creates nothing, since `BeginOperation` only refuses and `plan` only describes — and `Recover` is the only reader of that record. The manifest is the discriminator because it is the moment the change stops being something the vault is *doing* and becomes something it *did*: it is what `bn undo` reads, what authorizes committing a deletion, and what the receipt promises the peer. Before it, roll **back** — acknowledging a change this vault could not undo is the one thing a peer must never be told. After it, roll **forward** — the provenance record is already durable and the change is already this vault's own history — and every forward step is idempotent by construction: `RecordImport` is a no-op for an entry it already holds, `ensureSnapshot` skips an entry the content history has, and an already-published receipt is **adopted** rather than re-minted. Three details carry the weight. `snapshotNeeded` asks the content history *before* committing rather than letting the engine work it out, because an entry that deleted a note carries the only authorization for that deletion, so re-committing one whose deletion already landed meets a path gone from the working tree *and* from HEAD — which `vaultgit` reads as an unexplained deletion and latches `blocked.json` over: recovering from an interruption must not be able to block the vault. That question is asked *again* where it is actually safe to answer — `vaultgit.CommitJournalEntry` plans no commit for an entry whose manifest HEAD already holds, checked **inside the safety lock** — because the autosave watcher can commit the same finalized entry between `snapshotNeeded`'s answer and the snapshot, and a check outside the lock is a race however carefully it is placed. `snapshotNeeded` stays as the cheap pre-check that avoids taking the lock at all. A rollback asks `journal.Started` — the entry *directory*, created by the first `Capture`, which `FileTxn` runs before it applies anything — rather than inferring from the paths, because comparing a path against what the package *said* it would find is only meaningful when the package was right about that, and a package that was wrong is precisely the one that got refused. A path that had already **converged** is named in `Attempt.Converged` and exempted, and that record is load-bearing rather than bookkeeping: the transaction never staged it, but a rollback deciding per path sees a path holding what the package installs and reads it as applied — so without the record it would restore content this import never wrote to a baseline nobody asked for. The whole package converging is the same fact one size larger: nothing was staged, so there is no recovery entry to name and therefore no honest receipt to mint, and `Record.Converged` says so instead of leaving an application unrecorded. The peer keeps its copy and redelivers, which is the protocol's safe direction — every redelivery converges again and changes nothing. And `settleTransactions` runs `vault.LockPaths(root)` with **zero** paths first, so `internal/vault` rolls any prepared transaction forward before anything here reads a path; planning a rollback against the earlier reading would put half the package back and leave the other half applied. One refusal keeps every version: a rollback that would cross a path holding neither what the package replaced nor what it installed. That is `ErrStrandedImport`; it keeps the attempt, the entry and its snapshots, and the content, and it **blocks every further import** so the evidence cannot be buried by the next package the transport delivers — a person with all three versions can choose, and a process that guessed would have destroyed one. Because the price of that refusal is the whole import path, **a recovery pass is itself a sequence of durable steps and records its own progress**: `rollBack` writes `Attempt.Restored` the moment the content is back, before it discards the journal entry and settles the attempt. A restored path reads exactly like one never written, so without that record an interruption between the restore and the tidy-up would leave a rollback that a later human edit turns into paths holding "neither" — stranding the vault permanently over work that had already finished correctly. The `crashRestored` kill point is where that is tested, by interrupting a recovery pass and then editing a note before the next one runs. The record covers every step *after* it, including `DiscardUnfinalized`, which is a recursive directory removal rather than one write; it does **not** cover the instant between the restore commit and itself, because a content transaction and a state file cannot be made one write and recording first would make a crash before the restore skip the restoration and destroy the snapshots that are the only copy of the pre-change bytes. That residual window is also why `OutcomeDiscarded` is documented as a statement about what a pass did rather than a promise that no destination was ever written: a rollback that finished and did not survive to say so is reported by the next pass as discarded. The forward direction has no counterpart: an acknowledgment that cannot be minted or published fails the *message*, not the vault, so the attempt is settled with no receipt and the peer simply keeps its copy (see `resolver.complete`).
  - **A redelivery is answered from the ledger, never applied again.** The transport moves whole directories and knows nothing about receipts, so a package reappears whenever a channel is re-copied, a peer is restored from a backup, or an acknowledgment goes missing. Applying it twice is not merely wasteful: the vault no longer holds what the package expected to find *because the package changed it*, so the second delivery would be reported as a conflict between the peer and its own change — a confusing and unresolvable answer to a delivery that is in fact already satisfied. `answer` reports what was applied as it was applied, and republishes the **original** receipt rather than minting a new one. That distinction is the point rather than an optimization: a receipt is a statement the producer may drop its only copy of a change on, so repeating one is honest where making a second — with a new timestamp, for an application that happened earlier, possibly since undone — would not be. A receipt is published under a name that can only be taken once, so republishing meets its own bytes and must read `ErrPackageExists` as **success**; that reading is local to this one caller, which knows the bytes in the channel are its own because they came out of the record that published them. The single exception is a package applied and never successfully acknowledged: there is no earlier statement for a new one to contradict, so `retryAcknowledge` mints one — held to every check a first acknowledgment is held to, including reading the entry back off the disk and hashing what the paths hold *now*.
  - **A conflict is decided before the transaction exists, named in the vocabulary of its remedy, and every version of it is kept** (`conflict.go`). `applier.inspect` reads every change against this disk *ahead of* `plan`, and the ordering is the whole of what it buys: a transaction reports the first precondition that failed and has nothing to say about the rest, so a conflict discovered there could hold one path of an operation that contests three — and it reports *that* a path disagreed, never *how*, which is the only thing a resolution can act on. Deciding first also means the contested content is never staged over, so the local branch is read at leisure rather than rescued out of a rollback. `internal/vault` still re-checks every expectation under the path's own lock and that is not redundancy: this reads without holding anything, so this decides *which* refusal and the transaction still decides whether a write may happen. `classify`'s six `ConflictKind`s are ordered by how much each explains — a **filename collision** first, because it is true whatever the expectation says (the package can be perfectly right about the path it named and still be about to create a second file that is one file on a folding replica) and a name occupied by something that is not a regular file comes with it, since the remedy is the same act of clearing the name; the **configuration** layers next, ahead of the content comparison that would otherwise swallow them, because declarations govern notes that are not in the package at all and "keep mine" is not a cheap choice there; then the three content answers, with `Tombstone()` and absence separating **delete-edit** from **edit-delete** and a plain **concurrent edit** last. The **identical outcome** is not a conflict at all — a path already at the result is `converged` — with one exception: the *source* of a rename is "already at the result" whenever the note is merely gone, which is equally what this vault moving it elsewhere looks like, so it is judged against its destination and disagreement there is a **divergent rename**. `renamePairs` recovers the pairing from the package rather than trusting a label, because a producer's claim is one a consumer could not check: a tombstone whose exact content is created at a free path *in the same operation* is the signature, and two notes that merely hold identical bytes cannot fake it. Retention is durable and content-addressed — `ConflictRecord` in `import.json` under `Conflicts`, the bytes under `.bnotes/sync/conflicts/<package>/<sha256>` through `vault.WriteStateFile`, so a rename's three branches cost one file and re-detecting an unchanged conflict rewrites the same names instead of growing the directory. A hold is deliberately **not** an `Attempt`: it has touched nothing, and recording it as pending would make every later import refuse, which is the opposite of the point. The **baseline** is best-effort and says so — the package carries it for a rename, `vaultgit.OpenHistory` holds it whenever the local divergence is an uncommitted edit (the common case, since a committed one would have been exported and the two would be arguing through predecessors instead), and anything older is recorded by digest with no bytes, which is the honest answer rather than a merge against the wrong base. Dropping a hold is two steps in a fixed order for the reason `RecordImport` is: `release` takes it out of the record and the record is saved, *then* `discard` removes the bytes — a crash in between leaves files nothing points at, which the next hold overwrites and `collectRetained` sweeps, where the other order would leave a durable invitation to resolve a conflict from versions that no longer exist. `applier.retain` is the other end of `inspect`'s race: an edit landing between the inspection and the staging check is refused by `FileTxn` with nothing written down, so the rollback runs and the disk is inspected a second time — and a second inspection that finds nothing is not an error, it means the edit was itself undone.
  - **`Drain` is the ordering layer, and ordering is a fact about the set** (`schedule.go`). Nothing about it can be said from `Apply`, which answers only about the package it is handed. The channel is sorted by origin device, then sequence, then package identity — never by anything the filesystem says, since a directory has no order, modification times are the transport's rather than the producer's, and `CreatedAt` is a clock on another machine the protocol already documents as unorderable; an unreadable package sorts **last**, or a directory still being copied in would decide where everything else went. Four reasons hold a package back, checked in order of how much each explains: `HoldUnreadable` (not a scheduling decision at all — usually `ErrIncompletePackage`), `HoldDependency` (a stated `Requires`, matched at the **exact** position rather than against a high-water mark, because a vault that has applied 1 and 3 cannot tell whether 2 was skipped or has not arrived), `HoldPredecessor` (a change naming a causal ancestor carried by another package **still in the channel** — the restriction is load-bearing, since a predecessor is just as often one of this vault's *own* operations that the peer imported, an identity no import record here will ever hold, and holding on every unknown one would deadlock the first package a peer ever sends back), and `HoldOrder` (a path an earlier unapplied package also changes, compared through `CollisionKey`, against a **strictly** earlier package so an overlapping pair cannot hold each other). A conflict holds its own operation and everything downstream of it and **nothing else** — stopping the whole drain at the first one would be simple, correct about content, and would let one contested note keep a hundred unrelated ones out of the vault for as long as nobody looked. The pass takes the import guard **once**: a loop around `Apply` would take and release it per package, and an ordering decided at the top of that loop would be made against a vault that has moved since. `passes` is a fixed point rather than one sweep, so a chain arrives in one drain instead of one drain per link, and it stops when a pass applies nothing — the only termination condition independent of the graph's shape, so a cycle no honest producer can emit stalls rather than spins. `sweep` runs first and answers two different failures: a hold whose package left the channel describes a conflict nobody can act on, and a retained directory no hold names is what a process that died mid-`discard` leaves. `Drain` returns an **error** only for conditions about the *vault* — `ErrImportBusy`, `ErrStrandedImport`, an unreadable or foreign record — because everything a package can be wrong about leaves the others worth applying; a package whose content landed and whose bookkeeping did not is `Applied`, with the failure carried out on `Drained.Unfinished`, not a hold. Those four are the reasons `hold` decides *before* attempting; three more are verdicts on what came back, and the distinction every one of them draws is **what to do about it**: `HoldConflict` (a person resolves it), `HoldRejected` (a refusal no wait fixes — an unknown format token, a manifest that contradicts itself, a path that is not portable vault content, more than one operation, the wrong vault, an unenrolled origin, a stale or ahead epoch), and `HoldFailed` (everything else, which is a retry). **A reason is not a place**: `rejected` is asked of the scan's failure *and* of the application's, because the same distinction lands in either depending on whether it is a fact about the manifest — which `ReadManifest` checks, so an unknown format never reaches the application at all — or about the enrollment, which only `Accept` checks. `ErrIncompletePackage` is the one refusal that is a wait, and it too arrives from both: the scan reads only the manifest, so a package whose payloads are still copying in looks whole to the scheduler and is caught late. Both report `HoldUnreadable`. **A `Result` outranks the error it came with**: the `result != nil` arm is checked before any classification, because a failure to acknowledge can carry a sentinel that also means "refused" — a receipt written by a newer build in this vault's *own* outgoing channel raises `ErrUnsupportedFormat` after the content is durable — and reporting a committed package as one this vault will never accept would drop both the `Result` and the failure out of the report. A verdict is cleared at the top of every pass and re-decided, so the partial report a mid-pass refusal returns carries no stale wait; the packages that pass never reached report `HoldNotAttempted` rather than a blank reason, which is the difference between "the drain stopped before its turn" and "its explanation went missing". `Held.Conflict` is nil-checked even under `HoldConflict`: a precondition the transaction refused and a second inspection cannot reproduce — the concurrent editor put the note back — is a real refusal with no record, and `retain` writes none rather than inventing one. `Drained.Unfinished` carries what happened after the content landed, and reads `Result.Receipt` rather than the error to say which step it was: a `Result` carries a receipt exactly when this vault has an acknowledgment for the package — minted now, or minted before and being republished, including when publishing it just failed — so a nil one means the peer was never told and a non-nil one means it was and something after that did not finish.
- `internal/vaultsyncd` — the **companion**, and the **status model**. It is the one thing in the repository that runs a synchronization on a schedule with nobody typing a command, and the one thing that can be asked where anything has got to. Everything the work itself needs already existed — `vaultgit` records the content history, `vaultexport` turns commits into packages, `vaultimport` applies the peer's, `vaultsync` owns the wire protocol and the channel layout — so this package owns no protocol, no format another package reads, and no write to a note. Three doors: `Run(ctx, root, Options)` is the loop, `Once(ctx, root, Options)` is a single bounded pass, and `Read(ctx, root, ReadOptions)` is the whole observable surface. It sits above all four of those packages and nothing imports it but `cmd/bn-vault-sync` — the **second private companion**, beside `cmd/bn-vault-guard`, and a separate process rather than another loop inside that one because the guard protects a vault whether or not it synchronizes, and a vault that synchronizes still needs its content history protected on a machine where this is not installed. That command is the three modes and nothing else: no flag is the installed loop (a JSON `slog` record per event), `-once` runs one pass and prints it, and `-check` prints the status and exits **0 / 1 / 2** — will make progress on its own, needs a person, could not be read at all. The last two are separate because a vault waiting on a conflict is not broken and a vault nobody can read is not healthy, and a health script switches on the difference. There is no configuration: the interval, the backoff bounds and the disconnection threshold are constants here, because each is a statement about how much divergence between two replicas is acceptable rather than a preference.
  - **Three units, one goroutine, in one order — import, then export, then retire.** This is a lock-ordering decision and it is the invariant most worth protecting in the package. `vaultimport` holds its own import guard for a whole drain, and an application inside that drain calls `vaultexport.RecordImport`, which takes the export state lock; `vaultexport` holds that same lock for a whole pass. A drain and an export running concurrently would therefore approach one lock from opposite directions, and the loser does not merely wait — `internal/vault`'s path locks have a bounded acquisition budget, so it *fails*, and a drain that fails at `RecordImport` fails after the peer's change is already committed. Serializing the units in one goroutine means this process never holds two subsystem locks at once, which is the rule `internal/vault`'s `lock.go` already states for path sets. **Import precedes export** because a commit an application produced is already in the export ledger when the exporter reaches it, so the pass that imports a change cannot publish it straight back. **Retire runs last and takes no subsystem lock at all**, which is what keeps the invariant trivially true for it: the exporter creates package directories under fresh identities and never enumerates the channel, so there is no listing a removal could invalidate, and every removal is of something a verified receipt already made redundant (`os.RemoveAll` reports an already-gone path as success, so a concurrent remover is tolerated). Its one write is `discard`, which runs `vault.GuardMutation` first and carries the `//bn:direct-write` marker naming it — `internal/audit` has no exemption for this package.
  - **A pass knows what an earlier unit in it did** (`passState`). The status is read **once**, before the first unit, so a decision made from it is stale for every unit after the first — and the one that matters is the export's: an application commits, and an export skipped on a nothing-to-publish reading would leave that commit sitting until the next tick. A **resolution revision** — the commit that tells the peer which version won — is exactly the change nobody wants held, so `passState.imported` forces the export to run. The status carried on the `Pass` is read **after** the work for the mirror-image reason: a report and the vault it describes must not disagree about what the pass just did.
  - **Delivery is never reported as application.** A package this device published and the transport copied has been *delivered* at most; only a receipt says the peer applied it durably against a named local recovery entry, which is what `vaultsync` documents a receipt to mean. `StateTransportPending` therefore covers everything from "not copied yet" to "copied and being applied right now", and nothing but a verified receipt retires a package. The same distinction holds inbound: `StatePeerApplication` counts packages sitting in this vault's incoming channel, which are **not** changes this vault holds. Ten states in all — unenrolled, idle, local-saved, export-pending, transport-pending, peer-application, conflict, blocked, disconnected, failing — reported as a **set** with a `Headline()` ordered by which one a person would act on first (blocked, conflict, failing, disconnected before the ordinary progress states), and `NeedsPerson()` is the same judgement as one boolean, which is what `-check`'s exit 1 is.
  - **Retirement is sender-owned, and a receipt is released by the package's disappearance.** A device publishes receipts into its **own** outgoing channel, so each side removes only artifacts it put there — nothing here deletes from an incoming channel, because a transport that mirrors directories would turn that local deletion into a remote one. A receipt is dropped once the package it acknowledges has left the incoming channel, which is the sender's retirement observed from this side; an **unreadable** incoming channel stops the release rather than making it guess, since every package would look gone and every receipt would be released at once.
  - **Disconnection is the one state this package infers rather than observes**, and it says so. The transport is a separate program that must never touch a live vault, so what is visible from here is staleness: a package awaiting a receipt for longer than `DefaultDisconnectedAfter` with nothing having arrived in the meantime. Anything arriving from the peer clears it, even a delivery that acknowledges nothing — the inference is about the transport, not about the package.
  - **Nothing here hides a failure, and a skip is not one.** Each worker's last failure, its failure streak, and the backoff that streak implies are durable in `companion.json` beside the export cursor, and `Read` reports them, so a vault whose exports have been failing for an hour says so rather than looking idle. The backoff doubles from `MinBackoff` to a `MaxBackoff` ceiling and is a **delay rather than a latch**: the moment it elapses the worker runs again. A **skip** never *lengthens* the streak — an unenrolled vault, one with no content history or no commits, one being drained by a `bn sync` the operator is running by hand, and a blocked content history are all conditions to look at again next tick, and recording them as failures would put an idle vault into an ever-lengthening backoff and bury the one error that matters under a streak of ones that do not. A skip that **proves there was nothing to do** goes further and *clears* it, because the streak is otherwise only ever cleared by a success, and a worker that failed and then stopped being asked would carry `StateFailing` — and `-check`'s exit 1 — forever on the evidence of a failure nothing is retrying. That reading arrives by two doors, and they are the same fact: the skip decided before the worker runs, and the worker's own refusal as unenrolled, unmanaged, or unborn. `ErrImportBusy` is deliberately neither — a vault somebody else is draining is a worker that never got as far as looking, and clearing on it would drop the backoff too, so an import that fails and then meets a busy vault every pass would retry at the tick interval forever. The producer halts that would otherwise be hidden by that clearing are named directly instead: a cursor from an earlier enrollment epoch, one following another branch, and one the branch was reset *behind* are each a `Problem` on the status. All three leave nothing to measure — the epoch case most of all, because `vaultexport` resolves an interrupted publication *before* it checks the epoch and resolving one advances the cursor durably — so the halted vault reads as having nothing left to publish. Naming them is what makes them act: a status carrying a problem runs the export anyway, so the refusal becomes a recorded worker failure with its evidence instead of a silence. The backwards reset is inferred rather than asked for, from the count the cursor reading already takes: an empty `cursor..tip` whose ends differ is exactly the tip being behind the cursor, which is `vaultexport`'s `ErrHistoryRewritten`; a history rewritten the other way leaves that range non-empty and was already loud. The import worker is the one that skips on `Local.Blocked`, because every application it attempted would be refused identically; the export still runs there, since it reads committed objects and writes only under `.bnotes/sync/`, so a vault blocked today can still ship what it committed yesterday. A status that could not *determine* something also runs the export rather than skipping it: an unreadable export record reads here as "no pending commits", and skipping on it would turn a broken producer into a vault that looks permanently up to date.
  - **A restart costs one early retry and never a change.** Progress is durable in the packages this one does not own — the export cursor, the import ledger, the conflict records, and the published packages and receipts themselves — and `companion.json` carries *only* scheduling state. That is why an unreadable record is **discarded and started again** rather than refused, announced as a problem and no more, and why a record that cannot be *written* is announced rather than fatal: stopping a whole vault's synchronization over a scheduling detail is the worse trade. Shutdown is graceful in the only sense this loop needs — the unit in flight finishes and the loop stops **between** units — because every unit is one call into a package that is already crash-consistent, so a companion killed outright loses no more than one asked politely.
  - **One companion per vault, refused rather than queued.** `LockPath` is `.bnotes/locks/vault-sync.lock`, beside the per-note locks the vault's own ignore rules already exclude, so the coordination file can never become a pending change the content history would commit or a file the exporter would send. It is taken with `vault.TryLockPath`, never `vault.LockPaths`, for `vaultimport`'s reason — `LockPaths` escalates to the exclusive vault guard and the transaction this companion is about to drive escalates to the same guard from inside. Wait-free is also what a second instance wants: `Once` returns `ErrAlreadyRunning` with **no** `Pass` rather than queueing behind a process that intends to run forever.
  - **`Read` takes no lock of any kind.** It opens the content history through `vaultgit.OpenHistory`, reads the durable records with the read-only loaders their own packages expose, and lists the two channels and the receipts in them. A status command is most needed while a drain is running, so anything here that needed a lock would be answerable exactly when nobody is asking. A fact it cannot determine becomes a `Problem` on the status rather than an error off the door, for the same reason: a partial answer about a vault is worth more than no answer.
  - **A converged package is applied, never acknowledged, and therefore never retired** — a known gap this package can report but not fix. `vaultimport` mints no receipt for a package whose every path this vault already held, because an acknowledgment promises a local recovery entry that can undo the application and an application that wrote nothing produced none; it records the package as applied-and-converged and expects the sender to keep its copy and redeliver. The consequence here is that such a package stays in the sender's outgoing channel forever, counted in `TransportStatus.AwaitingReceipt`, and a pair quiet for long enough afterwards reaches `StateDisconnected` on a transport that is working. The status is not wrong about the facts it states — no receipt has arrived and nothing has been heard — but the headline names the wrong cause. Fixing it needs the protocol to carry a "this changed nothing" acknowledgment, which is `internal/vaultsync`'s decision; it is stated in `doc.go` and pinned by a test rather than left to be discovered.
- `internal/audit` — no production code; it holds the source-level invariant no runtime test can hold. `TestNoUnannotatedDirectWrites` parses every production `.go` file in the repository and fails when one calls an `os`/`ioutil` write function outside the approved persistence packages without saying why. The escape hatch is the annotation `//bn:direct-write <reason>`, placed either on the line immediately above the call or in the doc comment of the enclosing function, whose reason must answer the only question worth asking — *what already guaranteed this write is allowed to happen?* ("guarded by `BeginOperation` above", "inside a `FileTxn` that holds the lock"), not what the call does. Because `gofmt` treats a `//bn:` comment as a **directive**, the marker must be a single line pinned to the end of its comment group, with any prose above it. `approvedPackages` — `vault` (location policy and replacement primitives), `vaultgit` (content history), `vaultstate` (durable sidecar state), `journal` (undo manifests), `index` (a regenerable cache), `backup` (archive extraction) — carry the guarantee themselves and need no annotation; adding to that list is a decision about *where safety lives*, so it is made by editing the map with a reason, never by annotating call sites one at a time. Test files are exempt entirely: a fixture writes to a temp directory that is not a vault and has nothing to protect.
- `internal/vaultfixture` — verification infrastructure, and the only package here whose files are ordinary `.go` yet are imported by nothing but tests. It exists because the rule it enforces had been written twice and was about to be written a third time. `isolation.go` states the refusals once — a path naming a real vault at any depth, a vault or an asserted sandbox outside the system temporary directory, a resolved vault outside the sandbox the caller asserted — as `IsolationError(resolved, sandbox)`, which **fails closed on every input it cannot prove safe**: an unasserted sandbox and an unresolved vault are both refusals, because "no evidence of isolation" is exactly what the 214-note incident looked like from inside the process. `AmbientVaultRoot` deliberately reads process state rather than calling `config.Load`, because `Load` also *decodes* the file and a guard that decoded would mistake an intentionally malformed fixture config for an isolation failure; `TestAmbientEnvIsWhatBnResolves` pins the two resolutions together so they cannot drift. `NormalizePath` resolves the longest **existing** ancestor and re-attaches the rest, which is what lets `newVault` reach a verdict *before* `os.MkdirAll` — the same refusal-before-artifact ordering `noteops.BeginOperation` encodes, held for the same reason, and not a detail: macOS reaches the temp tree through `/var` → `/private/var`, so a lexical fallback would compare an unresolved candidate against a resolved root and refuse every legitimate not-yet-created sandbox. `vault.go` builds disposable Git-backed vaults and `Pair`s of them (two enrolled replicas of one vault, separate roots and separate object databases), always carrying an `Unrelated.md` sentinel no operation names, so a commit or a package containing it swept in a change nobody asked to record; commits are dated from `Epoch`, one second apart, because a commit hash covers its timestamp and a wall-clock fixture makes two identically-seeded vaults hash the same or differently depending on whether the pair straddled a second boundary. Its writes carry `//bn:direct-write` markers naming the containment check that precedes them, and it is **not** in `internal/audit`'s `approvedPackages`: a fixture package owns no safety property the rest of the system borrows. `clock.go` and `port.go` supply the other two isolations a verification needs — a `Clock` whose `Now` matches the repo-wide `func() time.Time` seam (`journal.WithClock`, `index.WithClock`, `vaultgit.Options.Now`) and moves only when a test advances it, and loopback-only listeners that refuse a wildcard bind. The manual half of the same rule stays `scripts/vault_sandbox.py`, and the browser suite under `internal/web/e2e` launches its server *through that script* rather than through a JavaScript port of these refusals — and `internal/synctransport` refuses every path it hands to Syncthing through `IsolationError` rather than restating the refusals — four callers, one statement of the rule. **What has a caller and what does not, stated plainly so nobody has to grep for it:** `IsolationError` and the environment scrubs are consumed today by `internal/cli/vault_isolation_test.go`; `Pair` and `Clock` are consumed by `internal/vaultsync`'s tests — the two-vault synchronization work they were built for, which arrived and used them unchanged — and by this package's own tests; the `ReserveLoopbackAddr` is consumed by `internal/synctransport`, the case it was written for and named in its own doc comment — a server started as a child process, which has to be told an address before it can bind one. Building the isolation and the fixtures together is what let the refusals be stated once instead of accreting a third copy inside that work. Treat an unused helper here as an interface to use, not as dead code to delete; if the synchronization work needs a shape this does not have, change it here rather than growing a local variant.
- `internal/syncthingbin` and `internal/synctransport` — the second pair of packages here with no production caller, and the answer to the one thing `internal/vaultsyncd`'s tests structurally cannot ask. That package's transport fixture is a function call: it copies a directory, mirrors removals, and returns. It is honest about what it is and it cannot be wrong about timing, because it has none — which also makes it the one place this design could be wrong without any test noticing, since every claim the architecture makes about the transport is a claim about a program this repository does not write. So `synctransport` starts two real Syncthing processes over a `vaultfixture.Pair` and the tests assert on **vault contents**, the only evidence that survives being wrong about Syncthing. `syncthingbin` is why that is reproducible: one pinned release (`v1.30.0`), fetched from the published archive and refused unless it matches a SHA-256 recorded in the package, because the protocol, the configuration schema (**version 37**) and the REST surface this repository writes against all move between releases — a harness that picked up whatever was on `PATH` would pass or fail for reasons nobody could reconstruct. `go install` is not an option: Syncthing's module carries replace directives and the command refuses outright. The recorded checksums are of *archives*, so a cache hit cannot be compared against them: the installer writes the digest of the bytes it extracted beside the binary and a later run re-hashes the file, reinstalling rather than running anything it cannot account for — and the cache directory is read at package initialization, before `vaultfixture.Isolate` rewrites `HOME`, so resolving from inside a test still caches outside the fixture. The configuration is rendered whole rather than patched over `syncthing generate`'s defaults, so every element present is present deliberately; discovery, relays, NAT traversal, auto-upgrade, usage reporting and crash reporting are each a way a test process could reach something that is not the other half of the fixture, and each is off — and each is **read back out of the running process** (`Containment`, compared as raw JSON so a renamed key is a failure rather than a zero value), as is the schema version, because a release that does not know the schema migrates the file on startup and keeps the folders, which would leave every other assertion here passing against a configuration this repository did not write. Identities are generated per fixture, addresses are reserved loopback ports (`vaultfixture.ReserveLoopbackAddr`, whose documented reason is exactly this), and administration is a loopback GUI with a per-instance key. **The folder set is the architecture, stated to a program that will act on it**: one send-only folder per device over its own `.bnotes/sync/outgoing`, arriving at the peer as a receive-only `.bnotes/sync/incoming`, two in total, and no vault directory anywhere — `IsolationError` refuses every path before it is created rather than a local copy of the rule, and the assertion is read back out of the running processes because a configuration Syncthing migrated or ignored would still look correct on disk. The directionality is load-bearing rather than tidy: a receive-only folder that loses a file locally records a local deviation and keeps being offered the bytes, which is precisely the semantics `vaultsyncd`'s retirement worker depends on and the reason a receiver cannot retire anything by deleting its own copy. The scenarios sit in `internal/vaultsyncd` behind a `synctransport` build tag, sharing that package's `world` so the *only* difference from `roundtrip_test.go` is the transport, and they cover what an in-process copy cannot: a package delivered before its predecessor, a link that is down when one is published (asserted down *while* the package fails to arrive, or the scenario would be describing nothing), a device that goes away and comes back on the same database, a package whose manifest never arrived, one whose payloads were altered underneath an intact manifest, and a deletion made by the wrong device. A refusal is asserted by running the vault's own pass repeatedly across a window of two folder rescans rather than by watching the filesystem while nothing runs — the second proves only that a program nobody started did nothing. They run from `just test-sync-transport` and are not in `just ci`, on the same terms as `just test-e2e` and stated in the recipe: they wait on two other processes and need a downloaded binary, and a gate that skips when its subject is absent is not a gate. The tag is on the test files only, so the harness itself is covered by gofmt, `go vet` and the ratchet on every ordinary run.
- `internal/mutationmatrix` — also no production code (only a `doc.go`, so `internal/audit` has nothing to flag). It exists because write safety is a property of the whole system rather than of any one package: `vault` refuses a forbidden location, `vaultgit` records exactly the paths a change touched, `noteops` is the seam that makes a caller go through both, each is thoroughly tested alone, and none of them can answer the question that matters to a person with a vault — *does the command I just ran get the guarantees, end to end, through the layer I reached it by?* One table answers it uniformly for every writer. Each row names a real production entry point — a CLI command driven through the Cobra tree by argv (`NewRootCmd` plus `--vault`, so `PersistentPreRunE` loads the fixture's own `brainnotes.toml` and nothing is stubbed), an HTTP route served by `internal/web`, a `noteops` mutation, a restore, a durable state write — and the same assertions run against all of them: a refused location fails before any artifact exists; an allowed one mutates; an operation with nothing to do leaves no empty commit; a success adds **exactly one** local commit holding only the operation's paths plus the journal entry authorizing them; an unrelated edit sitting in the working tree is not swept into it; and a failed snapshot leaves the change on disk, says so, and refuses the next mutation. The snapshot failure is provoked through the production resolution path rather than around it — every layer resolves its engine via `vaultgit.Shared(ctx, root, Options{})` with zero options, so `Options.GitExecutable` is unreachable and a `git` shim on `PATH` armed by a sentinel file is the only seam, which is precisely what makes the test evidence about production wiring. A row that reaches its operation over HTTP asserts the wire contract only (status, stable code, message), because a Go error type cannot survive that trip. Backup restore gets its own test instead of a row: it is wholesale, so the unrelated-edit assertion is not merely false there but meaningless. **The uniformity is the value** — a new mutating command is one row away from being covered, and a row that cannot be written is the signal that the command bypassed the seam, which is the same finding `internal/audit` reaches from the source side.
