# internal/vaultgit

[Back to the architecture map](../architecture.md).

- `internal/vaultgit` — the internal Git safety engine: it snapshots the vault into a local Git history after every change so that every version of every note stays recoverable, and pushes that history to a private remote. It exists for the same incident `docs/internals/locking.md` opens with — a note lost when a write vacated its destination and synchronizing storage propagated the vacancy back as a deletion — and it is the layer *below* that refusal, the one that survives whatever a write, a filesystem, or an external tool does that nobody anticipated. It is **not a Git porcelain and has no user-facing surface**: nothing in it reads or writes a note, it stages exact paths, builds a tree, writes a commit, and moves one ref. `Open(ctx, vaultRoot, Options)` returns `ErrUnmanaged` for a vault that is not the top level of its own repository — a vault with no `.git`, a `.git` *file* (a worktree or submodule), or a vault nested inside a larger repository, all of which the engine leaves entirely alone rather than half-managing. Everything else is a typed `*SafetyError` carrying a `Kind`, the operation, the paths, and object names but **never note contents**, and `Kind.blocking()` is the single place that decides which failures latch. Six invariants govern it and `doc.go` states them in full:
  1. **External deletions are ordinary recoverable changes.** Missing tracked regular files are recorded on the external autosave schedule. Earlier Git commits retain their bytes; journaled operations additionally preserve unsnapshotted pre-mutation content for undo. No journal proof is needed to remove a file in an editor or on another device. Classification still refuses ambiguous type changes and unmerged entries. External renames are represented as an addition and a deletion (`--no-renames` against a HEAD-seeded private index).
  2. **A local safety failure is durable and fails closed.** A classification ambiguity, a ref compare-and-swap that cannot be retried safely, or a failed local commit writes `blocked.json` and `Preflight` refuses every later mutation until `ClearBlock` (or a person) removes it. **The marker is an optimization for reporting, never the mechanism**: if writing it fails, the condition is still on disk and the next preflight re-derives the same verdict from the working tree. A marker that is corrupt, truncated, or carries an unknown version keeps refusing rather than silently re-enabling mutations — the deliberate inverse of `internal/index`'s self-healing, and the same fail-closed posture as `internal/recall`'s state store, for the same reason: this file records something that cannot be re-derived cheaply and must not be discarded on doubt. Valid legacy `unexplained_deletion` markers are migrated automatically under the safety lock after repository and interrupted-operation checks pass.
  3. **Remote availability is not a correctness input.** A push failure is retried with backoff (30s doubling to a 5min cap) and recorded in `push.json`; it never writes `blocked.json` and never prevents a local commit, because a vault that stops accepting edits when the remote is down is a worse vault. Conversely `Push` is never called from the immediate mutation path — a note save must not wait on a network round trip. `push` is run with `--porcelain --atomic` and **never** `--force`.
  4. **The user's index is theirs.** Every operation stages into a private `GIT_INDEX_FILE` seeded from HEAD and deleted afterwards, so a snapshot can never absorb what the user had staged and a `git add` they ran by hand is never committed by us. The seeded index also has no stat cache, which is what makes classification a full content comparison and therefore deterministic. After a successful commit the real index is refreshed for the exact committed paths and only where its entry still matched the *old* HEAD; that refresh is cosmetic (it keeps `git status` from showing our own commit as a staged revert) and its failure is never an operation failure.
  5. **No note *content* reaches a command line, a commit message, or a log, and a note *path* reaches one only where it cannot be read as syntax.** Git is invoked as an argv array with a controlled environment and never through a shell — the same argv-only posture as `internal/agent`. `stageAdd`/`stageRemove` hand `update-index` their paths NUL-delimited on stdin, so a leading dash, a newline, or a comma in a note name is data rather than syntax there. Four call sites do put a path on argv, and each disarms it differently rather than by exclusion: `ls-tree` and `ls-files` take pathspecs after `--` under `GIT_LITERAL_PATHSPECS`, `hash-object` takes a file operand after `--`, and `setIndexEntry` uses `update-index --cacheinfo`'s three-argument form, whose operands are consumed positionally — the newer `<mode>,<oid>,<path>` form splits on commas and would silently record a truncated path for a note whose name contains one. Local plumbing runs hermetically (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_LITERAL_PATHSPECS`, `LC_ALL=C`, `TZ=UTC`) because a global `core.excludesFile` would change what `status` reports; a push deliberately keeps the user's global config and `SSH_AUTH_SOCK`, since that is where an SSH command or a URL rewrite lives. Commit messages are the fixed shapes `brainnotes: <operation> [<journal-id>]` and `brainnotes: autosave <RFC3339 UTC>`, with the operation reduced to a bounded `[a-z0-9-]` token rather than escaped. In particular **`journal.Entry.Command` holds the full `bn` invocation, including note names and property values, and must never be used to build a message.**
  6. **An interrupted snapshot is distinguishable from one that never started.** Invariant 2 covers failures the engine *observed*; a process that is killed observes nothing and writes nothing, and what it leaves behind would otherwise look like a healthy vault. So every snapshot writes and fsyncs `intent.json` (`intent.go`, `state.go`) before its first index write, rewrites it with the new commit's object name **before** `update-ref` is attempted, and removes it only after the ref has moved and the directory naming it is durable — which is also why `writeAtomic` now fsyncs the state directory after every rename, so a marker or a record cannot vanish in a crash and be read as "nothing was wrong". The record carries the operation, an operation ID, the phase, the observation time, the ref, old/new object identifiers, and the paths (capped at 256 with an untruncated `path_count`), plus manual recovery steps — **never note contents**. A record found at startup means an operation began and never finished, and mutations stay refused until recovery proves the recorded commit is *reachable* from the branch (`git merge-base --is-ancestor`; reachability rather than equality, so another writer committing on top does not un-land the snapshot underneath) or a person clears it — `ClearBlock` clears the marker and the record together, because that is one act. An unreadable or unknown-version record refuses rather than self-heals, and for a sharper reason than the marker's: proving a snapshot landed *requires* the object name those bytes were supposed to hold. This is what covers the one case invariant 2 cannot: a local commit failure whose `blocked.json` write **also** fails leaves the record standing, and the vault stays refused across a restart on a spotless working tree. Conversely, a failure to *create* the record prevents the snapshot attempt entirely and is deliberately **not** a block — nothing was written, so the next mutation may retry. `Open` reads the record (one failed file open on a healthy vault) and takes `safety.lock` only to adjudicate one it finds; a busy lock means the record belongs to a live operation, so it is left alone.

  `InScope` (`scope.go`) is a fixed in-code policy, not a read of `.gitignore`, deciding which vault-relative paths BrainNotes may *add*: Markdown, attachments, `brainnotes.toml`, `.bnotes/journal/**`, and the `brief`/`cockpit`/`recall` sidecars, excluding `backups/`, `.codegraph/`, `.vault-cache/`, `.bnotes/index/**`, `.bnotes/locks/**`, and the `.note-*.tmp`/`.txn-*.tmp` scratch names `internal/vault` stages through. Anything already tracked in HEAD is in scope regardless of the policy, in both directions: a tracked file whose modification we skipped would drift out of the history silently, and a tracked file whose deletion we skipped would leave an deletion pending forever. Two staging guarantees are subtle enough to be tested by name. An unreadable note is a reported `SkippedPath` rather than a block **only on the external-change scan** (`CommitPending`), which offers to record whatever the working tree happens to hold, so leaving one path out costs the history nothing it held a moment ago; every other entry point is a caller naming exact paths, and there an unstaged required path is a `KindCommitFailed` block rather than a success that quietly omits it, with `CommitResult.Unrecorded()` letting the caller confirm that for itself. A path the engine can read that Git still refuses to stage is neither case — it is the repository failing, it would hit the rest of the pass too, and it is fatal everywhere including the external scan, which is what keeps an unwritable index from looking like an empty vault. Skipping is otherwise purely additive — but a skip in a pass that also holds removals **defers every removal in that pass and its associated journal entries**, preserving potential rename sources and keeping the undo record with its removal. And a ref that moves between planning and landing is retried, never forced: the commit is landed with `update-ref <ref> <new> <old>`, and a failure is re-read to distinguish a genuine compare-and-swap loss (retry, up to 3 attempts) from a ref that did not move (a real commit failure, which latches). Operational state lives under `<git-dir>/brainnotes-safety/` — inside `.git`, so it is never tracked and never walked by `vault.Walk` — and the locking contract is in `docs/internals/locking.md`.

  `OpenHistory(ctx, vaultRoot, HistoryOptions)` (`history.go`) is the package's **read-only second door**, added for `internal/vaultexport` and deliberately not a `Manager`. Opening a `Manager` is a *writing* act: it takes the vault lock, recovers an interrupted intent, and publishes the autosave policy into `watch.json`, which is the record that decides when the next external-edit autosave is due. A reader that acquired one would be an observation with the power to disturb what it observes — asking what there is to export would move somebody's next save. A `History` takes no lock, writes nothing, and never reads the working tree: `Tip`, `Contains`, `CommitsAfter`, `Inspect`, `Changes`, `Tree`, `Blobs`, `BlobDigest`, and `EntryKinds` all read committed objects, so an uncommitted edit is invisible **by construction** rather than by a filter a caller has to remember. `HistoryOptions` is not `Options` for the same reason: an author identity, a remote, and an autosave policy are all inputs to writing, and accepting them would invite a caller to believe they meant something. The two doors share `openWorkingTree` and `resolveGitDir` so they cannot disagree about what a managed vault is, and both refuse a detached HEAD — a reader has no stable thing to record a cursor against. Three details are load-bearing and tested by name: `CommitsAfter` is **oldest-first and unbounded**, because `rev-list -n` selects *before* `--reverse` reverses and a bounded query would hand back the newest few in oldest-first order, which reads as correct and replays a history backwards from the middle; rename detection is **off** in `Changes`, so each side of a rename carries its own prior-content expectation; and every object name a caller supplies goes through `checkObjectNames` first, so a corrupt cursor read back off a disk fails as a corrupt cursor rather than reaching `rev-list` as `--all` or as a range of its own devising. `ErrUnbornBranch` keeps "this vault has no history yet" — an ordinary state, meaning there is nothing to export — apart from "this repository is broken".
