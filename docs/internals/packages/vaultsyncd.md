# internal/vaultsyncd

[Back to the architecture map](../architecture.md).

- `internal/vaultsyncd` — the **companion**, and the **status model**. It is the one thing in the repository that runs a synchronization on a schedule with nobody typing a command, and the one thing that can be asked where anything has got to. Everything the work itself needs already existed — `vaultgit` records the content history, `vaultexport` turns commits into packages, `vaultimport` applies the peer's, `vaultsync` owns the wire protocol and the channel layout — so this package owns no protocol, no format another package reads, and no write to a note. Three doors: `Run(ctx, root, Options)` is the loop, `Once(ctx, root, Options)` is a single bounded pass, and `Read(ctx, root, ReadOptions)` is the whole observable surface. It sits above all four of those packages and nothing imports it but `cmd/bn-vault-sync` — the **second private companion**, beside `cmd/bn-vault-guard`, and a separate process rather than another loop inside that one because the guard protects a vault whether or not it synchronizes, and a vault that synchronizes still needs its content history protected on a machine where this is not installed. That command is the three modes and nothing else: no flag is the installed loop (a JSON `slog` record per event), `-once` runs one pass and prints it, and `-check` prints the status and exits **0 / 1 / 2** — will make progress on its own, needs a person, could not be read at all. The last two are separate because a vault waiting on a conflict is not broken and a vault nobody can read is not healthy, and a health script switches on the difference. There is no configuration: the interval, the backoff bounds and the disconnection threshold are constants here, because each is a statement about how much divergence between two replicas is acceptable rather than a preference.
  - **Three units, one goroutine, in one order — import, then export, then retire.** This is a lock-ordering decision and it is the invariant most worth protecting in the package. `vaultimport` holds its own import guard for a whole drain, and an application inside that drain calls `vaultexport.RecordImport`, which takes the export state lock for one write; `vaultexport` holds its producer guard (`export.lock`) for a whole pass and that state lock only around each write, so neither unit holds a lock the other needs for longer than one write. `RecordImport` also runs before the application touches the vault, so a lock that stayed busy refuses the import instead of committing it unrecognized. Serializing the units in one goroutine still means this process never holds two subsystem guards at once, which is the rule `internal/vault`'s `lock.go` already states for path sets. **Import precedes export** because a commit an application produced is already in the export ledger when the exporter reaches it, so the pass that imports a change cannot publish it straight back. **Retire runs last and joins the outer checkpoint barrier but takes no subsystem lock**, so a private snapshot cannot race a package removal. A verified peer receipt is necessary and no longer sufficient: `.bnotes/sync/backup-coverage.json` must name the exact immutable manifest digest from a successfully verified private backup, and no package still published in this channel may depend on that package's origin position. The dependency set is calculated from the sweep's initial package set, deliberately making a chain take another sweep instead of deleting its recovery evidence from underneath the scan. `discard` runs `vault.GuardMutation` first and carries the `//bn:direct-write` marker naming it — `internal/audit` has no exemption for this package.
  - **A pass knows what an earlier unit in it did** (`passState`). The status is read **once**, before the first unit, so a decision made from it is stale for every unit after the first — and the one that matters is the export's: an application commits, and an export skipped on a nothing-to-publish reading would leave that commit sitting until the next tick. A **resolution revision** — the commit that tells the peer which version won — is exactly the change nobody wants held, so `passState.imported` forces the export to run. The status carried on the `Pass` is read **after** the work for the mirror-image reason: a report and the vault it describes must not disagree about what the pass just did.
  - **Delivery is never reported as application.** A package this device published and the transport copied has been *delivered* at most; only a receipt says the peer durably holds every package result — against a named local recovery entry when it wrote content, or as explicit convergence when it wrote nothing, which is what `vaultsync` documents a receipt to mean. `StateTransportPending` therefore covers everything from "not copied yet" to "copied and being applied right now", and nothing but a verified receipt retires a package. The same distinction holds inbound: `StatePeerApplication` counts packages sitting in this vault's incoming channel, which are **not** changes this vault holds. Ten states in all — unenrolled, idle, local-saved, export-pending, transport-pending, peer-application, conflict, blocked, disconnected, failing — reported as a **set** with a `Headline()` ordered by which one a person would act on first (blocked, conflict, failing, disconnected before the ordinary progress states), and `NeedsPerson()` is the same judgement as one boolean, which is what `-check`'s exit 1 is.
  - **Retirement is sender-owned, and a receipt is released by the package's disappearance.** A device publishes receipts into its **own** outgoing channel, so each side removes only artifacts it put there — nothing here deletes from an incoming channel, because a transport that mirrors directories would turn that local deletion into a remote one. A receipt is dropped once the package it acknowledges has left the incoming channel, which is the sender's retirement observed from this side; an **unreadable** incoming channel stops the release rather than making it guess, since every package would look gone and every receipt would be released at once. The sender also advances one mutable `retirement.json` record after package removal. Its sequence high-water mark plus the exact still-published exceptions are bounded by outstanding work rather than vault lifetime. `vaultimport` prunes an applied-package record only when this sender-owned evidence excludes it **and** its directory has left the incoming channel: the evidence prevents a local receive-only deviation from erasing redelivery idempotence, while the absence check handles the watermark arriving before the mirrored deletion.
  - **Disconnection is the one state this package infers rather than observes**, and it says so. The transport is a separate program that must never touch a live vault, so what is visible from here is staleness: a package awaiting a receipt for longer than `DefaultDisconnectedAfter` with nothing having arrived in the meantime. Anything arriving from the peer clears it, even a delivery that acknowledges nothing — the inference is about the transport, not about the package.
  - **Nothing here hides a failure, and a skip is not one.** Each worker's last failure, its failure streak, and the backoff that streak implies are durable in `companion.json` beside the export cursor, and `Read` reports them, so a vault whose exports have been failing for an hour says so rather than looking idle. The backoff doubles from `MinBackoff` to a `MaxBackoff` ceiling and is a **delay rather than a latch**: the moment it elapses the worker runs again. A **skip** never *lengthens* the streak — an unenrolled vault, one with no content history or no commits, one whose import guard another import in this vault already holds (a sync conflict being resolved in the web workspace, say), and a blocked content history are all conditions to look at again next tick, and recording them as failures would put an idle vault into an ever-lengthening backoff and bury the one error that matters under a streak of ones that do not. A skip that **proves there was nothing to do** goes further and *clears* it, because the streak is otherwise only ever cleared by a success, and a worker that failed and then stopped being asked would carry `StateFailing` — and `-check`'s exit 1 — forever on the evidence of a failure nothing is retrying. That reading arrives by two doors, and they are the same fact: the skip decided before the worker runs, and the worker's own refusal as unenrolled, unmanaged, or unborn. `ErrImportBusy` is deliberately neither — a vault somebody else is draining is a worker that never got as far as looking, and clearing on it would drop the backoff too, so an import that fails and then meets a busy vault every pass would retry at the tick interval forever. The producer halts that would otherwise be hidden by that clearing are named directly instead: a cursor from an earlier enrollment epoch, one following another branch, and one the branch was reset *behind* are each a `Problem` on the status. All three leave nothing to measure — the epoch case most of all, because `vaultexport` resolves an interrupted publication *before* it checks the epoch and resolving one advances the cursor durably — so the halted vault reads as having nothing left to publish. Naming them is what makes them act: a status carrying a problem runs the export anyway, so the refusal becomes a recorded worker failure with its evidence instead of a silence. The backwards reset is inferred rather than asked for, from the count the cursor reading already takes: an empty `cursor..tip` whose ends differ is exactly the tip being behind the cursor, which is `vaultexport`'s `ErrHistoryRewritten`; a history rewritten the other way leaves that range non-empty and was already loud. The import worker is the one that skips on `Local.Blocked`, because every application it attempted would be refused identically; the export still runs there, since it reads committed objects and writes only under `.bnotes/sync/`, so a vault blocked today can still ship what it committed yesterday. A status that could not *determine* something also runs the export rather than skipping it: an unreadable export record reads here as "no pending commits", and skipping on it would turn a broken producer into a vault that looks permanently up to date.
  - **A restart costs one early retry and never a change.** Progress is durable in the packages this one does not own — the export cursor, the import ledger, the conflict records, and the published packages and receipts themselves — and `companion.json` carries *only* scheduling state. That is why an unreadable record is **discarded and started again** rather than refused, announced as a problem and no more, and why a record that cannot be *written* is announced rather than fatal: stopping a whole vault's synchronization over a scheduling detail is the worse trade. Shutdown is graceful in the only sense this loop needs — the unit in flight finishes and the loop stops **between** units — because every unit is one call into a package that is already crash-consistent, so a companion killed outright loses no more than one asked politely.
  - **One companion per vault, refused rather than queued.** `LockPath` is `.bnotes/locks/vault-sync.lock`, beside the per-note locks the vault's own ignore rules already exclude, so the coordination file can never become a pending change the content history would commit or a file the exporter would send. It is taken with `vault.TryLockPath`, never `vault.LockPaths`, for `vaultimport`'s reason — `LockPaths` escalates to the exclusive vault guard and the transaction this companion is about to drive escalates to the same guard from inside. Wait-free is also what a second instance wants: `Once` returns `ErrAlreadyRunning` with **no** `Pass` rather than queueing behind a process that intends to run forever.
  - **`Read` takes no lock of any kind.** It opens the content history through `vaultgit.OpenHistory`, reads the durable records with the read-only loaders their own packages expose, and lists the two channels and the receipts in them. A status command is most needed while a drain is running, so anything here that needed a lock would be answerable exactly when nobody is asking. A fact it cannot determine becomes a `Problem` on the status rather than an error off the door, for the same reason: a partial answer about a vault is worth more than no answer.
  - **A converged package still completes the receipt handshake.** `vaultimport` observes every package result on disk and publishes a receipt marked converged with no recovery entry, because the package wrote nothing and there is nothing to undo. The producer verifies the same exact manifest coverage as for an ordinary application and retires the package, so `TransportStatus.AwaitingReceipt` returns to zero and an otherwise healthy quiet pair does not drift into `StateDisconnected` over already-shared content.
