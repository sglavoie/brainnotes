# internal/vaultimport

[Back to the architecture map](../architecture.md).

- `internal/vaultimport` — the **consumer side** of synchronization, and the mirror of `internal/vaultexport`: that package turns this vault's committed history into packages, this one turns a peer's package into this vault's own history. `Drain(root, Options) (*Drained, error)` is the door a synchronization command calls — the whole incoming channel, in causal order, with what it held back and why — and `Apply(root, packageDir, Options) (*Result, error)` is the single-package primitive underneath it, which stays exported because one package is still the unit everything else is said about. `Recover(root, Options) (*Recovery, error)` completes the automatic surface, and `Apply` and `Drain` both run it themselves, so a caller never needs it. `Preview(root, packageID string, Choices) (*Plan, error)` and `Resolve(root, packageDir string, *Plan, Options) (*Resolution, error)` are the two doors a *person* comes through, and they are separate for the reason a dry run is: what a decision changes has to be sayable before it is made. It re-answers none of `vaultsync`'s questions and writes no byte that did not go through `vault.FileTxn`, `noteops.BeginOperation`/`Finalize`, and `vaultgit`'s snapshot — so it sits above all three and nothing imports it. What it is **not**: a transport, and a *merge algorithm* — it detects a conflict, says which of six kinds it is, keeps the remote branch, the local branch and the baseline, holds the operation, and then carries out whichever of four decisions a person made about it; choosing is still a person's act, and `ManualMerge` takes the reconciled bytes rather than computing them. It **is** idempotent, across both a redelivery and an interruption, and the sub-bullets at the end of this entry are how.
  - **Nothing is applied that was not accepted, and the bytes are checked twice.** `Apply` begins at `vaultsync.Accept`, so a malformed manifest, a package addressed to another vault, one from an unenrolled device, one from another epoch, and one whose payloads have not all arrived are each refused before any of this vault's content is touched — and those refusals are returned **unwrapped**, under `vaultsync`'s own sentinels, because the remedy is the same wherever the condition is noticed and a second name would make one problem look like two. Every payload is then re-verified by `vaultsync.ReadPayload` as it is read, and all of them are read *before* the transaction is planned: the transport is still writing into that directory while this code runs, and "checked a moment ago" is not "checked". Two things do run ahead of `Accept`, and both are about earlier runs rather than this package: the import guard is taken, so a package delivered while another import is running is `ErrImportBusy` before it is looked at, and an interrupted attempt is resolved, so the paths this package is about are settled before its preconditions are checked.
  - **One package is one local operation.** A package carrying two operation boundaries is `ErrMultipleOperations` rather than applied in pieces, and the reason is structural rather than a simplification deferred: an ordinary receipt names exactly one recovery entry, and `vaultexport`'s import ledger maps one journal entry to one peer operation and refuses a commit carrying two. `vaultexport` publishes one operation per package, so the refusal cannot fire against a package this project produces.
  - **A precondition failure leaves the contested content alone.** Each change's `ExpectExists`/`ExpectSHA256` becomes a `vault.FileExpectation` verified under that path's own lock, and `FileTxn` stages every replacement and checks every precondition *before* it touches a single destination, capturing the journal only once staging succeeds. So a package this disk disagrees with leaves the contested content exactly as it was, with no partial write, no journal entry, no commit, no receipt, and the package still in the channel — reported as `ErrConflict`, which is a fact about two devices rather than a fault. The peer, having had no receipt, still holds its own copy, which is what lets a later layer present both branches instead of losing one. The **qualification** is where the disagreement is noticed: `FileTxn` re-verifies its read-only requirements again around each individual change, so a configuration pin that fails mid-commit raises the same sentinel *after* the journal was captured — the content is compensated back, and the un-finalized entry directory it leaves is removed by `applier.unwind`, which runs the interruption resolution in-process on every failure path of an application and then returns the original cause unchanged. Such an entry has no manifest, so nothing undoes it, `journal.ListEntries` skips it and `journal.Prune` will never collect it, and its snapshots sit inside the content history's scope as pending additions forever — leaving one is residue nothing in the vault could account for. Using one code path for a conflict and a power cut is the point: they leave states that differ only in whether anybody is still there to look.
  - **The configuration is pinned for the whole commit**, which is session 3's composite pin applied to an import. `brainnotes.toml` is required unchanged unless the package is itself changing it (a transaction cannot both write a path and require it unchanged — and "the same path" is decided by `vaultsync.CollisionKey`, because a package naming `BrainNotes.toml` is writing the pinned file on the case-folding half of a Mac/Pi pair, where a literal comparison would make the transaction both write it and require it unchanged and refuse that package forever — the key is folded rather than resolved, so on a case-sensitive replica the same package drops a pin it could have kept, which weakens one import instead of breaking every one of them), and `brainnotes.local.toml` unconditionally — *including its absence*, since an overlay created mid-import would take effect over notes planned without it. This package supplies the pins; **`internal/vault` decides when they are checked**, and checks them at staging and again before and after every individual change. The first is the door these pins are refused at in practice and it costs nothing, because staging precedes every destination; the later re-checks are what make a mid-commit edit a rollback rather than a half-governed vault, and they are `vault`'s guarantee rather than something arranged here.
  - **Provenance is durable before anything it describes.** `vaultexport.RecordImport` must land before the snapshot, or a crash in between leaves a commit the exporter reads as this device's own work and publishes straight back to the peer that sent it — and it lands earlier still, before the attempt is declared and the transaction commits, so a ledger write that *fails* (an export holding the record's lock past the budget, a corrupt record) refuses an import that has touched nothing instead of leaving an undoable commit the exporter would echo. After `Commit`, `Journal.EntryID()` must answer the pinned identity: it answers the empty string until the first `Capture` — `noteops` creates the recorder lazily, so a refused operation leaves no entry directory — and a different identity would be an entry the ledger does not describe, so either is refused before `Finalize` (`requirePinnedEntry`). The cost of recording first is a ledger entry for an entry that never commits, when the transaction refuses or the process dies before it, which the exporter never looks up. The identity itself is knowable this early, and deliberately so: `apply` mints it with `journal.NewEntryID` and pins it onto the recorder through `WithIDGenerator` (appended last, so it overrules a generator a caller supplied) *before* `BeginOperation`, because the attempt record has to name the entry before the first byte moves. That pin is the one place this package overrules its own `Options`: a recorder that minted a different identity would build an entry the recovery record cannot name, which is the exact state the record exists to prevent.
  - **An acknowledgment is minted only for a durable result it can prove.** A fully converged package is the distinct case: complete per-path observations prove the package result is already present, and the receipt names no recovery entry because the package wrote nothing. `vaultsync` documents that an ordinary receipt means durable application backed by a named local recovery entry, and that it can only check the entry is *named* — it is a leaf and cannot import `internal/journal`. For an ordinary application this is the layer that can, so `journal.LoadEntry` reads the entry back off the disk before the receipt exists; mostly that is defence in depth, since a successful snapshot already loaded the entry to learn what to stage, and it is strictly load-bearing only in a vault with no content history, where there is no safety manager and `noteops` snapshots nothing. Every acknowledged hash is computed from what this disk holds now rather than copied from the change that asked for it, or the comparison `vaultsync.Acknowledge` makes would be the package against itself; a tombstone is `Lstat`ed, because a dangling symlink left at the name is still something occupying it. Failing to mint or publish a receipt does not unmake the change it would have described, so `Apply` returns the `Result` **alongside** the error there — journal entry named, `Receipt` nil. It is the one case where those two are not alternatives, and it is the *last* step rather than any post-commit step: a snapshot that did not happen returns a nil `Result`, because it names the entry in the error itself (`*noteops.SnapshotError` names the entry and says the change is on disk); a provenance record that could not be written refuses before anything is on disk, and names the package, entry, operation and origin. `finalize`'s remaining failures — nothing captured, a manifest the journal could not write — name a path or nothing, and are the defensive ones: reaching them means the recovery history is itself failing, which is exactly what a `Result` would have pointed at.
  - **A cleanup failure is not a failed import.** It means every destination durably holds what the package asked for and a scratch file beside one of them could not be unlinked. Most callers of `Commit` report that as a failed mutation, which is right for a command a person simply reruns; here, stopping would leave the peer's bytes on disk with no undo manifest, no snapshot and no provenance — the one state this package exists to make impossible — over a file that is safe to delete. It is carried out to the caller as `Result.Cleanup` instead. `internal/journal`'s `Restore` is the one other place that does this, and for the same reason rather than by imitation: `noteops.Undo` stops at the first error `Restore` hands it and so never reaches `Finalize`, which would leave a restore that removed a tracked note looking to `vaultgit`'s preflight like a deletion nothing authorizes — so it carries the failure on `RestorePlan.Cleanup` and the callers above render it as a success naming the leftover file. Classification is an **ordering** rather than a set (`classifyCommit`, tested directly because provoking five filesystem failures through a live `FileTxn` is not a test anyone would trust): `*TxnRollbackError` wraps the commit failure and `*TxnRecoveryError` wraps a join containing it, so the `errors.As`-based `IsTxnConflict` answers yes to both — asking the broad question first would report a half-applied package whose rollback failed as "nothing changed".
  - **One import at a time, decided by a wait-free guard that is also a liveness test.** `import.lock` lives in `vaultsync.StateDir()` — beside the record it guards, in the directory this package already owns and the content history already excludes — and is taken through `vault.TryLockPath`, **never** `vault.LockPaths`: that call takes the shared vault guard, and a large package's transaction escalates to the *exclusive* guard, so the import would deadlock against itself. Wait-free rather than queuing, because whoever holds it may be halfway through an application and a waiter would come out of its wait holding a package it read against a state file that has since changed; a second import is refused as `ErrImportBusy` before the package is read, having touched nothing. The second property is why the guard is a lock rather than a flag: an unresolved attempt in the state file cannot say whether the process that wrote it is still running — that is exactly what a crash makes unknowable — and a flock is the one signal an operating system withdraws when a process dies. Held guard means a live import and the attempt is none of our business; **free** guard beside a pending attempt means the writer is gone and the attempt is ours to resolve. Disjoint paths therefore buy no concurrency, which is the deliberate price: per-path concurrency would make that question unanswerable, and a retry is cheap next to a rollback over somebody's newer edit. The guard sits *upstream* of `vaultgit`'s safety lock, whose preflight takes it, checks, and **releases it before returning** — so the two remaining `vaultgit` fates are reachable only when something outside this package holds that lock: refused as `vaultgit.KindBusy` before any artifact existed, or **landed but not snapshotted**, where `FileTxn` committed the bytes, `RecordImport` recorded them, and the snapshot found the lock busy. The second is a `*vaultgit.SnapshotError`, and because that type unwraps to the engine refusal it carries, `IsBusy` is true of it too — so a caller distinguishing "nothing started" from "on disk, undoable, uncommitted" must ask `IsSnapshotFailure` **first**, the same ordering trap as the transaction sentinels above. Two packages describing *one* path are refused at the guard like any other pair, and retrying the loser afterwards reaches `ErrConflict` — it stages against what the winner committed, and the note now holds content its producer never saw. That is the same refusal a second delivery would have met with no race at all, which is the point: serializing the two changes *when* the conflict is found, never *whether*.
  - **An interruption converges on "never happened" or "happened completely", and the undo manifest is what decides which.** An import is six durable events — the peer's bytes, the provenance record, the manifest, the commit, the receipt, and the memory of all of it — and no two can be made one, so a process that dies in between leaves a vault that is perfectly consistent and completely unexplained. `apply` mints the recovery entry's identity and **declares the attempt before the first byte moves** — everything up to that point creates nothing, since `BeginOperation` only refuses and `plan` only describes — and `Recover` is the only reader of that record. The manifest is the discriminator because it is the moment the change stops being something the vault is *doing* and becomes something it *did*: it is what `bn undo` reads, what preserves pre-mutation bytes, and what the receipt promises the peer. Before it, roll **back** — acknowledging a change this vault could not undo is the one thing a peer must never be told. After it, roll **forward** — the provenance record is already durable and the change is already this vault's own history — and every forward step is idempotent by construction: `RecordImport` is a no-op for an entry it already holds, `ensureSnapshot` skips an entry the content history has, and an already-published receipt is **adopted** rather than re-minted. Three details carry the weight. `snapshotNeeded` asks the content history *before* committing rather than letting the engine work it out, because an entry that deleted a note carries the only authorization for that deletion, so re-committing one whose deletion already landed meets a path gone from the working tree *and* from HEAD — which `vaultgit` reads as an unexplained deletion and latches `blocked.json` over: recovering from an interruption must not be able to block the vault. That question is asked *again* where it is actually safe to answer — `vaultgit.CommitJournalEntry` plans no commit for an entry whose manifest HEAD already holds, checked **inside the safety lock** — because the autosave watcher can commit the same finalized entry between `snapshotNeeded`'s answer and the snapshot, and a check outside the lock is a race however carefully it is placed. `snapshotNeeded` stays as the cheap pre-check that avoids taking the lock at all. A rollback asks `journal.Started` — the entry *directory*, created by the first `Capture`, which `FileTxn` runs before it applies anything — rather than inferring from the paths, because comparing a path against what the package *said* it would find is only meaningful when the package was right about that, and a package that was wrong is precisely the one that got refused. A path that had already **converged** is named in `Attempt.Converged` and exempted, and that record is load-bearing rather than bookkeeping: the transaction never staged it, but a rollback deciding per path sees a path holding what the package installs and reads it as applied — so without the record it would restore content this import never wrote to a baseline nobody asked for. The whole package converging is the same fact one size larger: nothing was staged, so there is no recovery entry to name; `Record.Converged` records that fact and the receipt explicitly claims convergence after every result is observed on disk. The peer can then retire its copy through the ordinary verified-receipt path. And `settleTransactions` runs `vault.LockPaths(root)` with **zero** paths first, so `internal/vault` rolls any prepared transaction forward before anything here reads a path; planning a rollback against the earlier reading would put half the package back and leave the other half applied. One refusal keeps every version: a rollback that would cross a path holding neither what the package replaced nor what it installed. That is `ErrStrandedImport`; it keeps the attempt, the entry and its snapshots, and the content, and it **blocks every further import** so the evidence cannot be buried by the next package the transport delivers — a person with all three versions can choose, and a process that guessed would have destroyed one. Because the price of that refusal is the whole import path, **a recovery pass is itself a sequence of durable steps and records its own progress**: `rollBack` writes `Attempt.Restored` the moment the content is back, before it discards the journal entry and settles the attempt. A restored path reads exactly like one never written, so without that record an interruption between the restore and the tidy-up would leave a rollback that a later human edit turns into paths holding "neither" — stranding the vault permanently over work that had already finished correctly. The `crashRestored` kill point is where that is tested, by interrupting a recovery pass and then editing a note before the next one runs. The record covers every step *after* it, including `DiscardUnfinalized`, which is a recursive directory removal rather than one write; it does **not** cover the instant between the restore commit and itself, because a content transaction and a state file cannot be made one write and recording first would make a crash before the restore skip the restoration and destroy the snapshots that are the only copy of the pre-change bytes. That residual window is also why `OutcomeDiscarded` is documented as a statement about what a pass did rather than a promise that no destination was ever written: a rollback that finished and did not survive to say so is reported by the next pass as discarded. The forward direction has no counterpart: an acknowledgment that cannot be minted or published fails the *message*, not the vault, so the attempt is settled with no receipt and the peer simply keeps its copy (see `resolver.complete`).
  - **A redelivery is answered from the ledger, never applied again.** The transport moves whole directories and knows nothing about receipts, so a package reappears whenever a channel is re-copied, a peer is restored from a backup, or an acknowledgment goes missing. Applying it twice is not merely wasteful: the vault no longer holds what the package expected to find *because the package changed it*, so the second delivery would be reported as a conflict between the peer and its own change — a confusing and unresolvable answer to a delivery that is in fact already satisfied. `answer` reports what was applied as it was applied, and republishes the **original** receipt rather than minting a new one. That distinction is the point rather than an optimization: a receipt is a statement the producer may drop its only copy of a change on, so repeating one is honest where making a second — with a new timestamp, for an application that happened earlier, possibly since undone — would not be. A receipt is published under a name that can only be taken once, so republishing meets its own bytes and must read `ErrPackageExists` as **success**; that reading is local to this one caller, which knows the bytes in the channel are its own because they came out of the record that published them. The single exception is a package applied and never successfully acknowledged: there is no earlier statement for a new one to contradict, so `retryAcknowledge` mints one — held to every check a first acknowledgment is held to, including reading the entry back off the disk and hashing what the paths hold *now*.
  - **A conflict is decided before the transaction exists, named in the vocabulary of its remedy, and every version of it is kept** (`conflict.go`, `conflict_inspect.go`, `conflict_retain.go`). `applier.inspect` reads every change against this disk *ahead of* `plan`, and the ordering is the whole of what it buys: a transaction reports the first precondition that failed and has nothing to say about the rest, so a conflict discovered there could hold one path of an operation that contests three — and it reports *that* a path disagreed, never *how*, which is the only thing a resolution can act on. Deciding first also means the contested content is never staged over, so the local branch is read at leisure rather than rescued out of a rollback. `internal/vault` still re-checks every expectation under the path's own lock and that is not redundancy: this reads without holding anything, so this decides *which* refusal and the transaction still decides whether a write may happen. `classify`'s six `ConflictKind`s are ordered by how much each explains — a **filename collision** first, because it is true whatever the expectation says (the package can be perfectly right about the path it named and still be about to create a second file that is one file on a folding replica) and a name occupied by something that is not a regular file comes with it, since the remedy is the same act of clearing the name; the **configuration** layers next, ahead of the content comparison that would otherwise swallow them, because declarations govern notes that are not in the package at all and "keep mine" is not a cheap choice there; then the three content answers, with `Tombstone()` and absence separating **delete-edit** from **edit-delete** and a plain **concurrent edit** last. The **identical outcome** is not a conflict at all — a path already at the result is `converged` — with one exception: the *source* of a rename is "already at the result" whenever the note is merely gone, which is equally what this vault moving it elsewhere looks like, so it is judged against its destination and disagreement there is a **divergent rename**. `renamePairs` recovers the pairing from the package rather than trusting a label, because a producer's claim is one a consumer could not check: a tombstone whose exact content is created at a free path *in the same operation* is the signature, and two notes that merely hold identical bytes cannot fake it. Retention is durable and content-addressed — `ConflictRecord` in `import.json` under `Conflicts`, the bytes under `.bnotes/sync/conflicts/<package>/<sha256>` through `vault.WriteStateFile`, so a rename's three branches cost one file and re-detecting an unchanged conflict rewrites the same names instead of growing the directory. A hold is deliberately **not** an `Attempt`: it has touched nothing, and recording it as pending would make every later import refuse, which is the opposite of the point. The **baseline** is best-effort and says so — the package carries it for a rename, `vaultgit.OpenHistory` holds it whenever the local divergence is an uncommitted edit (the common case, since a committed one would have been exported and the two would be arguing through predecessors instead), and anything older is recorded by digest with no bytes, which is the honest answer rather than a merge against the wrong base. Dropping a hold is two steps in a fixed order for the reason `RecordImport` is: `release` takes it out of the record and the record is saved, *then* `discard` removes the bytes — a crash in between leaves files nothing points at, which the next hold overwrites and `collectRetained` sweeps, where the other order would leave a durable invitation to resolve a conflict from versions that no longer exist. `applier.retain` is the other end of `inspect`'s race: an edit landing between the inspection and the staging check is refused by `FileTxn` with nothing written down, so the rollback runs and the disk is inspected a second time — and a second inspection that finds nothing is not an error, it means the edit was itself undone.
  - **`Drain` is the ordering layer, and ordering is a fact about the set** (`schedule.go`). Nothing about it can be said from `Apply`, which answers only about the package it is handed. The channel is sorted by origin device, then sequence, then package identity — never by anything the filesystem says, since a directory has no order, modification times are the transport's rather than the producer's, and `CreatedAt` is a clock on another machine the protocol already documents as unorderable; an unreadable package sorts **last**, or a directory still being copied in would decide where everything else went. Four reasons hold a package back, checked in order of how much each explains: `HoldUnreadable` (not a scheduling decision at all — usually `ErrIncompletePackage`), `HoldDependency` (a stated `Requires`, matched at the **exact** position rather than against a high-water mark, because a vault that has applied 1 and 3 cannot tell whether 2 was skipped or has not arrived), `HoldPredecessor` (a change naming a causal ancestor carried by another package **still in the channel** — the restriction is load-bearing, since a predecessor is just as often one of this vault's *own* operations that the peer imported, an identity no import record here will ever hold, and holding on every unknown one would deadlock the first package a peer ever sends back), and `HoldOrder` (a path an earlier unapplied package also changes, compared through `CollisionKey`, against a **strictly** earlier package so an overlapping pair cannot hold each other). A conflict holds its own operation and everything downstream of it and **nothing else** — stopping the whole drain at the first one would be simple, correct about content, and would let one contested note keep a hundred unrelated ones out of the vault for as long as nobody looked. `DrainContext(ctx, root, Options)` is the same pass for a caller that has to be able to stop it — the sync companion on a signal — and `Drain` is it under `context.Background()`; the context is consulted only before recovery and before each package, never inside one, and each package runs under `context.WithoutCancel`, so a stop leaves every package either applied or untouched. The pass takes the import guard **once**: a loop around `Apply` would take and release it per package, and an ordering decided at the top of that loop would be made against a vault that has moved since. `passes` is a fixed point rather than one sweep, so a chain arrives in one drain instead of one drain per link, and it stops when a pass applies nothing — the only termination condition independent of the graph's shape, so a cycle no honest producer can emit stalls rather than spins. `sweep` runs first and answers two different failures: a hold whose package left the channel describes a conflict nobody can act on, and a retained directory no hold names is what a process that died mid-`discard` leaves. `Drain` returns an **error** only for conditions about the *vault* — `ErrImportBusy`, `ErrStrandedImport`, an unreadable or foreign record — because everything a package can be wrong about leaves the others worth applying; a package whose content landed and whose bookkeeping did not is `Applied`, with the failure carried out on `Drained.Unfinished`, not a hold. Those four are the reasons `hold` decides *before* attempting; three more are verdicts on what came back, and the distinction every one of them draws is **what to do about it**: `HoldConflict` (a person resolves it), `HoldRejected` (a refusal no wait fixes — an unknown format token, a manifest that contradicts itself, a path that is not portable vault content, more than one operation, the wrong vault, an unenrolled origin, a stale or ahead epoch), and `HoldFailed` (everything else, which is a retry). **A reason is not a place**: `rejected` is asked of the scan's failure *and* of the application's, because the same distinction lands in either depending on whether it is a fact about the manifest — which `ReadManifest` checks, so an unknown format never reaches the application at all — or about the enrollment, which only `Accept` checks. `ErrIncompletePackage` is the one refusal that is a wait, and it too arrives from both: the scan reads only the manifest, so a package whose payloads are still copying in looks whole to the scheduler and is caught late. Both report `HoldUnreadable`. **A `Result` outranks the error it came with**: the `result != nil` arm is checked before any classification, because a failure to acknowledge can carry a sentinel that also means "refused" — a receipt written by a newer build in this vault's *own* outgoing channel raises `ErrUnsupportedFormat` after the content is durable — and reporting a committed package as one this vault will never accept would drop both the `Result` and the failure out of the report. A verdict is cleared at the top of every pass and re-decided, so the partial report a mid-pass refusal returns carries no stale wait; the packages that pass never reached report `HoldNotAttempted` rather than a blank reason, which is the difference between "the drain stopped before its turn" and "its explanation went missing". `Held.Conflict` is nil-checked even under `HoldConflict`: a precondition the transaction refused and a second inspection cannot reproduce — the concurrent editor put the note back — is a real refusal with no record, and `retain` writes none rather than inventing one. `Drained.Unfinished` carries what happened after the content landed, and reads `Result.Receipt` rather than the error to say which step it was: a `Result` carries a receipt exactly when this vault has an acknowledgment for the package — minted now, or minted before and being republished, including when publishing it just failed — so a nil one means the peer was never told and a non-nil one means it was and something after that did not finish.
