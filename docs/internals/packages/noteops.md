# internal/noteops

[Back to the architecture map](../architecture.md).

- `internal/noteops` — the shared note-mutation layer used by both CLI commands and the web APIs. `preview.go` defines the canonical `NotePreview`/`PreviewChange` model that every mutating command's `--dry-run` and every web preview render through, so the two views can never drift. `capture.go` holds the quick-capture primitive behind `bn capture` and the web quick-capture box: `PreviewCapture`/`ApplyCapture` append one fixed-format `- YYYY-MM-DD HH:MM <text>` bullet to the configured inbox note under the configured heading, splicing bytes (never re-marshaling frontmatter) so every pre-existing byte survives — the write is strictly additive, so even the heading-absent path only appends a separator, the heading, and the bullet rather than collapsing trailing blank lines — bootstrapping the note inline when it is absent, and — uniquely among noteops writes — re-reading and re-planning up to 3 times on a `vault` transaction conflict before returning `CodeConflict`, which is safe only because an append is commutative. `capture_heading.go` owns the single line-oriented heading scanner and exports `CountSectionBullets` so `internal/cockpit` counts exactly the section the writer would append to; its `containsATXHeading` is what makes the synthesis draft's reserved `## Sources` heading detectable without matching fenced-code samples. `synthesis.go` is the create-only pair behind the synthesis workbench: `PlanSynthesisNote` resolves the destination, validates the draft, and returns the exact bytes plus every read-only expectation, and `ApplySynthesisNote` writes those exact bytes rather than rebuilding them, so what a user previewed is what lands. A synthesis plan always carries `ExpectMissing` — V1 creates new notes only and `ApplySynthesisNote` refuses any other expectation — and its `Requirements` pin every ordered source (and, when the caller supplies it, `brainnotes.toml`) through `FileTxn.Require`, so a source edited between preview and apply is a `CodeConflict` with no note and no journal entry. Plan-time verification through `vault.VerifyState` is a courtesy that refuses a doomed plan early; only the transaction's own recheck makes the write safe. `source.go` + `source_save.go` + `source_ledger.go` are the raw-Markdown pair behind the web editor, and the one noteops write whose unit is the **whole file**: `ReadSource` hands out the bytes on disk and their **revision** (`vault.HashBytes` of exactly those bytes), and `SaveSource` writes the submitted bytes back verbatim under `ExpectHash(revision)`. Verbatim is the load-bearing word — the content never round-trips through `frontmatter.Marshal`, which always sorts keys, so a save would otherwise silently reorder frontmatter nobody touched; `ValidateSource` therefore *parses* the frontmatter to refuse what could not be stored (a properties block that is opened **and closed** whose YAML does not parse, a NUL byte, over `MaxSourceBytes`) and then throws the parse away — and it refuses nothing else, so a `---` line with no closing delimiter is stored verbatim, because `frontmatter.Parse` reads that as a body beginning with a horizontal rule and a surface that refused it would be the only one in the vault unable to save a note the vault itself serves. `resolveSourceDestination` takes the `*config.Config` as an explicit second positional parameter for the same reason `PlanSynthesisNote` does, and owes the same four refusals its synthesis sibling owes: containment, the `.md` extension, no symlink, and `vault.WalkExclusion` — a destination `Walk` would never visit (any hidden component, the templates directory, the configured ignores) is `CodeForbidden`, because a note written there is on disk and in no index, no graph, no search and no query, and under `.bnotes/` it is also outside `vaultgit.InScope`, where the journaled write commits *nothing* while the answer reports a revision and a success. It is the deliberate inverse of `capture.go`: an append is commutative and may replan, a whole-file write is not and never does, so a conflict comes back as a typed `*SourceRevisionError` for a person to resolve rather than as a retry that would overwrite the other writer. The four remaining ways submitted bytes could vanish are each an answer rather than an error — a duplicate or a lost response replays a per-`save_id` record, a note that already holds the bytes converges to a success that changed nothing (which is also how a repeated create answers), and a snapshot failure returns a non-nil `*SaveSourceResult` **beside** the error, because the bytes are on disk and a caller told only "failed" would resubmit against a revision this save already replaced. The record lives under `.bnotes/source-saves/`, written inside the same transaction and journaled with the note so an undone save is re-submittable, and that path is deliberately outside `vaultgit.InScope` so an idempotency key never becomes commit content; `pruneSourceSaveLedger`'s expiry sweep is the single direct `os.Remove` on the surface and carries its marker. `journal.go` is the seam every mutating operation begins and ends through, and its two halves are the whole write-safety contract stated as code. `BeginOperation(vaultRoot, operation, command, targets, opts...)` runs both refusals **before** the operation may create anything — `vault.GuardMutation` over the vault root plus every target the caller can name yet, then the `internal/vaultgit` preflight, which is what catches a vault left blocked by an earlier failure or holding a deletion nothing explains — and only then returns a `*Journal` whose recorder is created lazily on the first `Capture`. Putting both ahead of recorder creation, lock acquisition, directory creation, and temp files *is* the point: those artifacts are exactly what a refusal exists to prevent from existing. Targets that cannot be known yet are not a gap, because the same location policy is enforced again underneath every individual write; naming what is known only makes the refusal earlier. `Journal.Finalize` inverts the order deliberately — the undo manifest is written and made durable **first**, so the undo bytes are durable before history records the mutation, and the snapshot is taken **second**, staging exactly the paths that manifest names. An operation is a success only when both have happened, so a snapshot that fails after the bytes have landed is returned as a `*SnapshotError` (an alias for `vaultgit.SnapshotError`; `IsSnapshotFailure`, `CodeSnapshotFailed`, which `HTTPStatusForError` renders as a **distinct 500**) whose message states that the change is on disk and that further writes are blocked, and which **never claims a rollback** — nothing was rolled back, and inviting a retry of a write that already happened is how one capture becomes two bullets. A no-op captures nothing, finalizes nothing, and commits nothing, which is what keeps an empty commit off a clean vault. `operation` is a fixed token chosen by the code and is the only part of this that reaches a commit message; `command` carries the full `bn` invocation, note names and property values included, and never leaves the local journal. Two operator-authorized restores sit beside the ordinary mutations and go through the same begin/finalize pair: `undo.go`'s `Undo` replays a journal entry, and `backup_restore.go`'s `RestoreBackup` preflights, extracts, and then calls `Safety.CommitRestore` — the single **wholesale** snapshot in the system, justified only because the operator asked for the entire tree rather than for a set of paths, and therefore the one place where "an unrelated working-tree edit is not swept in" deliberately does not hold. `--wipe` empties the vault first, and what it skips is exactly what `internal/backup` excluded from the archive — `backups/` and `.git/`. That is not tidiness: neither is ever inside an archive, so removing either would destroy the only copy of something no restore could put back, and for `.git/` that copy is the history this very operation is about to commit into, plus every version the wipe just discarded.
