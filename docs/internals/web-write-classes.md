# Web write classes

Companion to `CLAUDE.md`; read before adding or changing any mutating web API route.

Every class below is reached only after the serving mode has allowed the request.
Which modes may write at all, which routes are refused at the guard, and where
the process-launch and media boundaries live are in
[Serving modes and capabilities](serving-modes.md) — read that first when adding
a route, and ask `s.caps` rather than branching on an option flag.

- **Read-only query routes**: `GET /api/query/validate` and `GET /api/query/completions` (`internal/web/query_api.go`) are *not* a write class and deliberately carry no CSRF token — they are the `/api/facets` shape: re-check `r.URL.Path` exactly and 404 anything below it, reject a non-`GET` method with `Allow: GET` and 405, read one snapshot, and write nothing. Validate answers `200` with `ok:false` for a query that does not parse or compile, because a half-typed expression is not a client error; only a malformed `pos` is a `400`. It compiles through `compileFilterExpr`, the same door `/api/search?expr=` uses, so validate accepts a query exactly when search would. Both routes speak **UTF-16 code-unit offsets** in every position they emit or accept (`error.start`/`end`/`column`, `pos`, `replace`), converted server-side by `internal/web/utf16.go`: the browser's `selectionStart`/`setSelectionRange` count code units, so a byte offset would drift a caret or a highlight by one per non-ASCII character in an NFC vault full of accented titles. A new read-only route belongs in this class; do not give it a token, and do not let it emit a byte offset a caret will consume.
- **Saved-views write class**: `POST /api/views/preview` then `POST /api/views/apply` (`internal/web/views_api.go`) are the `/api/properties/schema/{preview,apply}` class, reusing `s.propertyPreviews` under a `propertyPreviewView` kind so receipt expiry, one-use semantics, and the file-digest check come free. The class choice is not a judgement call: `brainnotes.toml` *is* the vault-root marker, a mangled patch is a vault-wide failure that blocks every later write through `ensureConfigWritable`, and `PatchViews`'s upsert replaces a whole `[[views]]` block, destroying any comment inside it. **The create case still auto-chains preview into apply** — a view that does not exist yet has no block to destroy, so the client fires both calls and then shows the rendered diff as a receipt; overwrite, rename, and delete must have the diff confirmed before apply. The create receipt is a *post-success record*, published only after the apply landed and modelled as a `SavedViewCreateReceipt` that carries the diff and the name but no preview ID, so the consumed one-use receipt is structurally unreachable from it; it renders into the same block an overwrite confirms in, tagged `data-saved-views-diff-role="receipt"` with the confirm button hidden, and a confirmation with only a create receipt in hand is refused like any other unbacked confirmation. That is one write class with two client behaviours, driven by the `created` flag the preview returns, not a second class. `GET /api/views` is read-only and belongs to the `/api/facets` class above; it answers from `config.Config` alone, with no vault walk and no graph, and reports a view whose query stopped compiling as `enabled:false` plus a `detail` rather than dropping it. Applying goes through `commitPropertyPlan` with the pin from `s.pinnedConfig()`, so `brainnotes.toml`'s three independent writers (`/api/properties/apply`, `/api/properties/schema/apply`, `/api/views/apply`) cannot corrupt each other — `configPin` makes the loser a 409, which `viewsWriteError` surfaces as "config changed, re-check the diff" wherever it fires (receipt digests, replan, or the transaction precondition) rather than as a generic failure. The pin is a **pair**, one `configLayerPin` per layer, because the patch these writers computed was decided by reading both files: the portable layer carries `ExpectHash`, and `brainnotes.local.toml` carries `ExpectHash` when it is present and `ExpectMissing` when it is not, so an overlay *appearing* between the plan and the commit is a conflict rather than a second source nothing read. Absence is a precondition here, not a missing one — an overlay is what would shadow the key just written and turn a reported success into a no-op. A view write finishes through `finishConfigWrite`, not `finishPropertyWrite`: no note changed, so the unconditional `s.state.invalidate()` is pointless. `[views]` is deliberately **not** excluded from the configuration generation — a generation meaning "some parts of the config changed" would be a footgun for every pin that compares it — so a view save does pay one `properties.Build` and one recall corpus rebuild, which is accepted.
- **Property intelligence cache**: `internal/web`'s `vaultState` caches one `*properties.Index` keyed on the snapshot serial plus the configuration generation, so a note reload or a configuration reload — either layer — rebuilds it and nothing else does. The cached index is shared and must stay immutable — `properties.Build` copies what it needs from notes and never mutates its inputs.
- **Property workbench save model**: `/api/properties/value` is the workbench's only unpreviewed write, and it is deliberately narrow — one note, one property, either a whole-value replacement or a single list addition, gated on the caller echoing the note's current hash. It is *not* the server's only unpreviewed property write: `/api/notes/frontmatter/set`, `/api/notes/frontmatter/unset`, and the three `/api/pins/*` routes are the same single-note single-property class, differing only in that they rely on the write's own revision precondition instead of a client-echoed hash. Everything else (unset, list removal, multi-note changes, bulk value replacement, property rename, repair, and every schema edit) must go through `/api/properties/preview` then `/api/properties/apply`. Property receipts carry the configuration generation as well as the note hashes, so a configuration change invalidates outstanding note receipts rather than letting a plan built against old declarations apply. The generation tracks the **composite** fingerprint of both layers, so an edit to `brainnotes.local.toml` alone — including its appearance or removal, which are distinct from an empty one — invalidates receipts exactly as a portable edit does. A fatal blocker (`parse_error`, `not_found`, `key_conflict`, `config_conflict`) suppresses the receipt entirely so the whole selection is refused; `repair_skip` is advisory and leaves the receipt intact. When adding a property action, decide which side of this line it falls on rather than adding a third path.
- **Unpreviewed web write classes**: `/api/capture` is the deliberately-unpreviewed *additive* body write, and `/api/source/{save,create}` the deliberately-unpreviewed *whole-file* one (the other unpreviewed Markdown routes — `/api/properties/value`, `/api/notes/frontmatter/set`, `/api/notes/frontmatter/unset`, `/api/pins/*` — write properties). Capture is narrow for different reasons: one note, strictly additive, so it cannot destroy existing bytes, and a confirm step would defeat the entire point of a quick-capture box. Its safety comes from the `vault.FileTxn` precondition pinning the revision the append was planned against — not from a client-echoed hash, because the box never loaded the note and has no hash to send. A conflict surviving `ApplyCapture`'s 3 internal replans returns `409`; the browser resubmits. The CLI keeps the canonical `--dry-run` preview, so the unpreviewed path is web-only. `POST /api/related/item` is a distinct unpreviewed, non-Markdown class: it is CSRF-protected, resolves both note identities through the current graph, and writes only serialized runtime state in `<vault>/.bnotes/recall.json`, never Markdown or the undo journal. Do not invent a further write class: a new Markdown or configuration write still belongs on one of the two file-write sides — preview-gated, or narrow with a precondition that refuses a stale plan — while runtime-state writes must remain confined to a documented sidecar boundary with route-appropriate validation.
- **Raw Markdown source write class**: `GET /api/source`, `POST /api/source/preview`, `POST /api/source/save`, `POST /api/source/create` (`internal/web/source_api.go` over `internal/noteops/source.go` + `source_save.go`) are a whole-note Markdown write, and they sit on the **narrow-with-a-precondition** side of the two file-write sides named by *Unpreviewed web write classes* above, not the preview-gated one. `/api/source/preview` is a **renderer, not a gate**: it takes the bytes in the editor and answers rendered HTML so a person can see what they typed, it holds no receipt, and a save neither needs nor consults one. Nothing about a save is validated by having previewed — the preview and the save each call `noteops.ValidateSource` themselves, and a client that never previews is not a client that skipped a check. A receipt would be the wrong instrument anyway: a raw editor's diff is the two versions of the file, which the client already has, and a one-use token would only make a slow typist's save expire. The precondition is the **revision** — `vault.HashBytes` of the bytes on disk, handed out by the read and required back by the save — pinned into the `vault.FileTxn` as `ExpectHash`, so an edit planned against a version somebody else has replaced is a `409` carrying the *current* content and revision rather than an overwrite. That expectation is derived from what the save itself just read, never from what the client sent, so the message and the guarantee cannot disagree. **Unlike a capture this never replans**: an append is commutative and a whole-note save is not, so a conflict is the person's to resolve and retrying would silently discard the other writer. The six ways submitted bytes could vanish are each answered, in a fixed order — unstorable content first (a properties block that is opened *and closed* whose YAML does not parse, a NUL byte, over `noteops.MaxSourceBytes`), so nothing downstream can turn it into a success; then a recorded outcome; then convergence; then the revision comparison. `ValidateSource` refuses only what could not be stored **as a note**, so a `---` line with no closing delimiter is accepted and written verbatim: `frontmatter.Parse` reads it as a body beginning with a horizontal rule, and a surface that refused it would be the only one in the vault that cannot save a note the vault itself serves. A **stale** revision is a typed `*noteops.SourceRevisionError`. A **duplicate** or **lost-response** resubmission is answered from the idempotency ledger under `.bnotes/source-saves/`, one file per `save_id`, written inside the *same* transaction as the note and journaled with it, so an undone save is re-submittable; the directory is deliberately outside `vaultgit.InScope`, so the record never becomes commit content, and `pruneSourceSaveLedger` holds the one annotated `os.Remove` on this surface. A reused id carrying *different* content is a conflict, never a replay. A **no-op** — the note already holds exactly these bytes — is a success with `changed:false` and the revision the note is actually at, which is also how a repeated create answers, because a destination holding the submitted bytes is the create that already happened. A **snapshot failure** returns a non-nil result *beside* the error: the bytes are on disk, so `writeSourceSaveError` answers `500 snapshot_failed` with the landed revision and `changed:true`, and a client told only "500" must not resubmit against a revision this save already replaced. `/api/source/create` is the only route on this surface that names a **brand-new** path, so it owes the location rule the synthesis apply owes: `resolveSourceDestination` refuses a destination `vault.Walk` would never visit — any hidden component (`.bnotes/`, `.git/`), the configured `templates.dir`, and anything under the `ignore` list — as `403`, because a note written there is on disk and in no index, no graph, no search and no query, and under `.bnotes/` it is also outside `vaultgit.InScope`, where the save's own snapshot commits nothing while the answer reports a revision. Both losses are invisible from the client's side, which is why the refusal is part of this write class rather than a nicety. It is decided from the *configuration*, so the read path takes `s.config()` and the write path `s.pinnedConfig()` — the same bytes the transaction verifies at the commit boundary. `brainnotes.toml` is pinned through `sourceConfigPinOptions(s.pinnedConfig())` like every other note write, and the state cache is invalidated whenever a result came back at all, landed or not. All four routes are absent from read-only's POST allowlist and from `replicaReadPath`, so a replica refuses every one of them. Body bounds are in [Serving modes](serving-modes.md): the three write routes widen to `sourceRequestBodyLimit` in `routeBodyLimit` and re-apply it in `requireManagementPost`.
- **Attachment staging write class**: `POST /api/attachments/upload` and `POST /api/attachments/cancel` (`internal/web/attachments_api.go` over `internal/attachments`) are the one write class whose bytes do **not** become vault content when the request succeeds. An upload streams into private staging under `.bnotes/uploads/`, and only the save that references it puts anything in the vault — so this class is a *staging* surface with a *commit* that belongs to the raw Markdown source class above. `/api/attachments/upload` is the only mutating route on any surface that cannot use `requireManagementPost`: the body **is** the file, so `ParseForm` would consume it, and `requireStreamedAttachmentPost` restates the same preamble without the parse — exact route, POST only, `http.MaxBytesReader` at `config.MaxAttachmentFileBytes`, the CSRF token from the `X-BN-CSRF` **header** (which `requestCSRFToken` already prefers and is the only form available to a request whose body is not a form), then `ensureConfigWritable`. The metadata — the owner and the client's filename — rides in the query string, and a multipart form is deliberately not used: it would mean buffering or re-spooling megabytes this process has no reason to hold. **Two bounds in series**, and they are different numbers for a reason: the transport refuses a body no vault could accept before a byte is written, and `Store.Stage` refuses one *this* vault does not accept while streaming into a private file it then deletes, because `[attachments].max_file_bytes` is configurable downward from the ceiling and never upward. Both refusals are a `400` — `attachmentError` classifies `*http.MaxBytesError` alongside the store's `ErrTooLarge`, or a vault that left its limit at the ceiling would be told "server error" for a file that is merely too big. Nothing in the upload's answer can be turned into a request for staged content, because **staging is not served at all**: `.bnotes/uploads/` is a dot-path, and `privateMediaPath` refuses it under its own name and through any symlink resolving into it. The **destination is claimed at staging time, not at commit time** (`Store.reserve`, keyed by `vaultsync.CollisionKey` so a case-only or normalization-only clash is one name): a transaction can only refuse a destination that is taken, and refusing is the wrong answer to two drafts uploading `photo.png` — claiming while both are private turns that into two destinations with nothing left for the commit to negotiate. The **owner** is an opaque client-minted string that scopes a cancel and a commit; it never becomes a path component, and `ErrNotFound` covers both "no such upload" and "not yours" deliberately, so the difference is not a way to ask whether somebody else's id exists. A save names its uploads with repeated `attachment` fields plus one `owner`, and `resolveSaveAttachments` **carries** an id the store cannot resolve rather than refusing it, because the save whose staging is gone is very often the save that already succeeded: `noteops` refuses `UnresolvedAttachments` *after* the `save_id` ledger has had its chance to replay, which is the only place a retry and a save naming a file nobody staged can be told apart. After a result comes back, `forgetCommittedAttachments` drops only the staged copies the **result** names — a replayed save answers from an earlier call's record, and discarding an upload on the strength of somebody else's outcome would delete bytes no note holds — and its failures are not reported, because the bytes are in the vault and a leftover staging file is disk the sweep collects. Abandoned staging is collected **once per server start and again at the start of each upload** (`Store.Sweep` under `vault.TryLockPath`, so a second sweeper stands down instantly), and the sweep's failure is **dropped, never returned**: it is housekeeping over files belonging to other requests, so an artifact nobody can remove says nothing about the upload in hand — and since the upload route is where the sweep runs, returning it would let the first un-removable file refuse every upload the vault ever receives again. The startup sweep is what keeps the arrears bounded at one session: the person whose browser died mid-upload is exactly the person who may never upload again, and staging is outside `vaultgit.InScope` and outside `vault.Walk`, so nothing else would ever report it. A read-only server does not sweep, because sweeping is a write. Neither route is in read-only's POST allowlist, which is the right default twice over: a replica accepts no writes, and staging no save could ever commit is disk somebody else pays for. A cancel is a **courtesy, not a guarantee** — an upload nobody cancels is swept, and one already gone answers exactly like a successful cancel, because "it is not in staging" is what the caller asked for either way.
- **The raw editor page is a client of that class, never a class of its own**: `GET /edit?key=<key>` (`internal/web/editor_page.go`, `templates/editor.html`, `static_src/source-editor*.ts`) writes nothing and renders **no note bytes**. The template carries the key, the route, the CSRF token and `noteops.MaxSourceBytes`, and the source itself is fetched from `/api/source` after the page loads — deliberately, because rendering the content into the template would make the page two reads (the handler's snapshot and the API's later read of the file) with no revision tying them together, so a save could be planned against bytes the editor never showed anybody. The page resolves its note exactly once, through the shared snapshot like `/synthesize`, and is absent from `replicaReadPath` along with the four API routes it calls: a replica refuses the page rather than serving an editor whose every save is refused. The preview pane posts to `/api/source/preview` and injects the HTML the server answers with, because `internal/web/markdown.go` is the vault's **only** Markdown renderer and a browser-side one would be a second answer to what a note looks like — `internal/web/e2e/editor.spec.js` asserts that parity in a real browser, against the shipped bundle. Out-of-order previews are the client's own hazard and are answered in `static_src/source-preview.ts`: a monotonic sequence, a response applied only when it is the newest yet applied, and a "rendering" state that clears only for the newest response *issued*. The editor sends `save_id` per attempt and re-pins to the revision the save answered with, which is what makes the ledger's replay reachable from a browser that lost a response; a `409` parks the vault's current bytes *and* the revision they came at on the conflict panel and offers exactly two explicit choices — overwrite (re-pin to that revision and resubmit the same text, the one place a revision moves without this page having read the vault) or discard mine (adopt both) — so neither outcome is a silent overwrite. `searchResult.Wikilink` (`internal/web/search.go`) exists for this page's `[[` completion and for nothing else: a client that wants to *write* a link cannot derive it from `Key` (folded) or `Title` (frontmatter), so the server publishes the exact-case target the graph resolves.
- **Portable settings write class**: `GET /api/settings`, `POST /api/settings/preview`, `POST /api/settings/apply` (`internal/web/settings_api.go`) are the saved-views class again — `s.propertyPreviews` under a `propertyPreviewSetting` kind, `commitPropertyPlan` with the pair pin from `s.pinnedConfig()`, `finishConfigWrite` rather than `finishPropertyWrite` because no note changed — and for the same reason: `brainnotes.toml` *is* the vault-root marker, so a mangled patch blocks every later write. What is new here is **which keys exist at all**. The list is built from `config.EditableSettings` alone, which is the portable half of `internal/config/ownership.go`'s table, so the eight machine-local keys (`fzf.args`, `open.editor`, `serve.addr`, `serve.open_browser`, `agent.command`, `agent.timeout_seconds`, `cockpit.agent_command`, `cockpit.agent_timeout_seconds`) are absent from the response rather than filtered by the client — an editor binary, a bind address or an agent command cannot reach a browser through this surface even on a hosted deployment, and a write cannot name one because the key resolves to no portable spec. `refuseShadowedSetting` covers the case ownership alone does not: misplacement is rejected by the loader only once the vault is **enrolled**, so in an unenrolled vault `brainnotes.local.toml` may legally assign a portable key and win, and writing the portable file would report a success the loader then ignores. That refusal is decided per key, before the patch, and the list carries `shadowed` so the browser disables the row and says why instead of discovering it at apply time. `planSettingsMutation` patches the portable source in memory and **re-decodes the layered pair**, so the projected values are the ones the loader would accept rather than the ones the patcher emitted — which is what makes the diff a person confirms the same thing the vault will hold. The apply keeps no plan of its own: the stored request is replanned and must reproduce the pinned generation *and* the identical `fileStates()`, or it is refused stale. Unset is a distinct op, not a set-to-empty: it removes the assignment so the key resolves to its default, and the two answer with different sentences. Type checking is the **server's**; the browser parses only what a control can produce (a bool from a checkbox, a whole number, one list item per line) and sends the declared kind along, so a rule like `capture.heading` being an ATX heading lives in the loader and nowhere else.
- **Templates write class**: `GET /api/templates`, `POST /api/templates/preview`, `POST /api/templates/apply` (`internal/web/templates_api.go`) are a preview-gated **file** write under `propertyPreviewTemplate`, and they are the one write class whose whole safety argument is about *where* the bytes land. The precondition is the **revision** — `vault.HashBytes` of the file the edit was planned against, pinned into the `vault.FileTxn` as `ExpectHash`, empty meaning "this file does not exist" so a create cannot silently overwrite, and required on a delete — while `configPin` pins both configuration layers, because the destination was computed from `templates.dir`. `templateDestination` is deliberately *not* `noteops.resolveSourceDestination`: that one refuses the templates directory, correctly, because a note written there is invisible to every query. The narrower policy a template needs is stated here — a flat file directly inside the configured directory, no separator, NUL, `.`/`..` or leading dot; an extension `template.Find` could resolve (the configured one, plus `.md`); a resolved path inside the vault that is exactly where it was asked for, so a symlink cannot redirect the write; and at most `maxTemplateBytes` (128 KiB). `templateDirRel` refuses a hidden or escaping `templates.dir` as a `CodeConflict` rather than writing into it, because `vaultgit.InScope` and `vaultsync.Portable` both judge a hidden component out of scope — a template there would have no undo history and no way to reach a peer, which is exactly the pair of properties this class exists to preserve; `templateDirStatusOf` reports both by asking those predicates rather than restating them, and the page states the answer. The name policy is the server's alone: the browser refuses only an empty name and otherwise lets the server decide, or it would eventually disagree with the vault about a legal name. `GET /api/templates` is read-only and lists only the files in that directory, so the directory being absent is an empty list — the first save creates it.
- **The settings page is a client of both classes, never a class of its own**: `GET /settings` (`internal/web/settings_page.go`, `templates/settings.html`, `static_src/settings-*.ts` + `templates-*.ts`) writes nothing and renders **no setting value and no template byte**. It carries the two endpoint names and the CSRF token; both panels fetch their own state, so the page and the API cannot report different things. Neither panel auto-chains preview into apply — unlike the saved-views create case, both a setting write and a template write always show the diff and wait for a confirmation, and a confirmation with no receipt in hand issues nothing. `/settings`, `/api/settings` and `/api/templates` are all absent from `replicaReadPath`, so a replica answers `403` for the page and for both APIs, and the navigation link is gated on the same condition: a mode that refuses the page must not link to it. The page mounts the history panel because both classes are journaled and undoable and the template panel's own delete message points a person at it.
- **Pin write class**: `/api/pins/set`, `/api/pins/remove`, and `/api/pins/reorder` (`internal/web/pins_api.go`) are the `/api/notes/frontmatter/set` class (`internal/web/manage.go:223`) and share its prologue verbatim through `beginPinnedNotesRequest`: CSRF, writability gate, fresh snapshot, resolved note. `/api/properties/value` cannot be reused for a pin because its replace op hard-fails when the property is absent, which is exactly the first-pin case. Every rank is written with an explicit `type=float`, so pinning works in a vault whose `brainnotes.toml` declares no `[frontmatter.properties.pinned]` block. Reorder is the one exception to "one note": a rank-exhaustion renormalize rewrites the whole list through `noteops.SetFrontmatterAtomic` in a single transaction, routed on `plan.Renormalized || len(writes) > 1`, because half a renumbering is a scrambled order rather than a partial one. The browser posts note keys and never a rank — the server takes the midpoint of the neighbouring ranks as they are on disk — so a stale page cannot write an order it computed against a list that has since moved. Neighbour resolution and pin planning fail differently and must stay documented that way: a neighbour key that names no note in the vault fails in `noteops.ResolveExistingRouteNote` as `CodeNotFound` (404), while a neighbour that still exists but is no longer pinned, or a pair that no longer straddles one gap, fails in `pins.PlanMove` (`ErrNeighborMissing`/`ErrStaleGap`) as `CodeConflict` (409). Validating the gap against a fresh snapshot is not enough on its own, because two reorders of *different* targets into one gap modify neither neighbour and would both commit the same midpoint; `pinnedListRequirements` therefore turns the validated list into commit preconditions, adding a `noteops.WithFrontmatterRequire(ExpectHash(...))` for every pin the plan does not itself write. Required paths are never locked, staged, or journaled and are verified in `FileTxn.stage` before `journaler.Capture`, so the losing reorder returns 409 with no note change and no journal entry. `/api/pins/set` and `/api/pins/remove` deliberately carry no such requirements — they do not interpolate between existing ranks.
