# Web write classes

Companion to `CLAUDE.md`; read before adding or changing any mutating web API route.

Every class below is reached only after the serving mode has allowed the request.
Which modes may write at all, which routes are refused at the guard, and where
the process-launch and media boundaries live are in
[Serving modes and capabilities](serving-modes.md) — read that first when adding
a route, and ask `s.caps` rather than branching on an option flag.

Standalone creation at `GET /new` uses `POST /api/notes/new` with `title`,
optional `folder`, and required `save_id`. It is a client of the raw Markdown
source write class: `noteops.NewNoteSource` prepares title frontmatter and
`applySourceSave` applies the existing configuration-pinned, journaled transaction.
`ExclusiveCreate` refuses an existing destination even when its bytes match;
only a recorded replay of the same save ID can succeed again. Local and hosted
modes allow the page and API; read-only replicas refuse both. A post-write error
carries the created note's key and relative path, so the form preserves the
warning and offers the editor without issuing another creation request.

- **Read-only query routes**: `GET /api/query/validate` and `GET /api/query/completions` (`internal/web/query_api.go`) are *not* a write class and deliberately carry no CSRF token — they are the `/api/facets` shape: re-check `r.URL.Path` exactly and 404 anything below it, reject a non-`GET` method with `Allow: GET` and 405, read one snapshot, and write nothing. Validate answers `200` with `ok:false` for a query that does not parse or compile, because a half-typed expression is not a client error; only a malformed `pos` is a `400`. It compiles through `compileFilterExpr`, the same door `/api/search?expr=` uses, so validate accepts a query exactly when search would. Both routes speak **UTF-16 code-unit offsets** in every position they emit or accept (`error.start`/`end`/`column`, `pos`, `replace`), converted server-side by `internal/web/utf16.go`: the browser's `selectionStart`/`setSelectionRange` count code units, so a byte offset would drift a caret or a highlight by one per non-ASCII character in an NFC vault full of accented titles. A new read-only route belongs in this class; do not give it a token, and do not let it emit a byte offset a caret will consume.
- **Saved-views write class**: `POST /api/views/preview` then `POST /api/views/apply` (`internal/web/views_api.go`) are the `/api/properties/schema/{preview,apply}` class, reusing `s.propertyPreviews` under a `propertyPreviewView` kind so receipt expiry, one-use semantics, and the file-digest check come free. The class choice is not a judgement call: `brainnotes.toml` *is* the vault-root marker, a mangled patch is a vault-wide failure that blocks every later write through `ensureConfigWritable`, and `PatchViews`'s upsert replaces a whole `[[views]]` block, destroying any comment inside it. **The create case still auto-chains preview into apply** — a view that does not exist yet has no block to destroy, so the client fires both calls and then shows the rendered diff as a receipt; overwrite, rename, and delete must have the diff confirmed before apply. The create receipt is a *post-success record*, published only after the apply landed and modelled as a `SavedViewCreateReceipt` that carries the diff and the name but no preview ID, so the consumed one-use receipt is structurally unreachable from it; it renders into the same block an overwrite confirms in, tagged `data-saved-views-diff-role="receipt"` with the confirm button hidden, and a confirmation with only a create receipt in hand is refused like any other unbacked confirmation. That is one write class with two client behaviours, driven by the `created` flag the preview returns, not a second class. `GET /api/views` is read-only and belongs to the `/api/facets` class above; it answers from `config.Config` alone, with no vault walk and no graph, and reports a view whose query stopped compiling as `enabled:false` plus a `detail` rather than dropping it. Applying goes through `commitPropertyPlan` with the pin from `s.pinnedConfig()`, so `brainnotes.toml`'s three independent writers (`/api/properties/apply`, `/api/properties/schema/apply`, `/api/views/apply`) cannot corrupt each other — `configPin` makes the loser a 409, which `viewsWriteError` surfaces as "config changed, re-check the diff" wherever it fires (receipt digests, replan, or the transaction precondition) rather than as a generic failure. The pin is a **pair**, one `configLayerPin` per layer, because the patch these writers computed was decided by reading both files: the portable layer carries `ExpectHash`, and `brainnotes.local.toml` carries `ExpectHash` when it is present and `ExpectMissing` when it is not, so an overlay *appearing* between the plan and the commit is a conflict rather than a second source nothing read. Absence is a precondition here, not a missing one — an overlay is what would shadow the key just written and turn a reported success into a no-op. A view write finishes through `finishConfigWrite`, not `finishPropertyWrite`: no note changed, so the unconditional `s.state.invalidate()` is pointless. `[views]` is deliberately **not** excluded from the configuration generation — a generation meaning "some parts of the config changed" would be a footgun for every pin that compares it — so a view save does pay one `properties.Build` and one recall corpus rebuild, which is accepted.
- **Property intelligence cache**: `internal/web`'s `vaultState` caches one `*properties.Index` keyed on the snapshot serial plus the configuration generation, so a note reload or a configuration reload — either layer — rebuilds it and nothing else does. The cached index is shared and must stay immutable — `properties.Build` copies what it needs from notes and never mutates its inputs.
- **Property workbench save model**: `/api/properties/value` is the workbench's only unpreviewed write, and it is deliberately narrow — one note, one property, either a whole-value replacement or a single list addition, gated on the caller echoing the note's current hash. It is *not* the server's only unpreviewed property write: `/api/notes/frontmatter/set`, `/api/notes/frontmatter/unset`, and the three `/api/pins/*` routes are the same single-note single-property class, differing only in that they rely on the write's own revision precondition instead of a client-echoed hash. Everything else (unset, list removal, multi-note changes, bulk value replacement, property rename, repair, and every schema edit) must go through `/api/properties/preview` then `/api/properties/apply`. Property receipts carry the configuration generation as well as the note hashes, so a configuration change invalidates outstanding note receipts rather than letting a plan built against old declarations apply. The generation tracks the **composite** fingerprint of both layers, so an edit to `brainnotes.local.toml` alone — including its appearance or removal, which are distinct from an empty one — invalidates receipts exactly as a portable edit does. A fatal blocker (`parse_error`, `not_found`, `key_conflict`, `config_conflict`) suppresses the receipt entirely so the whole selection is refused; `repair_skip` is advisory and leaves the receipt intact. When adding a property action, decide which side of this line it falls on rather than adding a third path.
- **Unpreviewed web write classes**: `/api/capture` is the deliberately-unpreviewed *additive* body write, and `/api/source/{save,create}` the deliberately-unpreviewed *whole-file* one (the other unpreviewed Markdown routes — `/api/properties/value`, `/api/notes/frontmatter/set`, `/api/notes/frontmatter/unset`, `/api/pins/*` — write properties). Capture is narrow for different reasons: one note, strictly additive, so it cannot destroy existing bytes, and a confirm step would defeat the entire point of a quick-capture box. Its safety comes from the `vault.FileTxn` precondition pinning the revision the append was planned against — not from a client-echoed hash, because the box never loaded the note and has no hash to send. A conflict surviving `ApplyCapture`'s 3 internal replans returns `409`; the browser resubmits. Browser captures include `capture_id`; `ApplyCapture` checks `.bnotes/captures/<digest>.json` before planning and writes the receipt in the append's own transaction. Concurrent retries use `ExpectMissing` on that receipt and re-read after a conflict. Receipts bind an ID to the submitted text digest and retain the original destination and timestamp without storing thought text. They are private, outside content Git scope, and journaled with the append, so undo removes both. Receipts do not expire: unlike a whole-file save, an append cannot use revision convergence after an expired receipt. Corrupt receipts refuse retries. Unkeyed CLI captures retain their existing behavior. The CLI keeps the canonical `--dry-run` preview, so the unpreviewed path is web-only. `POST /api/related/item` is a distinct unpreviewed, non-Markdown class: it is CSRF-protected, resolves both note identities through the current graph, and writes only serialized runtime state in `<vault>/.bnotes/recall.json`, never Markdown or the undo journal. Do not invent a further write class: a new Markdown or configuration write still belongs on one of the two file-write sides — preview-gated, or narrow with a precondition that refuses a stale plan — while runtime-state writes must remain confined to a documented sidecar boundary with route-appropriate validation.
- **Raw Markdown source write class**: `GET /api/source`, `POST /api/source/preview`, `POST /api/source/save`, `POST /api/source/create` (`internal/web/source_api.go` over `internal/noteops/source.go` + `source_save.go`) are a whole-note Markdown write, and they sit on the **narrow-with-a-precondition** side of the two file-write sides named by *Unpreviewed web write classes* above, not the preview-gated one. `/api/source/preview` is a **renderer, not a gate**: it takes the bytes in the editor and answers rendered HTML so a person can see what they typed, it holds no receipt, and a save neither needs nor consults one. Nothing about a save is validated by having previewed — the preview and the save each call `noteops.ValidateSource` themselves, and a client that never previews is not a client that skipped a check. A receipt would be the wrong instrument anyway: a raw editor's diff is the two versions of the file, which the client already has, and a one-use token would only make a slow typist's save expire. The precondition is the **revision** — `vault.HashBytes` of the bytes on disk, handed out by the read and required back by the save — pinned into the `vault.FileTxn` as `ExpectHash`, so an edit planned against a version somebody else has replaced is a `409` carrying the *current* content and revision rather than an overwrite. That expectation is derived from what the save itself just read, never from what the client sent, so the message and the guarantee cannot disagree. **Unlike a capture this never replans**: an append is commutative and a whole-note save is not, so a conflict is the person's to resolve and retrying would silently discard the other writer. The six ways submitted bytes could vanish are each answered, in a fixed order — unstorable content first (a properties block that is opened *and closed* whose YAML does not parse, a NUL byte, over `noteops.MaxSourceBytes`), so nothing downstream can turn it into a success; then a recorded outcome; then convergence; then the revision comparison. `ValidateSource` refuses only what could not be stored **as a note**, so a `---` line with no closing delimiter is accepted and written verbatim: `frontmatter.Parse` reads it as a body beginning with a horizontal rule, and a surface that refused it would be the only one in the vault that cannot save a note the vault itself serves. A **stale** revision is a typed `*noteops.SourceRevisionError`. A **duplicate** or **lost-response** resubmission is answered from the idempotency ledger under `.bnotes/source-saves/`, one file per `save_id`, written inside the *same* transaction as the note and journaled with it, so an undone save is re-submittable; the directory is deliberately outside `vaultgit.InScope`, so the record never becomes commit content, and `pruneSourceSaveLedger` holds the one annotated `os.Remove` on this surface. A reused id carrying *different* content is a conflict, never a replay. A **no-op** — the note already holds exactly these bytes — is a success with `changed:false` and the revision the note is actually at, which is also how a repeated create answers, because a destination holding the submitted bytes is the create that already happened. A **snapshot failure** returns a non-nil result *beside* the error: the bytes are on disk, so `writeSourceSaveError` answers `500 snapshot_failed` with the landed revision and `changed:true`, and a client told only "500" must not resubmit against a revision this save already replaced. `/api/source/create` is the only route on this surface that names a **brand-new** path, so it owes the location rule the synthesis apply owes: `resolveSourceDestination` refuses a destination `vault.Walk` would never visit — any hidden component (`.bnotes/`, `.git/`), the configured `templates.dir`, and anything under the `ignore` list — as `403`, because a note written there is on disk and in no index, no graph, no search and no query, and under `.bnotes/` it is also outside `vaultgit.InScope`, where the save's own snapshot commits nothing while the answer reports a revision. Both losses are invisible from the client's side, which is why the refusal is part of this write class rather than a nicety. It is decided from the *configuration*, so the read path takes `s.config()` and the write path `s.pinnedConfig()` — the same bytes the transaction verifies at the commit boundary. `brainnotes.toml` is pinned through `sourceConfigPinOptions(s.pinnedConfig())` like every other note write, and the state cache is invalidated whenever a result came back at all, landed or not. All four routes are absent from read-only's POST allowlist and from `replicaReadPath`, so a replica refuses every one of them. Body bounds are in [Serving modes](serving-modes.md): the three write routes widen to `sourceRequestBodyLimit` in `routeBodyLimit` and re-apply it in `requireManagementPost`.
- **Attachment staging write class**: `POST /api/attachments/upload` and `POST /api/attachments/cancel` (`internal/web/attachments_api.go` over `internal/attachments`) are the one write class whose bytes do **not** become vault content when the request succeeds. An upload streams into private staging under `.bnotes/uploads/`, and only the save that references it puts anything in the vault — so this class is a *staging* surface with a *commit* that belongs to the raw Markdown source class above. `/api/attachments/upload` is the only mutating route on any surface that cannot use `requireManagementPost`: the body **is** the file, so `ParseForm` would consume it, and `requireStreamedAttachmentPost` restates the same preamble without the parse — exact route, POST only, `http.MaxBytesReader` at `config.MaxAttachmentFileBytes`, the CSRF token from the `X-BN-CSRF` **header** (which `requestCSRFToken` already prefers and is the only form available to a request whose body is not a form), then `ensureConfigWritable`. The metadata — the owner and the client's filename — rides in the query string, and a multipart form is deliberately not used: it would mean buffering or re-spooling megabytes this process has no reason to hold. **Two bounds in series**, and they are different numbers for a reason: the transport refuses a body no vault could accept before a byte is written, and `Store.Stage` refuses one *this* vault does not accept while streaming into a private file it then deletes, because `[attachments].max_file_bytes` is configurable downward from the ceiling and never upward. Both refusals are a `400` — `attachmentError` classifies `*http.MaxBytesError` alongside the store's `ErrTooLarge`, or a vault that left its limit at the ceiling would be told "server error" for a file that is merely too big. Nothing in the upload's answer can be turned into a request for staged content, because **staging is not served at all**: `.bnotes/uploads/` is a dot-path, and `privateMediaPath` refuses it under its own name and through any symlink resolving into it. The **destination is claimed at staging time, not at commit time** (`Store.reserve`, keyed by `vaultsync.CollisionKey` so a case-only or normalization-only clash is one name): a transaction can only refuse a destination that is taken, and refusing is the wrong answer to two drafts uploading `photo.png` — claiming while both are private turns that into two destinations with nothing left for the commit to negotiate. The **owner** is an opaque client-minted string that scopes a cancel and a commit; it never becomes a path component, and `ErrNotFound` covers both "no such upload" and "not yours" deliberately, so the difference is not a way to ask whether somebody else's id exists. A save names its uploads with repeated `attachment` fields plus one `owner`, and `resolveSaveAttachments` **carries** an id the store cannot resolve rather than refusing it, because the save whose staging is gone is very often the save that already succeeded: `noteops` refuses `UnresolvedAttachments` *after* the `save_id` ledger has had its chance to replay, which is the only place a retry and a save naming a file nobody staged can be told apart. After a result comes back, `forgetCommittedAttachments` drops only the staged copies the **result** names — a replayed save answers from an earlier call's record, and discarding an upload on the strength of somebody else's outcome would delete bytes no note holds — and its failures are not reported, because the bytes are in the vault and a leftover staging file is disk the sweep collects. Abandoned staging is collected **once per server start and again at the start of each upload** (`Store.Sweep` under `vault.TryLockPath`, so a second sweeper stands down instantly), and the sweep's failure is **dropped, never returned**: it is housekeeping over files belonging to other requests, so an artifact nobody can remove says nothing about the upload in hand — and since the upload route is where the sweep runs, returning it would let the first un-removable file refuse every upload the vault ever receives again. The startup sweep is what keeps the arrears bounded at one session: the person whose browser died mid-upload is exactly the person who may never upload again, and staging is outside `vaultgit.InScope` and outside `vault.Walk`, so nothing else would ever report it. A read-only server does not sweep, because sweeping is a write. Neither route is in read-only's POST allowlist, which is the right default twice over: a replica accepts no writes, and staging no save could ever commit is disk somebody else pays for. A cancel is a **courtesy, not a guarantee** — an upload nobody cancels is swept, and one already gone answers exactly like a successful cancel, because "it is not in staging" is what the caller asked for either way.
- **The raw editor page is a client of that class, never a class of its own**: `GET /edit?key=<key>` (`internal/web/editor_page.go`, `templates/editor.html`, `static_src/source-editor*.ts`) writes nothing and renders **no note bytes**. The template carries the key, the route, the CSRF token and `noteops.MaxSourceBytes`, and the source itself is fetched from `/api/source` after the page loads — deliberately, because rendering the content into the template would make the page two reads (the handler's snapshot and the API's later read of the file) with no revision tying them together, so a save could be planned against bytes the editor never showed anybody. The page resolves its note exactly once, through the shared snapshot like `/synthesize`, and is absent from `replicaReadPath` along with the four API routes it calls: a replica refuses the page rather than serving an editor whose every save is refused. The preview pane posts to `/api/source/preview` and injects the HTML the server answers with, because `internal/web/markdown.go` is the vault's **only** Markdown renderer and a browser-side one would be a second answer to what a note looks like — `internal/web/e2e/editor.spec.js` asserts that parity in a real browser, against the shipped bundle. Out-of-order previews are the client's own hazard and are answered in `static_src/source-preview.ts`: a monotonic sequence, a response applied only when it is the newest yet applied, and a "rendering" state that clears only for the newest response *issued*. The editor sends `save_id` per attempt and re-pins to the revision the save answered with, which is what makes the ledger's replay reachable from a browser that lost a response; a `409` parks the vault's current bytes *and* the revision they came at on the conflict panel and offers exactly two explicit choices — overwrite (re-pin to that revision and resubmit the same text, the one place a revision moves without this page having read the vault) or discard mine (adopt both) — so neither outcome is a silent overwrite. `searchResult.Wikilink` (`internal/web/search.go`) exists for this page's `[[` completion and for nothing else: a client that wants to *write* a link cannot derive it from `Key` (folded) or `Title` (frontmatter), so the server publishes the exact-case target the graph resolves.
- **Portable settings write class**: `GET /api/settings`, `POST /api/settings/preview`, `POST /api/settings/apply` (`internal/web/settings_api.go`) are the saved-views class again — `s.propertyPreviews` under a `propertyPreviewSetting` kind, `commitPropertyPlan` with the pair pin from `s.pinnedConfig()`, `finishConfigWrite` rather than `finishPropertyWrite` because no note changed — and for the same reason: `brainnotes.toml` *is* the vault-root marker, so a mangled patch blocks every later write. What is new here is **which keys exist at all**. The list is built from `config.EditableSettings` alone, which is the portable half of `internal/config/ownership.go`'s table, so the eight machine-local keys (`fzf.args`, `open.editor`, `serve.addr`, `serve.open_browser`, `agent.command`, `agent.timeout_seconds`, `cockpit.agent_command`, `cockpit.agent_timeout_seconds`) are absent from the response rather than filtered by the client — an editor binary, a bind address or an agent command cannot reach a browser through this surface even on a hosted deployment, and a write cannot name one because the key resolves to no portable spec. `refuseShadowedSetting` covers the case ownership alone does not: misplacement is rejected by the loader only once the vault is **enrolled**, so in an unenrolled vault `brainnotes.local.toml` may legally assign a portable key and win, and writing the portable file would report a success the loader then ignores. That refusal is decided per key, before the patch, and the list carries `shadowed` so the browser disables the row and says why instead of discovering it at apply time. `planSettingsMutation` patches the portable source in memory and **re-decodes the layered pair**, so the projected values are the ones the loader would accept rather than the ones the patcher emitted — which is what makes the diff a person confirms the same thing the vault will hold. The apply keeps no plan of its own: the stored request is replanned and must reproduce the pinned generation *and* the identical `fileStates()`, or it is refused stale. Unset is a distinct op, not a set-to-empty: it removes the assignment so the key resolves to its default, and the two answer with different sentences. Type checking is the **server's**; the browser parses only what a control can produce (a bool from a checkbox, a whole number, one list item per line) and sends the declared kind along, so a rule like `capture.heading` being an ATX heading lives in the loader and nowhere else.
- **Templates write class**: `GET /api/templates`, `POST /api/templates/preview`, `POST /api/templates/apply` (`internal/web/templates_api.go`, with planning and commit in `templates_api_plan.go` and destination and listing policy in `templates_api_files.go`) are a preview-gated **file** write under `propertyPreviewTemplate`, and they are the one write class whose whole safety argument is about *where* the bytes land. The precondition is the **revision** — `vault.HashBytes` of the file the edit was planned against, pinned into the `vault.FileTxn` as `ExpectHash`, empty meaning "this file does not exist" so a create cannot silently overwrite, and required on a delete — while `configPin` pins both configuration layers, because the destination was computed from `templates.dir`. `templateDestination` is deliberately *not* `noteops.resolveSourceDestination`: that one refuses the templates directory, correctly, because a note written there is invisible to every query. The narrower policy a template needs is stated here — a flat file directly inside the configured directory, no separator, NUL, `.`/`..` or leading dot; an extension `template.Find` could resolve (the configured one, plus `.md`); a resolved path inside the vault that is exactly where it was asked for, so a symlink cannot redirect the write; and at most `maxTemplateBytes` (128 KiB). `templateDirRel` refuses a hidden or escaping `templates.dir` as a `CodeConflict` rather than writing into it, because `vaultgit.InScope` and `vaultsync.Portable` both judge a hidden component out of scope — a template there would have no undo history and no way to reach a peer, which is exactly the pair of properties this class exists to preserve; `templateDirStatusOf` reports both by asking those predicates rather than restating them, and the page states the answer. The name policy is the server's alone: the browser refuses only an empty name and otherwise lets the server decide, or it would eventually disagree with the vault about a legal name. `GET /api/templates` is read-only and lists only the files in that directory, so the directory being absent is an empty list — the first save creates it.
- **The settings page is a client of both classes, never a class of its own**: `GET /settings` (`internal/web/settings_page.go`, `templates/settings.html`, `static_src/settings-*.ts` + `templates-*.ts`) writes nothing and renders **no setting value and no template byte**. It carries the two endpoint names and the CSRF token; both panels fetch their own state, so the page and the API cannot report different things. Neither panel auto-chains preview into apply — unlike the saved-views create case, both a setting write and a template write always show the diff and wait for a confirmation, and a confirmation with no receipt in hand issues nothing. `/settings`, `/api/settings` and `/api/templates` are all absent from `replicaReadPath`, so a replica answers `403` for the page and for both APIs, and the navigation link is gated on the same condition: a mode that refuses the page must not link to it. The page mounts the history panel because both classes are journaled and undoable and the template panel's own delete message points a person at it.
- **Sync resolution write class**: `POST /api/sync/conflicts/preview` then `POST /api/sync/conflicts/resolve` (`internal/web/sync_resolve.go`, `sync_resolve_view.go`, `sync_resolve_errors.go` over `internal/vaultimport`'s `Preview`/`Resolve`) are the **third** write class, and what makes them a class of their own is the precondition: the receipt carries the **plan**, not the request. The two preview-gated classes above both replan at apply time and compare against pinned file digests, which is what stops an apply writing something the preview never showed. That is the wrong instrument here, twice over. `vaultimport.Resolve` re-asks *every* fact the plan was built on — the hold, each `ConflictKind`, both branches, and this vault's own current version of each path, which is the one that moves — refusing as `ErrStalePreview` with nothing written and then pinning each step again as a `vault.FileExpectation` inside the transaction; a replan in this layer would answer a weaker question a second time. And it could not reproduce the plan anyway: a manual merge exists only in the plan its author composed, staged beside it, so a serialized receipt would have to re-read a version nobody can re-read. The receipt is therefore `s.propertyPreviews` under a `propertyPreviewResolution` kind — one-use, kind-separated, TTL-bounded, so a replay and a cross-endpoint redemption are refused exactly as they are for a property receipt — and `syncResolutionRecord` also carries the `PackageDir`, which `Resolve` checks against the plan, so a receipt cannot be redeemed against a different package. **Completeness is this surface's rule, not the engine's**: `Choices.Default` is right for a command line where somebody says "accept everything incoming" in one word, and wrong for a page showing every contested path with both versions beside it, so a request that does not name a contested path is refused by name (`CodeInvalidRequest`) rather than inheriting a destructive decision for a path nobody looked at. A merge is held to what this page can have shown — present (a `*string`, because an empty merge is a decision somebody can mean and is not the same as supplying none), valid UTF-8, and within `syncVersionTextLimit`, the same bound the review route reads a version under. The **partial outcome is reported rather than smoothed over**, and it is the whole reason this class has its own error mapping: a resolution is two commits, so it can apply the peer's change and fail to record the decision, leaving the vault holding the version the person decided *against* — `syncPartialResolutionError(resolution, plan, err, root)` answers that non-nil-`Resolution`-beside-an-error with a sentence about what is durable, never a generic 500 and never a success — and it takes the **plan** as well as the error because an empty `Resolution.JournalEntry` is **five** states rather than one, and only the two together say which. A plan that revises nothing (`!Plan.Revises()`, which accepting the other replica's version is) never owed a second commit, so nothing is outstanding; a plan that does revise and got no entry has a durable promise `finishResolutions` makes on the next pass; and one whose revision failed on an `unkeepable` sentinel (`vaultimport.IsUnrecordableDecision` — `ErrConflict`, `ErrResolutionUnavailable`, `ErrCorruptState`) has a promise no pass will keep: `Resolve` itself leaves it on disk, and the next `finishResolutions` — the pass that runs ahead of every import, drain and resolution, and would otherwise retry it forever — abandons it instead, so that second commit is never made and this vault is left holding the version somebody decided against. The web sentence says "it will not be tried again" rather than "it was dropped" for exactly that reason: at the moment the failure is answered the promise is still recorded. The other two are failures no journal entry is ever written for, and `syncPartialOutcome` asks them **first**: a `*noteops.SnapshotError` means the change and its undo manifest are both durable and the content history is not (`noteops.Finalize` writes the manifest *before* it snapshots), and it is answered under its own `Blocked` field rather than under its type, because that field is `vaultgit.Blocks` of the engine's failure and only five kinds answer yes to it — `KindBlocked`, which is how an already-latched vault arrives here, plus the four `blocking()` kinds that latch on their way out: a blocked one refuses the very write that would keep the promise, so the promise sentence is exactly wrong there, while an unlatched one — in practice a snapshot a lock somebody else was holding refused — leaves a finalized entry the next pass re-snapshots (`revision.commit`'s first case), so saying this vault refuses further changes would send somebody to clear a `blocked.json` that is not there; and `ErrStrandedImport` means a half-made revision could not be taken back out, which stops **every** later import until a person resolves it, so no pass will finish it either. Those five are told apart because they are the difference between waiting for a commit that is coming, waiting for one that is not, waiting for one that was never owed, and two states where the vault needs a person before anything else moves. The promise that survives is answered **two ways**, and what splits it is the failure rather than the plan, so this is a sixth sentence and not a sixth state: the split is the same fact the snapshot's `Blocked` field carries, one step earlier. A `vaultgit.IsBlocked` failure with no entry is the revision's own `noteops.BeginOperation` preflight refused after the application committed, so there is no snapshot failure to read the latch off, the promise is still on disk, and "a later pass finishes it" is wrong for exactly the reason it is wrong above — the pass is refused the same write, and `finishResolutions` running ahead of every import means nothing else is applied either. **One classification serves both answers**: `syncResolutionCode` asks the engine's **decision** sentinels first and separately from its write failures (`ErrStalePreview` → `preview_stale`, `ErrNoConflict`/`ErrImportBusy`/`ErrConflict` → `409`, `ErrResolutionUnavailable` → `400`, `ErrStrandedImport`/`ErrCorruptState` → `internal_error`), because those are answers about the decision that a client retries or re-reads for, then falls through to `syncWriteCode`, which classifies the writes in `internal/vaultimport`'s own order — snapshot failure before busy, blocked before the rollback failure, and that before the conflict nested inside it. `syncResolveError` and `syncPartialResolutionError` both route through it, so a sentinel cannot mean one thing when the call came back empty-handed and another when a resolution came back beside it — `ErrConflict` is why that matters: `syncWriteCode` alone would call a decision the vault refused an internal error. Three of those codes are **not** `safety_error`, and deliberately: `CodeSafety` is documented as the engine refusing *before it changed anything*, so it is the wrong answer for every state where something landed. A stranded import is the negation of it in each part (the package is applied, the peer has been told to drop its copy, the revision is half recorded), a rollback or recovery failure is the one state where content is provably somewhere nobody asked for it — which is also what `internal/noteops`' own two classifiers and the property class answer for those predicates — and on the **partial** path no write failure may answer `safety_error` at all, which is `syncPartialResolutionCode`'s whole job: a resolution that came back applied the other replica's version, so even a genuinely latched block (`vaultgit.IsBlocked`, which the revision's own `noteops.BeginOperation` preflight can raise *after* the application committed) becomes `internal_error` there. What gets a person to the repair on this surface is the sentence, not the code. A success reports `acknowledged` from `Resolution.Applied.Receipt`, so "the peer has not been told yet and will keep offering it" is said rather than implied, and `abandoned` names earlier promises this call's recovery pass dropped, with each reason, because after the pass the vault no longer remembers them and the person reading the page is usually the one whose earlier attempt was dropped. `syncResolvedViewOf` takes the plan for the same reason the failure answer does: a *success* with no journal entry is two states, and "it needed nothing revised on top of it" is true only of `!Plan.Revises()` — a revising plan that came back with no entry had every step already satisfied on disk (`revision.commit` answers `("", nil)`, which is what a re-drive of a rolled-forward promise finds), and denying the revision this vault is holding would send somebody looking for a change they already have. Both of those sentences are claims about a plan, so `syncResolvedSummary` has a third arm for not having one — a state this surface cannot produce, since the receipt carries the plan it was minted for — which claims only what the resolution itself reports, exactly as the failure side answers an absent plan with the sentence that tells nobody to stop looking. Both routes go through `requirePropertyPost` (exact route, POST only, CSRF, `writeManagementError`) and both are absent from `replicaReadPath`; `finishPropertyWrite` runs **unconditionally** after `Resolve` returns, because a nil `Resolution` does not mean nothing landed — an application that failed after committing has its own in-process recovery, which can finish the whole resolution on the way out and leaves the error with no `Resolution` to carry, so gating the reload on one would serve the rejected version from cache.
- **The sync page is a client of that class, never a class of its own**: `GET /sync` (`internal/web/sync_page.go`, `templates/sync.html`, `static_src/sync*.ts`) writes nothing and renders **no status, no version and no decision**. It carries the four endpoint names, the CSRF token, and the vault identity — the same identity the editor page publishes, because a merge somebody is composing is the one text on this page that exists nowhere else and must be kept under a key no other vault served by this origin can read. Status and conflicts are fetched from `GET /api/sync/status` and `GET /api/sync/conflicts` (read-only, `requireSyncGet`, the `/api/facets` shape), deliberately rather than rendered into the template: what this page reports is how far behind the vault is, and a state rendered once into HTML is wrong by the time somebody reads it. Nothing auto-chains — a decision is planned, the plan is read, and only then is it applied — and a confirmation with no receipt in hand issues nothing. `registerSyncRoutes` groups the page with its APIs because the grouping that matters here is the capability: a replica refuses every route in that function except the status one, which reports the replica's own freshness rather than somebody else's vault (`replicaSyncStatus`), and the navigation link is gated on the same condition.
- **Pin write class**: `/api/pins/set`, `/api/pins/remove`, and `/api/pins/reorder` (`internal/web/pins_api.go`) are the `/api/notes/frontmatter/set` class (`internal/web/manage.go:223`) and share its prologue verbatim through `beginPinnedNotesRequest`: CSRF, writability gate, fresh snapshot, resolved note. `/api/properties/value` cannot be reused for a pin because its replace op hard-fails when the property is absent, which is exactly the first-pin case. Every rank is written with an explicit `type=float`, so pinning works in a vault whose `brainnotes.toml` declares no `[frontmatter.properties.pinned]` block. Reorder is the one exception to "one note": a rank-exhaustion renormalize rewrites the whole list through `noteops.SetFrontmatterAtomic` in a single transaction, routed on `plan.Renormalized || len(writes) > 1`, because half a renumbering is a scrambled order rather than a partial one. The browser posts note keys and never a rank — the server takes the midpoint of the neighbouring ranks as they are on disk — so a stale page cannot write an order it computed against a list that has since moved. Neighbour resolution and pin planning fail differently and must stay documented that way: a neighbour key that names no note in the vault fails in `noteops.ResolveExistingRouteNote` as `CodeNotFound` (404), while a neighbour that still exists but is no longer pinned, or a pair that no longer straddles one gap, fails in `pins.PlanMove` (`ErrNeighborMissing`/`ErrStaleGap`) as `CodeConflict` (409). Validating the gap against a fresh snapshot is not enough on its own, because two reorders of *different* targets into one gap modify neither neighbour and would both commit the same midpoint; `pinnedListRequirements` therefore turns the validated list into commit preconditions, adding a `noteops.WithFrontmatterRequire(ExpectHash(...))` for every pin the plan does not itself write. Required paths are never locked, staged, or journaled and are verified in `FileTxn.stage` before `journaler.Capture`, so the losing reorder returns 409 with no note change and no journal entry. `/api/pins/set` and `/api/pins/remove` deliberately carry no such requirements — they do not interpolate between existing ranks.
- **History and recovery write class**: `GET /api/history`, `POST /api/history/preview`, `POST /api/undo` (`internal/web/history.go`, `history_undo.go`, `history_response.go`, `history_restore.go`, `history_origin.go`, registered together in `history_page.go`) are the fourth preview-gated class, and the only one whose *subject* is an earlier version of the vault rather than the current one. The list route is read-only and carries no CSRF token, for the reason the query routes give; what makes it part of this class is that it is the only way to find the entry the other two act on, so **a filter that silently did nothing would be the failure this surface must not have** — a person looking for the version they want must never be shown a list that hides it, or a list they believe is narrower than it is. `parseHistoryQuery` therefore refuses an unparseable limit, a negative offset, and an unknown origin or class rather than defaulting, since a dropped filter answers a narrower question with the whole journal and its reply is indistinguishable from a filter that matched everything; `Total` is the match count *before* the page is taken, so a client can say which slice of what it is showing; the `origins`/`classes` vocabulary is always the **full** table rather than the values this page happened to contain, or a filter would lose the option that empties it and could never be undone; and the **unreadable entries are neither filtered nor paged** — a manifest that will not parse has no command and no paths, so no filter can be true of it, which is why `warning_count` is the journal's own total and not the length of the capped list. The origin is a *reading* of the recorded command (`historyOriginForCommand`, ordered most-specific-first so `bn web undo` is a restore and not a browser save) and is published **beside** the raw command, never instead of it, so a reader who doubts the label can check it. `/api/history/preview` writes nothing, takes no lock and reads no snapshot — the state somebody is most likely to be in when they come looking for a recovery is a vault that cannot currently be written — and it mints the receipt under `propertyPreviewRestore`, one-use, TTL-bounded and kind-separated exactly as the property and resolution receipts are. What that receipt authorizes is **not** "restore this entry" but "restore this entry over exactly these pieces of newer work": it pins the entry identity, the sorted set of paths the restore writes, the sorted set of paths that would be overwritten, a digest of the current bytes at every written path, and the configuration generation — since either configuration file can itself be restored, which is why all three routes `reloadConfig` before answering — and `/api/undo` does it *before the receipt is judged* rather than after the restore, or the pinned generation would be compared against a value this process happened to be holding. Those digests are taken by `historyRestoreDigest`, which deliberately parts company with `propertyFileDigest` by **not** failing on a path that is no longer a regular file: a configuration write is planned against files the server manages, so a changed kind is a surprise worth refusing on, while a restore is aimed at whatever the vault has become, and refusing to *describe* a note replaced by a directory would make the one entry somebody needs impossible to preview and so impossible to recover — the kind is recorded as the digest instead, and a change of kind is caught by the same comparison a change of bytes is. The path sets are compared as **sets, not counts**, because a conflict that vanished and a different one that appeared keeps the count identical while changing entirely what was agreed to. `/api/undo` is the write, and the rule this class adds is that **force needs a preview**. Without force the precondition is the journal's own and needs nothing from this layer: `planRestore` pins every target to the state on disk at plan time, so one drifted path aborts the whole restore before a byte is written and an unpreviewed undo simply cannot replace newer work — which is why the panel callers that post here without a receipt keep working. Force removes that protection, so a request carrying it must carry both `confirm_force` — the receipt proves the overwrite was *shown*, the flag says it was *accepted*, and neither implies the other — and a `preview_id` that survives `checkHistoryRestorePreview`. That check is deliberately four questions and not one: the entry must match, every pinned digest must still hold, the configuration generation must not have moved, and the entry is **replanned** and both path sets compared again. The digests and the replan are not redundant — digests catch a path whose bytes moved, the replan catches a conflict set that moved for a reason the pinned paths cannot show (a rewritten manifest, or a path newly drifted from its recorded "after" state without its current bytes differing from what the preview read) — and what was authorized was the pair, which is what `TestServer_HistoryPreviewAPI_RefusesWhenTheConflictSetChanged` pins. A supplied preview is verified **whenever it is supplied**, force or not, so a client that previews a clean restore and finds it dirty by the time it confirms is refused rather than falling through to the weaker check. What that check returns is **not a yes but the pins themselves**: the receipt's digests are carried into `journal.RestoreOptions.Require` and enforced *inside* the transaction, because everything this layer can check runs before the path locks and before `BeginOperation`'s Git preflight, and `bn-vault-sync` can land in that window without changing which paths are in conflict — so under force the bytes somebody agreed to replace would otherwise be replaced by whatever arrived instead. A supplied map must name **every** recorded path, and `stageRestoreTarget` refuses one it does not, which is why a pin that records a *kind* rather than a `sha256:` digest — the non-regular-file case `historyRestoreDigest` deliberately describes instead of refusing — is a `CodeConflict` here: it cannot be stated as a `vault.FileExpectation`, and a pin that cannot be expressed must not quietly become no pin at all. A refusal is `CodePreviewRequired` or `CodePreviewStale` and writes nothing; a missing entry stays a `404` through `historyPreviewError`, which uses `errors.Is(err, os.ErrNotExist)` rather than `os.IsNotExist` because `journal.LoadEntry` wraps the read failure with the entry it was looking for and the un-unwrapping form reported every pruned entry as a broken history. The restore itself is **an ordinary journaled mutation and not a special one**: `noteops.Undo` goes through `BeginOperation`/`Finalize` under `Command: "bn web undo"`, so it is snapshotted into the content history, is undoable in turn, and travels to the other replica like any other change — recovering a version never erases the record of the version it replaced, and the failures are forwarded rather than reclassified (`undoRestoreError`), since a location refusal is a `403`, a safety refusal a `500` that says nothing was written, and a snapshot failure a `500` that says the files are already restored. The transaction's own failures are classified as an **ordering**, the same one `classifyCommit` and `syncWriteCode` use and for the same reason: `*TxnRollbackError` and `*TxnRecoveryError` nest the conflict that caused them while `IsTxnConflict` is `errors.As`, so rollback and recovery are asked before conflict and lock-busy, and anything unrecognized stays a `CodeJournal`. A `*vault.TxnCleanupError` no longer arrives at that switch from a restore, because it is not a failed restore and returning it would *stop the operation*: `noteops.Undo` halts on the first error `journal.Restore` gives it and so never reaches `Finalize`, which would leave the restore's writes on disk with no undo manifest authorizing them — and an undo that removed a tracked note then reads to `vaultgit`'s preflight as a deletion nothing explains, latching `blocked.json` over every later mutation. `journal.Restore` therefore carries it out on `RestorePlan.Cleanup` (`restoreCommitOutcome`, tested as the pure function it is, the way `classifyCommit` is), `Undo` finalizes and snapshots as usual, and this layer renders a **success that names the leftover file** (`undoSuccessMessage`; `bn undo` prints the same notice to stderr). The arm still standing in `undoRestoreError` is defensive and deliberately unreassuring — it says the restore was *not recorded*, because that is the only state it could be reporting. The server's caches are refreshed on the **failure** path too (`finishUndo`), since a restore error is not proof that nothing landed; and on the **success** path a refresh that could not be completed is folded into the answer as a trailing sentence rather than replacing it (`undoResponseWithReloadNotice`), because a landed restore reported as a 500 both lies and throws the cleanup notice away. That branch is defensive: `configManager.Refresh` publishes an unreadable configuration as a `ReloadInvalid` **status** and answers nil, so nothing in this package reaches a non-nil `reloadConfig` error today. All four paths are absent from `replicaReadPath`: a replica holds somebody else's vault and its journal describes writes it did not make and must not reverse.
- **The history page is a client of that class, never a class of its own**: `GET /history` (`internal/web/history_page.go`, `templates/history.html`, `static_src/history-workspace*.ts`) writes nothing and renders **no entry**, for the reason `syncPageData` gives — every list on it is a question about state that moves while somebody reads it. It carries the three endpoint names, the CSRF token, and the route's own `PageSize`/`MaxPageSize`, published so the page offers sizes the route will accept instead of discovering the ceiling by being refused; the filter vocabulary is deliberately **not** in the template, so the names in the filter and the names in the rows come from one table. It never chains preview into apply: the panel shows what would be written, which of those paths are in the content history and which reach the peer, and what is contested, and a confirmation with no receipt in hand issues nothing. The consent sentence is built from the **preview**, never from a `409`'s conflict list — a refusal names the paths that refused, while only the preview names everything the restore writes, so wording the consent from the refusal would ask somebody to agree to less than they would lose; the refusal's own paths are still shown, as a refusal. Because the receipt is one-use, applying it clears the stored preview and hides the panel on **both** answers — leaving the button would offer a refusal — and the paging offset is taken from the reply rather than from what was sent — not because that prevents walking past the end (`has_more` does; a page past it comes back empty with Next disabled), but because the reply is what the rest of the render describes, so the pager, the range label and the next Previous/Next click agree with the window the server actually read. A reply is rendered only when it belongs to the **newest** request the page issued: every filter checkbox, both pager buttons and Refresh start a request immediately and nothing cancels the one in flight, so a slow first answer landing after a fast second one would otherwise repaint the list, the pager *and the offset* with the older view while the controls describe the newer one — and that offset is the one a subsequent Next pages on from. A refused restore re-reads the list for the same reason the class's failure path refreshes the server's caches: an error is not proof that nothing landed. The nav link is gated on the same capability the page is (`templates/theme.html`), since a mode that refuses the page must not link to it. The round trip — the chosen bytes back on disk after a *rewrite* is undone, the peer equal to a reading taken before the restore, the served vault clean, and the restore listed as its own entry — is `internal/web/e2e/history.spec.js`; everything the page *decides* stays in `static_src/history-workspace*.test.ts` and `history-panel.test.ts`.


### History text comparisons

`POST /api/history/preview` adds bounded text comparisons for note and template
paths. `journal.ReadRestoreText` verifies snapshot size and hash, refuses live-path symlinks, snapshot escapes,
non-regular files and binary data, and returns the current digest. The web layer
only includes text when that digest matches the existing restore receipt pin.
Each version is capped at 128 KiB and the whole response's comparison content at
1 MiB, with at most 32 file comparisons per entry. Other file classes and oversized content carry an explicit unavailable
reason. Comparisons do not change receipt, conflict, or restore semantics.

The editor and History share `text-comparison.ts`: unchanged passages collapse,
text is rendered without interpreting Markdown or HTML, and large rewrites use
a bounded comparison with complete changed text. An editor conflict compares the
current vault version to the live draft, including edits made after the refusal.
