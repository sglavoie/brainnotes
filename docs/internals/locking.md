# Atomicity and writer serialization

Companion to `CLAUDE.md`; read before touching any code path that writes a note, takes a lock, or commits a `vault.FileTxn`.

- **Storage-location policy — the preflight that runs before anything exists.** The path-preserving replacement above keeps a destination name occupied *during* a write; it cannot help with storage where the whole vault is replicated by a file provider, because a temp file, a lock file, or a journal entry appearing and then vanishing is itself a change that gets synchronized. So on darwin `bn` refuses to mutate under such storage at all. `vault.GuardMutation(root, targets...)` (`internal/vault/mutation_guard.go`) is that check, and it is an **invariant, not caller advice**: it runs from `acquirePathLocks` and `Note.Save`, so anything reaching disk through the lock hierarchy or a note save is covered without knowing the policy exists. Callers that create something *before* they lock call it explicitly, because the point of the guard is that **no artifact exists when it refuses**: `journal.NewRecorder`'s entry directory, `bn new`/`bn init`'s `atomicWriteFile`, `backup.Create` and `backup.Restore`, `index.persist`, and — as the front half of a two-refusal preflight rather than as a lone call — `noteops.BeginOperation` for every journaled mutation and `vaultstate.Save` for the durable `brief`/`cockpit`/`recall` state files.
  - The darwin policy (`mutation_guard_darwin.go`) resolves symlinks, finds the deepest existing *directory* on the target, and walks its ancestors to the volume root looking for the `com.apple.file-provider-domain-id` xattr that iCloud Drive, Dropbox, Google Drive, and OneDrive set on the directories they own. A missing attribute continues the walk; **any other outcome — a permission error, an undecodable value, a broken walk — refuses the write.** A policy that cannot decide is not a policy that permits. A location is judged as a directory, never as a file: an unreadable mode on one note is a fact about that note, not about where it is stored.
  - Off darwin `mutationLocationPolicy` is nil and the guard is a no-op (`mutation_guard_other.go`), because this is a File Provider behavior. The unsafe-replacement refusal above still applies everywhere.
  - Refusal is one typed error, `*vault.ForbiddenMutationError` (`vault.IsForbiddenMutation`), carrying the target and the protected ancestor and **no file contents** — the guard runs before anything is read. `noteops.CodeOf` maps it to `CodeForbidden`, which the web layer already renders as HTTP 403. **Do not add an override.** A flag, environment variable, or config switch would exist precisely for the user who is certain their storage is fine, which is the case that loses a note. Reads are never guarded: a vault that moved under synced storage stays fully listable, findable, and browsable, and `bn history` still renders — it just cannot be written to.
  - **The guard is half of one operation-begin contract, and the ordering there is this same argument one level up.** `noteops.BeginOperation` (`internal/noteops/journal.go`) runs `GuardMutation` over the vault root and every target the caller can name yet, then the `internal/vaultgit` preflight, and only then returns the journal handle whose recorder is created lazily on the first `Capture`. Both refusals precede recorder creation, lock acquisition, directory creation, and staged temp files, so a vault on refused storage — or one left blocked by an earlier failure, or holding a deletion nothing explains — never takes a lock, never writes an intent, and never leaves a journal entry directory behind. `Journal.Finalize` reverses the order for the reason it exists: the undo manifest is made durable *before* the snapshot stages the paths it names, because that manifest is the only thing that authorizes committing a deletion. A snapshot that fails once the bytes have landed comes back as a `*vaultgit.SnapshotError` saying exactly that — the change is on disk, further writes are blocked, and **nothing was rolled back**. Do not add a caller that locks or creates a recorder ahead of this pair; the guarantee is stated entirely by what has *not* happened yet when the refusal fires.
  - **Durable sidecar state routes through `internal/vaultstate`, not through three hand-rolled temp-file-and-renames.** `vaultstate.Save` is guard → preflight → `vault.WriteStateFile` (the path-continuous replacement below) → a snapshot staging that exact path and nothing else. It judges only the **last** component of the state directory and of the state file for symlinks: an ancestor symlink is ordinary (`/var` is one on macOS and every `t.TempDir` lives under it), while a symlinked final component is how a write the location policy just approved gets redirected somewhere it did not approve. The generated index and the lock files are deliberately excluded and must stay excluded — derived state carrying no user intent, and snapshotting either would put a commit on every read-shaped operation.
  - **A production write outside the approved persistence packages has to say what already makes it safe.** `internal/audit`'s `TestNoUnannotatedDirectWrites` parses every production file and fails on a bare `os` write unless it carries `//bn:direct-write <reason>` on the line immediately above the call or in the enclosing function's doc comment, naming the guarantee in force ("guarded by `BeginOperation` above", "inside a `FileTxn` that holds the lock"). `gofmt` treats `//bn:` as a directive and pins it to the last line of its comment group, so the marker is one line with any prose above it. Widening `approvedPackages` is a decision about where safety lives — make it there, with a reason, rather than annotating call sites one at a time.
- **Atomicity model**: every write stages its bytes into a sibling temp file (fsynced, final mode already applied) and then installs that temp file with one filesystem operation, chosen by what the destination is supposed to be:
  - **Creating a path, and putting a removed one back**, expect the destination to be absent, so they place exclusively: hard-link the staged file into place, falling back to a no-replace rename (`renameNoReplace`) on a filesystem without links. Both fail rather than overwrite, which is what makes a writer that claimed the path in the meantime survive.
  - **Overwriting an existing path** goes through `internal/vault/replace.go`'s `replaceExisting`, which **never vacates the destination name**. On darwin that is `renameatx_np(RENAME_SWAP)`, on linux `renameat2(RENAME_EXCHANGE)`, on Windows `ReplaceFileW` with a same-volume backup; every other platform returns `*UnsafeReplacementError` (`IsUnsafeReplacement`). **There is no fallback that renames the destination out of the way first.** That vacancy — not a torn write — is the failure this design exists to prevent: a synchronizing file provider (iCloud, Dropbox, OneDrive) watching the directory reads the momentary absence as a deletion and can later propagate that deletion back over the replacement, so a note is lost by a write that locally looked atomic. Do not add a "best effort" rename path here; refusing to write is the correct outcome.
- **Proving the primitive before trusting it**: compiling the syscall in is not evidence it works — a network mount, a FUSE filesystem, or an old kernel can accept the call and do something else. Before the first real overwrite on a given volume (`syscall.Stat_t.Dev`, or the Windows volume serial), `proveReplacement` stages two probe files in the destination's directory, runs **the exact production primitive** on them while a busy-polling `presenceWatch` goroutine watches both names, and refuses the volume unless both names existed continuously *and* their content and metadata came out exchanged, and the directory then fsyncs. Only successes are cached (`provenVolumes`): a failed volume may be a different filesystem by the next call, and a cached failure would outlive its cause. A staged file on a different volume from its destination is refused by name (`requireSameVolume`) rather than left to surface as a confusing syscall error. All of this happens **before the first user path changes**. The probe pair carries its own `.txn-probe-<hex>.tmp` prefix so one a crash stranded is distinguishable from a staged write (`.txn-<hex>.tmp`) or a displaced note.
  - Ordering: staged bytes are fsynced before the exchange, the exchange is the only operation that touches the live path, and parent directories are fsynced after the commit applies (`syncParentDirs`). Commit, rollback, and recovery are therefore idempotent across an interruption at any durable step — a retry re-derives its state from the filesystem and converges.
  - Windows alone can fail *part-way*: `ReplaceFileW` has intermediate failure modes where the original is already in the backup. That is `*PartialReplacementError` (`IsPartialReplacement`), which says whether the original was put straight back and, if not, names the backup holding the only copy.
- **Overwrites are compare-and-swap on what they displaced, not on what they read.** `compareAndSwap` (`txn_replace.go`) exchanges first and judges afterwards, because a read-then-write judges bytes a save landing in the gap may already have replaced. The primitive hands back the path now holding the destination's previous content, so the bytes checked against the `FileExpectation` are the exact bytes displaced. A stale preimage is by definition a writer that ran after the last validation: its bytes are swapped straight back with the same path-preserving primitive and the caller gets a `TxnConflictError`, leaving the destination holding *their* version and this transaction holding nothing. An expectation that pins no hash skips the read entirely — a successful exchange already proves the destination existed, and a deliberately unreadable note (mode `0000`) must not fail on a permission error that has nothing to do with concurrency.
  - The one mixed state left is a put-back that itself fails: the destination is intact and holds this transaction's bytes, but the other writer's version survives only in a temp file, so it is named in a `TxnRecoveryError` with `Foreign: true`.
  - **Deleting the superseded temp file after a landed exchange is housekeeping, not part of the write.** It comes back as `*TxnCleanupError` collected on the transaction and returned by `Commit` *alongside* success — it never triggers a rollback, and the leftover file is deliberately retained so the content is still recoverable. Callers that only care whether the vault changed can ignore it; callers reporting to a human should not.
- **A killed process leaves a recovery intent, and reopening the vault finishes the transaction.** The idempotence above is about a *retry*; a process that dies mid-commit never retries anything, and its transaction is spread across renames that have happened and renames that have not. `internal/vault/txn_intent.go` closes that: after staging and journaling are durable and **strictly before the first rename**, `Commit` writes a versioned JSON record to `<vault>/.bnotes/txn/<id>.intent`, fsyncs it *and* its directory, and removes it only once every destination is renamed and every parent directory is synced. The record names each path, whether it is a removal, the staged temp file, and the sha256+size of both the prior and the intended content — **digests only, never note bytes**, so it is safe to read, mail, or paste into an issue.
  - **Recovery rolls forward, never back.** The swap unlinks the displaced copy (`removeSuperseded`), so after a crash the prior bytes are already gone and there is nothing to restore. Recovery instead completes the transaction from the surviving staged temps using the same primitives an ordinary commit uses — `compareAndSwap`, `placeNew`, `takeVerifiedCustody` — none of which can destroy a concurrent writer's file. Every decision is re-derived from what is on disk (does the destination already hold the intended digest? does it still hold the prior one?) rather than from a phase counter, which is what makes running recovery twice a no-op.
  - **Live transactions are told apart from abandoned ones by an flock on the record itself.** The committing process holds its intent file open under an exclusive `flock` for the transaction's life; recovery try-locks each record and skips any it cannot take, then re-`Stat`s to confirm (`os.SameFile`) that the path still names the inode it locked, closing the unlink race. The record is unlinked *before* the lock is released, so a finished transaction never leaves a lockable record behind.
  - **Where it runs, and how each caller fails.** `Vault.Open` runs a pass and **ignores the result** — `bn find` and every other read-only command must not be refused by a vault they are not writing to. `acquirePathLocks` runs the same pass and **returns its error**, so every mutation fails closed; it calls `acquirePathLocksRaw` and recovery calls that raw form too, because nesting the two would deadlock a writer against itself on a shared path.
  - **Corrupt fails open, unknown fails closed.** A record that does not decode proves the crash happened while it was still being written — its fsync and its directory fsync both precede the first rename — so it is discarded and the vault self-heals. A record whose `version` this build does not understand is kept and every mutation is refused (`vault.IsTxnIntentRecoveryFailure`), because a build that cannot read the plan cannot claim the work was finished.
  - A staged temp is dropped once its intended outcome is on disk, but **kept** when a foreign writer superseded the change: it then holds bytes that exist nowhere else.
- There is no cross-file transaction outside `FileTxn` — if `bn rename` or `bn move` errors mid-apply, prior writes stand. Mention this caveat in user-facing messages when relevant; rely on `git diff` for recovery.
- **CI must execute these primitives, not cross-compile them.** `.github/workflows/ci.yml` has a `vault-native` matrix running `go test ./internal/vault/...` on macOS, Ubuntu, and Windows runners for exactly that reason; the Ubuntu `just ci` job stays authoritative for the repo as a whole.
- **Writer serialization**: every `bn` writer takes an exclusive `flock`-style lock per note path (`<vault>/.bnotes/locks/<sha256-of-vault-relative-path>.lock`) around the write. The path is case-folded and NFC-normalized before hashing (`lockKey`), on every volume: on APFS, HFS+ and NTFS `Note.md`, `note.md` and an NFD spelling are one file and must meet on one lock, and on a case-sensitive volume the fold only makes case-variant files share a lock, which costs concurrency and never correctness. A set naming one note under two spellings is collapsed by that key, so it never waits on itself. `internal/vault/lock.go` owns the primitive; `vault.LockPaths` is the entry point for writers outside a transaction, and `FileTxn.Commit` uses the same code so lock naming and ordering cannot drift between the two. Locks are always taken in sorted key order, which is what makes multi-path callers deadlock-free. The lock is not what makes a single write safe — the compare-and-swap above is, and it detects an interleaved writer whether or not anyone locked. The lock exists so `bn`-vs-`bn` concurrency does not *have* to reach that detection: it keeps a multi-path commit's staged plan valid for the whole apply, so two `bn` processes serialize instead of one of them losing a whole transaction to a `TxnConflictError` it would then have to replan. Covered writers: `FileTxn.Commit`, `Note.Save`, `noteops.RenameFile` (both ends), `moveToTrash` (both ends, spanning the existence check so it cannot go stale), `CreateStubFromBrokenTarget`, and `bn new`. `bn init` deliberately does not lock — it writes the vault marker before a vault exists to lock in.
  - The lock must be `flock` (owned by the open file description), never an `fcntl` record lock (owned by the process), or in-process writers such as the web server's goroutines would silently not contend; a fresh descriptor per acquisition is required for the same reason. That also makes the locks **non-re-entrant**: a caller holding a path lock must not call into anything that locks the same path, or it waits out the full budget against itself — and, because of the shared vault guard below, must not nest a write large enough to escalate either. Keep new locking at the individual write, not around a whole multi-note operation — a vault-wide `bn rename` touches hundreds of notes, and holding hundreds of descriptors would hit `ulimit -n` and lock the whole vault.
  - Every writer first takes `<vault>/.bnotes/locks/vault.lock`, **shared**, and then its per-path locks. That guard exists so lock acquisition can escalate: a transaction planning more paths than `vault.MaxLockedPaths()` takes `vault.lock` **exclusively** and no per-path locks at all, since one exclusive guard already excludes every other `bn` writer using a single descriptor however many paths the set covers. `vault.MaxLockedPaths()` is therefore an escalation threshold, not a transaction-size limit — it is derived from the process descriptor limit (`RLIMIT_NOFILE` minus a 128-descriptor reserve minus the one guard descriptor, capped at 4096) only to decide when per-path locking stops paying for itself. It deliberately has **no floor**: a threshold above what the process can actually hold makes a set below it take one lock per path and die on `EMFILE` during acquisition instead of escalating, so on a process whose limit is under the reserve the threshold is `0` and every write escalates. **There is no cap on how many notes one atomic write may cover**; `noteops.SetFrontmatterAtomic` refuses no set for its size. That matters because an ordering that spans notes — a whole-list pin renormalize — rewrites every note in the list, and the pinned list is uncapped, so any fixed boundary leaves a list that renders fine and can never reorder. What escalation costs is concurrency for that one commit: every other writer in the vault waits on the guard, and an escalating writer that never finds a gap between ordinary writers exhausts its wait and gets a retryable `*TxnLockBusyError`.
  - The compare-and-swap stays regardless, because no lock binds an external writer like Obsidian: locking narrows the window, and only the swap-then-judge order closes it. A wait that exceeds the budget returns `*TxnLockBusyError` (`IsTxnLockBusy`), which is deliberately **not** a `TxnConflictError`: nothing was read or staged, so the caller's plan is still valid — `noteops.ClassifyTxnError` still reports it as `CodeConflict` because "retry" is the right advice. Locking is unsupported outside darwin/linux/windows, where the older unserialized behavior stands. Lock files are never unlinked — deleting one another process holds would let a third create a new file at the same name and lock nothing.
  - `vault.TryLockPath(lockPath)` is the wait-free end of the same primitive, for work that is optional rather than owed: it makes exactly one attempt and reports a held lock as `acquired == false` with a nil error, so a caller whose job another process is already doing skips it instead of spending the blocking budget. It routes through the same `lockOne` as everything above (fresh descriptor, real exclusive `flock`), so it contends with ordinary writers and with other goroutines in one process. It takes an explicit lock-file path rather than a note path, because not every lock belongs to the `<sha256>.lock` note namespace under `.bnotes/locks/`; missing parent directories are created, and the returned release is non-nil and idempotent even on a miss.
  - `Note.Save` needs a root to name its lock file, and a bare `vault.Note{Path: ...}` literal has none, so **`Save` refuses a rootless note** rather than silently skipping both the lock and the containment check. Build any note that will be written through `vault.NewNote` or `Vault.Notes`. `Save` is also a compare-and-swap, and **the same one** `FileTxn` uses: it turns the hash `Load` read into a `FileExpectation` and hands it to `compareAndSwap`, so a `Note.Save` and a transaction racing for one path resolve under identical rules rather than two hand-written approximations of them. A concurrent edit between `Load` and `Save` is a `TxnConflictError` instead of a lost update. Three deliberate carve-outs — the check applies only while `Path` still equals the path `Load` read (retargeting `Path` to save elsewhere is a supported pattern the loaded revision makes no claim about); an unreadable destination (mode `0000`) counts as unverifiable rather than refused, and downgrades to "must exist" rather than skipping the swap; and a destination that exists but is not a regular file is a `TxnConflictError` rather than something to replace. `Save` ignores `TxnCleanupError` — a leftover temp file is not a failed save.
  - `compareAndSwap`, `placeNew`, `linkExclusive`, and `takeVerifiedCustody` are free functions taking a possibly-nil `*txnHooks` precisely so `Note.Save` can call them directly. Do not re-implement replacement inside a caller to avoid constructing a transaction; pass `nil` hooks instead.
  - Still unserialized, by design or by omission: external writers (no lock to take), and the journal's pre-write `Capture` reads in the rename/move/trash flows, which happen outside the lock.
- **A transaction member may live inside `.bnotes/`, and that is how a write records something about itself.** `FileTxn` locks and swaps a path, not a *kind* of path, so a small record can be written in the same commit as the note it describes and get the same atomicity, the same preconditions, and the same journal entry — which is what makes it survive an undo the way the note does. The worked example is `internal/noteops`'s source-save ledger at `<vault>/.bnotes/source-saves/<sha256(save_id)>.json`: one file per idempotency key, staged into the note's own transaction, so "the note was saved" and "this save id was answered" cannot disagree in either direction. The key is digested rather than spelled out, so nothing about it is load-bearing for containment, and the `.json` suffix is not cosmetic — it is what the expiry sweep below matches on, so the one direct removal on the surface can only ever name a file this package wrote. Two constraints come with the pattern. The path must be chosen against `vaultgit.InScope` — `.bnotes/` is excluded wholesale bar a named few, so a record under a new subdirectory is invisible to the content history and never becomes commit content, while a record placed under one of the named ones would put a client's opaque key into a commit — through the record's *body*, which names the `save_id` in full, rather than through the digested filename (`Manager.journalEntryPaths` drops an out-of-scope member before it reaches the worktree comparison, so it also never surfaces as `Skipped` or `Unrecorded`). And an **expiry sweep is not part of the transaction**: `pruneSourceSaveLedger` removes an aged record with a plain annotated `os.Remove` after the commit, because a best-effort tidy that failed must not fail the save it was tidying up after. Nothing else on that surface may write directly; `internal/audit`'s `TestSourceSaveLedgerWritesOnlyRemovals` pins the exemption to removals alone.
- **A transaction member may also be bytes that are already on disk, staged by path rather than by value.** `FileTxn.WriteFrom(dest, sourcePath, size, sha256Hex, mode)` is the streaming seam for the case where the content is a file somebody uploaded, not a `[]byte` the caller is holding: it copies the source into the transaction's staged temp while re-hashing it, and refuses the member if the digest or the size it was promised is not what it read. That re-hash is the whole point — the staging area is written by a different request, minutes earlier, and a transaction that trusted a recorded digest would commit whatever happened to be at that path at commit time. It is **create-only** (`ExpectMissing`, always), because an attachment is not a note: nobody pinned a revision to it, so there is no precondition that could make replacing one safe. The worked example is `internal/noteops`'s attachment commit (`source_attachments.go`), which stages every referenced upload into the *note's own* transaction under the note's own journal entry, so a save stores the note and every file it points at or stores none of them, and one `bn undo` takes all of it back. Its destination rule is deliberately **not** `vault.WalkExclusion`: `config.DefaultIgnore` contains `Attachments`, which fold-matches the default `[attachments].dir`, so reusing the walk's exclusion would refuse exactly the directory attachments belong in. The replacement rules are about safety rather than about walking — no hidden path component, no Markdown extension, must be `vaultgit.InScope` so undo and the content history cover it, and no symlink traversal — and a destination already holding byte-for-byte this upload is reported as *done* rather than staged, which is what lets a retry after a lost response plan fresh and still succeed against a create-only member. The bound holds on **every** path the member can take and not just the forward one, which is a thing to check when editing any of them: staging streams, the intent record pins the digest rather than hashing a slice, `verifyUnchangedSinceStage` and `restoreCreated` judge the destination by stat or by `verifyFileDigest`, `recoverTxnIntentChange` compares the destination and the staged copy by streamed digest (`currentFileDigest`) rather than by content, and `journal.Restore` puts a create-shaped snapshot back with `WriteFrom` rather than reading it — `applyRestore` stages every target before it commits any of them, so a restore that read its snapshots would hold the whole entry at once. Each of those has a whole-file counterpart it would still pass every functional test after regressing to, so the residency itself is asserted: `internal/vault/txn_stream_test.go` and `internal/journal/journal_restore_test.go` measure `runtime.MemStats.TotalAlloc` across a commit, a recovery, and a restore of an 8 MiB file. The one direction that is **not** bounded is a streamed member's *removal*: `FileTxn.Remove` has no streaming counterpart, so undoing a save that committed attachments still buffers each one (`stageChange` reads the destination into `change.priorData`, and `journal.Recorder.Capture` reads it a second time to snapshot it). Do not read the create direction's bound as covering it: a streamed removal needs the compensating rollback to put the file back by renaming the custody copy rather than by rewriting held bytes, which is a change to the delete primitive's crash contract and not a local edit.
- **Upload staging is the inverse of that pattern: a `.bnotes/` area that is deliberately outside every transaction.** `internal/attachments` writes `<vault>/.bnotes/uploads/` — one blob, one record, and one destination claim per upload — with plain annotated direct writes rather than through `FileTxn`, because none of it is vault content and none of it is owed atomicity with anything: an upload that dies mid-body is an artifact to collect, not a change to roll back. What it does owe is the same location policy as every other write, so `Store.prepare` calls `vault.GuardMutation` on the staging root once and every path below it is inside what that call allowed. Three further properties are load-bearing. The area is **out of `vaultgit.InScope`**, so staged bytes never reach a commit, and it is a **dot-path**, so `privateMediaPath` makes it unservable (see [Serving modes](serving-modes.md)). Each artifact is created `O_EXCL` and fsynced before anything is allowed to depend on it — the blob before the record that promises it, the directory entry before a sweep could be asked to find it — so a record that does not decode was never a complete record, and the honest answer about the upload it would have described is that it is not there. And the sweep that collects abandoned staging takes `vault.TryLockPath`, never `LockPaths`: it is optional work, a second sweeper has nothing to add, and `LockPaths` escalates to the same vault guard a transaction escalates to from the inside. It stops *before* the lock when the staging directory does not exist, so a vault nobody has ever uploaded to does not acquire a lock file because a server started over it; and every caller treats its failure as housekeeping rather than as the outcome of whatever it was doing (see [Web write classes](web-write-classes.md)).
- **The note index (`internal/index`) sits outside all of the above.** Its state is `<vault>/.bnotes/index/` — a subdirectory, so `index.lock` stays out of `.bnotes/locks/`, whose filenames are `sha256(vault-relative path)` and belong to the note namespace, and so `rm -rf .bnotes/index` is the whole repair. Three rules govern it, and they are rules rather than implementation details because the first future caller to break one gets a deadlock rather than a bug:
  1. **The index never enters the lock hierarchy** — it takes no per-path lock and no `vault.lock`, not even shared. If a refresh took the shared guard it would block behind a writer escalating to the exclusive guard, and that writer would in turn have to wait out every in-flight refresh before it could escalate. A cache that can stall every writer in the vault is worse than a cache that is occasionally cold.
  2. **The index's own lock is a try-lock.** `persist` uses `vault.TryLockPath` on `<vault>/.bnotes/index/index.lock`; on contention it skips the disk write entirely and keeps its in-process cache. Another process is already writing an equally valid revision, so waiting buys nothing. Every write failure below that — read-only vault, full disk, unwritable `.bnotes` — is likewise swallowed: it costs the *next* process a warm start and cannot make this one wrong.
  3. **Never refresh the index inside a transaction.** The only wiring that exists today is safe by construction (`finishPropertyWrite` runs after `Commit`), but the rule is stated because the non-re-entrancy warning above makes a refresh-during-write a latent self-deadlock the moment anyone gives the index a code path that locks.

  Torn reads need no rule: the state file is written temp-file-then-rename like every other write here, so a reader opens either the old inode or the new one.
- **Synchronization serializes whole operations on two guards beside its state, not on the record locks.** `<vault>/.bnotes/sync/import.lock` excludes a second import and `<vault>/.bnotes/sync/export.lock` a second producer (`Export`, `Reset`, `RebaselineAfterReviewContext`); both are named by `vaultsync.StateLockPath` and taken through `vault.TryLockPath`, after the checkpoint barrier and never under a vault lock, and a held one is refused (`ErrImportBusy`, `ErrExportBusy`) rather than waited for. The records themselves — `import.json`, `export.json` — are written under `vault.LockPaths` on their own path **for one write at a time**, which is the "keep new locking at the individual write" rule above applied to sidecar state. That matters because the export record has a writer from the other side: an import records provenance through `vaultexport.RecordImport` while a pass may be running, and a pass that held `export.json`'s lock for its whole length made that call wait out the path-lock budget and fail. So a pass re-reads the record under the lock on every write and merges back the provenance entries it has not consumed, and the import records provenance before it touches the vault, so a lock that stayed busy refuses an import instead of committing it unrecognized. Re-enrollment's reset of `import.json` takes `import.lock` like every other writer of that file. Neither guard carries state, so backups neither archive nor restore them (`vaultsync.IsStateLock`), for the reason `.bnotes/locks/` is excluded: replacing a held inode would let a second holder in.
- **The Git safety engine (`internal/vaultgit`) sits outside the hierarchy too, and the ordering rule is one-way.** Its state is `<vault>/.git/brainnotes-safety/`, which is inside `.git` and therefore neither tracked nor walked. It holds two `flock` locks there, both taken through the same `vault.TryLockPath` primitive as the index: `safety.lock` serializes mutation snapshots and `push.lock` serializes remote attempts. Four rules, for the same reason as the index's — the first caller to break one gets a deadlock rather than a bug:
  1. **The engine never acquires a vault lock.** It calls no `LockPaths`, no `FileTxn`, and no `Note.Save`, so it cannot participate in a cycle with the note lock hierarchy, and a caller may safely hold path locks (or the escalated exclusive `vault.lock`) across a call into it. Stated positively: **vault locks first, safety lock last, never the reverse.** The engine reads the working tree through `git` and writes only inside `.git`, so it needs nothing from the note namespace.
  2. **The two safety locks are never held at the same time.** A push is a network round trip with no useful bound; holding `safety.lock` across one would stall the immediate mutation path behind an unreachable remote, which is exactly the contention the watcher and a note save would otherwise deadlock over. `Push` takes `push.lock` alone and a snapshot takes `safety.lock` alone.
  3. **Lock acquisition is wait-free except for mutation preflight; checkpoint admission is not.** Snapshot and push take their lock with one `TryLockPath` attempt. `Preflight` retries only a busy acquisition for at most 1.5 seconds, respecting context cancellation, so short background snapshots do not interrupt ordinary saves. Neither path is wait-free end to end, because the checkpoint barrier sits above both locks: before `safety.lock` is tried, the snapshot or preflight joins it with `checkpoint.JoinContext`, which waits up to `checkpoint.DefaultWriterWait` (15 seconds) while a live checkpoint holds the vault, unless the caller's context already carries a join (a `noteops.BeginOperation` or `vaultstate.Save` caller), in which case the nested join is counted and returns at once. Push does not join for `push.lock` — holding the barrier across a network round trip would let an unreachable remote exhaust every checkpoint's drain budget — but recording or clearing its retry state afterwards joins through `checkpoint.Join` with the same 15-second budget. Checkpoint admission happens once, before the lock wait; only `checkpoint.ErrBarrierHeld` (the checkpoint outlasted that budget) is reported as the retryable `KindBusy`, and any other admission failure, such as a pending restore or an unreadable checkpoint record, is a non-retryable error carrying its cause. The join is released when acquisition fails or the acquired lock is released. Checks run exactly once after acquisition; writes and uncertain outcomes are never replayed. A lock still held at the deadline returns the existing retryable `KindBusy` error. Because `TryLockPath` opens a fresh descriptor per acquisition, two goroutines in one process contend exactly as two processes do.
  4. **`Open` takes `safety.lock` in exactly one case.** It reads `intent.json` first — one failed file open on a healthy vault — and takes the lock only when a recovery intent is present and has to be adjudicated. A busy lock there means the record belongs to a live operation in another process, so opening leaves it alone rather than deciding on someone else's behalf. This is the engine's counterpart to the vault's own reopen-time recovery pass above, and it obeys the same one-way ordering: `Open` is still called with no vault lock held by this package.

  The record itself is the engine's sixth invariant (`internal/vaultgit/intent.go`, and the package's `doc.go`): written and fsynced before a snapshot's first index write, rewritten with the new commit's object name **before** `update-ref` is attempted, and removed only after the ref has moved and the directory naming it is durable. A surviving record refuses every mutation until recovery proves the recorded commit is *reachable* from the branch — reachability rather than equality, so another writer committing on top does not un-land the snapshot underneath — or until a person clears it. `Manager.ClearBlock` clears the marker and the record together inside the checkpoint barrier; `bn` exposes no command for it, and the supported manual procedure (`docs/operations/vault-safety-recovery.md`, "Clearing, in order", which the record's own recovery text points to) removes the same pair under `bn checkpoint run` so the removal keeps the same checkpoint protection. This is what makes an interrupted snapshot distinguishable from one that never started, including the case invariant 2 cannot cover: a local commit failure whose `blocked.json` write *also* fails leaves the intent standing, and the vault stays refused on a spotless working tree. A failure to write the record prevents the snapshot attempt entirely and is deliberately **not** a block — nothing was written, so the next mutation may retry.
