# Atomicity and writer serialization

Companion to `CLAUDE.md`; read before touching any code path that writes a note, takes a lock, or commits a `vault.FileTxn`.

- **Atomicity model**: file rewrites use temp-file + rename per file. There is no cross-file transaction — if `bn rename` or `bn move` errors mid-apply, prior writes stand. Mention this caveat in user-facing messages when relevant; rely on `git diff` for recovery.
- **Writer serialization**: every `bn` writer takes an exclusive `flock`-style lock per note path (`<vault>/.bnotes/locks/<sha256-of-vault-relative-path>.lock`) around the write. `internal/vault/lock.go` owns the primitive; `vault.LockPaths` is the entry point for writers outside a transaction, and `FileTxn.Commit` uses the same code so lock naming and ordering cannot drift between the two. Locks are always taken in sorted path order, which is what makes multi-path callers deadlock-free. This exists because replacing a destination renames it into custody first, leaving the path transiently vacant — without the lock a second writer creates into that vacancy, wins the path, and forces the custody holder to surface a `TxnRecoveryError` with the note's only prior copy stranded in a `.txn-custody-*.tmp` for a human to merge. Serializing `bn`-vs-`bn` writers demotes that to an ordinary staging conflict callers already replan. Covered writers: `FileTxn.Commit`, `Note.Save`, `noteops.RenameFile` (both ends), `moveToTrash` (both ends, spanning the existence check so it cannot go stale), `CreateStubFromBrokenTarget`, and `bn new`. `bn init` deliberately does not lock — it writes the vault marker before a vault exists to lock in.
  - The lock must be `flock` (owned by the open file description), never an `fcntl` record lock (owned by the process), or in-process writers such as the web server's goroutines would silently not contend; a fresh descriptor per acquisition is required for the same reason. That also makes the locks **non-re-entrant**: a caller holding a path lock must not call into anything that locks the same path, or it waits out the full budget against itself — and, because of the shared vault guard below, must not nest a write large enough to escalate either. Keep new locking at the individual write, not around a whole multi-note operation — a vault-wide `bn rename` touches hundreds of notes, and holding hundreds of descriptors would hit `ulimit -n` and lock the whole vault.
  - Every writer first takes `<vault>/.bnotes/locks/vault.lock`, **shared**, and then its per-path locks. That guard exists so lock acquisition can escalate: a transaction planning more paths than `vault.MaxLockedPaths()` takes `vault.lock` **exclusively** and no per-path locks at all, since one exclusive guard already excludes every other `bn` writer using a single descriptor however many paths the set covers. `vault.MaxLockedPaths()` is therefore an escalation threshold, not a transaction-size limit — it is derived from the process descriptor limit (`RLIMIT_NOFILE` minus a 128-descriptor reserve minus the one guard descriptor, capped at 4096) only to decide when per-path locking stops paying for itself. It deliberately has **no floor**: a threshold above what the process can actually hold makes a set below it take one lock per path and die on `EMFILE` during acquisition instead of escalating, so on a process whose limit is under the reserve the threshold is `0` and every write escalates. **There is no cap on how many notes one atomic write may cover**; `noteops.SetFrontmatterAtomic` refuses no set for its size. That matters because an ordering that spans notes — a whole-list pin renormalize — rewrites every note in the list, and the pinned list is uncapped, so any fixed boundary leaves a list that renders fine and can never reorder. What escalation costs is concurrency for that one commit: every other writer in the vault waits on the guard, and an escalating writer that never finds a gap between ordinary writers exhausts its wait and gets a retryable `*TxnLockBusyError`.
  - Custody stays regardless, because no lock binds an external writer like Obsidian. A wait that exceeds the budget returns `*TxnLockBusyError` (`IsTxnLockBusy`), which is deliberately **not** a `TxnConflictError`: nothing was read or staged, so the caller's plan is still valid — `noteops.classifyTxnError` still reports it as `CodeConflict` because "retry" is the right advice. Locking is unsupported outside darwin/linux/windows, where the older unserialized behavior stands. Lock files are never unlinked — deleting one another process holds would let a third create a new file at the same name and lock nothing.
  - `vault.TryLockPath(lockPath)` is the wait-free end of the same primitive, for work that is optional rather than owed: it makes exactly one attempt and reports a held lock as `acquired == false` with a nil error, so a caller whose job another process is already doing skips it instead of spending the blocking budget. It routes through the same `lockOne` as everything above (fresh descriptor, real exclusive `flock`), so it contends with ordinary writers and with other goroutines in one process. It takes an explicit lock-file path rather than a note path, because not every lock belongs to the `<sha256>.lock` note namespace under `.bnotes/locks/`; missing parent directories are created, and the returned release is non-nil and idempotent even on a miss.
  - `Note.Save` needs a root to name its lock file, and a bare `vault.Note{Path: ...}` literal has none, so **`Save` refuses a rootless note** rather than silently skipping both the lock and the containment check. Build any note that will be written through `vault.NewNote` or `Vault.Notes`. `Save` is also a compare-and-swap: inside the lock it verifies the destination still holds the hash `Load` read, so a concurrent edit between `Load` and `Save` is a `TxnConflictError` instead of a lost update. Two deliberate carve-outs — the check applies only while `Path` still equals the path `Load` read (retargeting `Path` to save elsewhere is a supported pattern the loaded revision makes no claim about), and an unreadable destination (mode `0000`) counts as unverifiable rather than refused.
  - Still unserialized, by design or by omission: external writers (no lock to take), and the journal's pre-write `Capture` reads in the rename/move/trash flows, which happen outside the lock.
- **The note index (`internal/index`) sits outside all of the above.** Its state is `<vault>/.bnotes/index/` — a subdirectory, so `index.lock` stays out of `.bnotes/locks/`, whose filenames are `sha256(vault-relative path)` and belong to the note namespace, and so `rm -rf .bnotes/index` is the whole repair. Three rules govern it, and they are rules rather than implementation details because the first future caller to break one gets a deadlock rather than a bug:
  1. **The index never enters the lock hierarchy** — it takes no per-path lock and no `vault.lock`, not even shared. If a refresh took the shared guard it would block behind a writer escalating to the exclusive guard, and that writer would in turn have to wait out every in-flight refresh before it could escalate. A cache that can stall every writer in the vault is worse than a cache that is occasionally cold.
  2. **The index's own lock is a try-lock.** `persist` uses `vault.TryLockPath` on `<vault>/.bnotes/index/index.lock`; on contention it skips the disk write entirely and keeps its in-process cache. Another process is already writing an equally valid revision, so waiting buys nothing. Every write failure below that — read-only vault, full disk, unwritable `.bnotes` — is likewise swallowed: it costs the *next* process a warm start and cannot make this one wrong.
  3. **Never refresh the index inside a transaction.** The only wiring that exists today is safe by construction (`finishPropertyWrite` runs after `Commit`), but the rule is stated because the non-re-entrancy warning above makes a refresh-during-write a latent self-deadlock the moment anyone gives the index a code path that locks.

  Torn reads need no rule: the state file is written temp-file-then-rename like every other write here, so a reader opens either the old inode or the new one.
