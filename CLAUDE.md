# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`bn` (Brain Notes) is a small Go CLI for editing and querying a plain-Markdown notes vault. It targets fast, vault-aware operations (frontmatter queries, wikilink-aware rename/move, templated note creation) that complement an editor rather than replace one. The README is the canonical user-facing spec — keep behavior aligned with it when changing commands.

## Common commands

The repo uses `just` for development tasks (see `justfile`):

- `just build` — build the `bn` binary in the repo root via `go build -o bn ./cmd/bn`.
- `just install` — `go install` for all three binaries (`$GOPATH/bin`): `bn`, plus the two private companions `bn-vault-guard` and `bn-vault-sync`. The companions are installed with `bn` and never separately, because each drives the same internal packages the CLI does — one a version behind its CLI is two processes disagreeing about what a snapshot or a package means.
- `just test` — `go test ./...`.
- `npm ci` — install pinned frontend tooling before changing TypeScript source or running frontend checks.
- `just web-build` — bundle `internal/web/static_src/main.ts` into committed `internal/web/static/app.js`, and concatenate `internal/web/static_src/css/` into committed `internal/web/static/app.css`.
- `just web-check` — run frontend typecheck, `npm run lint:web`, Vitest/jsdom tests, and the browser bundle build.
- `just lint` — fails on `gofmt -l .` output, runs `go vet`, runs `just lint-new`, then runs `just web-check`.
- **`node_modules` is excluded from every Go tool by hand.** An npm dependency (`flatted`, via `eslint`) ships Go source, and Go's `./...` matcher skips `testdata`/`vendor`/dot-directories but not `node_modules` — so it silently joined the module and moved the recorded complexity floor from 552 to 555. The `justfile`'s `go_packages` / `gofmt_check` substitutions, `.golangci.yml`'s path exclusion, and the `gocyclo`/`deadcode` filters in `scripts/metrics_*.py` all encode that one decision. After adding an npm dependency, compare `just lint-full` and `just metrics` before and after installation on the same Go source tree; their Go issue totals must agree and must not move merely because `node_modules` changed.
- `just lint-new` — the **function-complexity ratchet**: `go run ./scripts/lintratchet -base {{ratchet_base}}` over `.golangci.yml` (funlen 100/50, cyclop 10, gocognit 20, nestif 4). The unit of judgement is the **function, not the line**: it takes the whole-tree report, maps each violation onto its enclosing top-level function with `go/parser`, and fails when any line of that function differs from the base — uncommitted and untracked work included. That replaces `golangci-lint --new-from-merge-base`, which filtered by changed *line* while cyclop/gocognit/funlen report a score on the *declaration* line, so editing only a body made a function worse with the gate staying green (measured: `contextOutput` sat at gocognit 21 and `just lint-new` reported `0 issues.`). `ratchet_base` is a *commit*, not the branch `main`, because work lands directly on `main` and `merge-base main HEAD` is then `HEAD` — an empty diff range that passes on anything. Violations in functions nobody touched — the floor recorded in `docs/internals/refactor-baseline.md` — are still tolerated, so a pre-existing violation that merely shifts line number stays out of the way; deliberately not `issues.whole-files`. It **fails** rather than skips when `golangci-lint` is absent (`just install-lint` installs the pinned version). Read that doc before changing a threshold or moving `ratchet_base`.
- `just lint-ratchet-selftest` — the ratchet's regression test (`scripts/lint_ratchet_selftest.py`): it builds a throwaway git repository with the repo's own `.golangci.yml`, edits only the *body* of a pre-existing function from under to over the thresholds, and proves the gate exits non-zero and names the function — then proves an untouched violation in the same file is still tolerated. Deliberately outside `just ci` (it runs golangci-lint a second time against a synthetic tree) and wired into `.github/workflows/ci.yml` as its own step, so the gate cannot silently stop enforcing.
- `just lint-full` — the same config over the whole tree, exit 0. A report, not a gate; it is how the remaining count is measured. Deliberately absent from `just lint` and `just ci`, like `just metrics`.
- `npm run lint:web` — the **TypeScript half of the same ratchet**: `eslint.config.js` (complexity 10, max-lines-per-function 100, max-depth 4, `@typescript-eslint/no-unused-vars`) over `internal/web/static_src/**/*.ts`. ESLint has no per-changed-line mode, so `scripts/lint_web.mjs` restricts it to the `.ts` files changed since `ratchet_base` — read from the `justfile` so the two gates cannot drift onto different anchors — including unstaged and untracked ones. That granularity is per *file* — coarser than the Go half's per-function judgement: touching a file that still has a violation means fixing that file. It **fails** rather than skips when ESLint is missing (`npm ci`). `npm run lint:web:full` is the whole-tree report, exit 0, like `just lint-full`.
- `just ci` — the full validation envelope: `gofmt -l` check, `go vet ./...`, `just lint-new`, `go test ./...`, frontend typecheck, `npm run lint:web`, Vitest, and a bundle-drift check that hashes `internal/web/static/app.js`, rebuilds it, and byte-compares the result against those on-disk bytes. That compares the bundle against its own source rather than against `git`, so it passes on an uncommitted tree and fails only when the checked-in bundle is genuinely stale. Run this before declaring work complete (`scripts/health.py` runs exactly this).
- `just fmt` — `gofmt -w .`.
- `just test-sync-transport` — the **real-transport gate**: two actual Syncthing processes on loopback, over two disposable vaults, carrying real `vaultexport` packages. It is the synchronization counterpart of `just test-e2e` and is outside `just ci` on the same terms (it waits on other processes and needs a pinned binary downloaded once; a gate that skips when its subject is absent is not a gate). Scenarios are in `internal/vaultsyncd/realtransport_test.go` behind the `synctransport` build tag; the harness is `internal/synctransport` and the pin is `internal/syncthingbin`. See their entry under Architecture.
- `just test-sync-recovery` — the **distributed recovery gate**: fixed-seed offline delivery schedules and capacity failures compose with every ordinary synchronization package test, then with `just test-sync-transport`. The long randomized scenario is behind the `syncrecovery` build tag; the fast import-state ENOSPC cases remain in ordinary test runs. Use it for changes to synchronization durability, conflict recovery, receipts, retirement, or transport behavior.
- **Never verify a mutating command against an ambient vault.** `$BNOTES_VAULT` is normally set in a developer's shell and it **overrides a `cd`**, so `cd $scratch && bn rename-key ...` writes to the real vault — which is how a verification run once renamed a frontmatter key in 214 real notes. Use `just vault-sandbox -- <bn args>` (`scripts/vault_sandbox.py`): it scrubs `$BNOTES_VAULT`, builds a throwaway vault under the system temp directory, asks `bn config` which root it *actually* resolved, and refuses with exit 2 unless that root is the sandbox. The test half of the same rule is **`internal/vaultfixture`**, which states the three refusals once as `IsolationError` (a real vault by name, anything outside the system temporary directory, anything outside the asserted sandbox) and offers disposable Git-backed vault `Pair`s, an `Epoch`-anchored clock, and loopback-only listeners. `internal/cli/vault_isolation_test.go` delegates the refusals to it — `TestMain` scrubs the variable for the whole package and `markVaultRoot`/`useVaultRoot` route through `IsolationError`; the `Pair`/`Clock` helpers were deliberately ahead of the two-vault synchronization work and `internal/vaultsync`'s tests are now their first caller, while `ReserveLoopbackAddr` now has its first caller in `internal/synctransport`, which must hand a reserved address to a child process before it can bind (`ListenLoopback` and `LoopbackHost` are still used only by this package's own tests). `just test-e2e` is the third caller of the *rule*, launching its server through `scripts/vault_sandbox.py` rather than re-implementing the guard in JavaScript. **Do not write a fourth copy of these refusals**; add a caller.
- `just test-e2e` / `npm run test:e2e` — the **real-browser gate** (`internal/web/e2e/`, Playwright + Chromium, `playwright.config.js` at the repo root). `prepare.mjs` builds an *unstamped* `bn` and a disposable vault pair under the system temp directory, seeds each `brainnotes.toml` with a marker line so `/api/config/status`'s `source_hash` identifies which vault a server actually loaded, and reserves a loopback port; the config launches `bn serve` through `scripts/vault_sandbox.py` with `cwd` set to the fixture, so `serveWebProjectRoot` finds no checkout and the suite tests the **embedded** bundle rather than one it just regenerated into the working tree. `fixture.js` installs an always-on `page.route` origin guard, so a request leaving the fixture origin is aborted and recorded whether or not the spec asked for the guard — and it *parses* rather than prefix-matches, because `http://<fixture-origin>@evil.example/` starts with the fixture origin and is a request to somebody else. `smoke.spec.js` covers only what jsdom structurally cannot (the shipped bundle executing, rendered HTML parsed by an engine, a wikilink that actually navigates); `isolation.spec.js` covers containment, including the suite's one real write — a quick capture typed into the browser, asserted to land in the fixture vault and not in the peer; `editor.spec.js` covers the `/edit` page for the same reason — the bundled CodeMirror mounting, keystrokes and Ctrl/⌘ + S reaching `/api/source/save`, a toolbar command and a `[[` completion editing the document, and the typed bytes landing in the fixture note and in nothing else; `editor-journey.spec.js` covers the attachment and note-management halves of that page — a file chooser the browser opened, a drop and a paste onto the element CodeMirror owns, a server-chosen destination arriving back percent-encoded in a mounted document, the `<details>` nothing inside is clickable until it is open, `window.confirm` in front of a trash and an undo, and the dirty gate in both of its answers — refusing a rename past unsaved text, and offering the "anyway" button for the actions that may proceed over a draft (a capture, taken over unsaved text, with the draft still in the editor afterwards and absent from the file) — each journey ending in the same `gitStatus` assertion; the two editor specs share `editor-helpers.js` and work on **different notes** (`Alpha.md` is editor.spec.js's, which renames it away and recreates it), because the suite runs one worker over one vault pair; `guards.spec.js` tests the harness's own two predicates directly; `history.spec.js` covers the `/history` workspace — where each recorded change came from, filtered by origin and by path, and then a restore previewed, confirmed and *checked against the disk*, which is the one thing jsdom structurally cannot answer here: the Vitest suite stops at the request the page issued, not at whether the bytes came back. So the restore test makes **two** changes to its template and recovers the second: undoing a creation only has to delete a path, which would leave the central claim — that the bytes somebody chose come back — untested, while undoing a rewrite has to put those bytes back, and `readFileSync` is what says whether it did. Containment is a **before/after comparison** rather than a restatement of how the fixture started: the peer's existence and its `gitStatus` are read before the restore and re-asserted equal to that reading afterwards, while the served vault is asserted *clean*, which is what says the restore was journaled and snapshotted like any other mutation rather than left dirty — with a `bn web undo` entry now listed beside the entry it reversed, that entry asserted by **its own identifier** rather than by its command, since the journal holds two saves of this template and the origin test left more, so "an entry with this command is listed" is true whether or not the restored one survived. The path filter narrows to a directory matching nothing and only then widens back, because an entry already on screen passes a filter that does nothing at all. It works on its own `Templates/` files, one per test, created and deleted by the spec: that directory is excluded from note queries, so writing there cannot disturb the twelve-item recent list `smoke.spec.js` asserts against, and it is inside both `vaultgit.InScope` and `vaultsync.Portable`, which is what makes the panel's "travels to your other replica" claim checkable rather than decorative — what the spec checks is that *classification*, against `vaultsync.Portable`; it synchronizes nothing, and no e2e test does — a spec that recovered a change another spec made would be asserting against whatever ran before it. Each template write is awaited by its own status sentence for the same lock reason every other management action here is, and so is *opening* one: the bytes and the revision are fetched and then written into the editor, so typing before that lands is typing into a draft about to be replaced; `sync.spec.js` covers the `/sync` review surface — five held packages resolved in a browser (a text conflict merged by typing into the mounted editor, an attachment and a divergent rename accepted from the peer, a delete-edit and a configuration conflict kept), with the receipt count under `.bnotes/sync/outgoing/receipts/` and the status panel's own sentences as the assertion that status follows **durable acknowledgment** rather than delivery. Its holds are seeded by `scripts/syncfixture`, a Go program `prepare.mjs` runs after both vaults are committed rather than more JavaScript: a hold is only real once `internal/vaultimport` has refused to apply a package, and a package only once `internal/vaultsync`'s `Builder` has produced one, so a state file written by hand would give the spec a page that agrees with the harness instead of with the engine. Two properties of that fixture are load-bearing — the contested content it writes into the served vault is dated `seededAt` (2024-02-01) so those notes sort behind `SEED_NOTES` on `/library`, whose twelve-item recent list `smoke.spec.js` asserts every seeded note is in, and none of its paths joins `SEED_NOTES`, because one worker over one vault pair means a conflict on `Alpha.md` would be contesting the note `editor.spec.js` renames away — and because the holds are consumed by resolving them, the file is `test.describe.configure({ mode: "serial" })` and deliberately ordered: the review assertions come before the resolutions that spend them. Three things that spec learned the hard way, none of them optional: a synthetic `drop`/`paste` is dispatched at **`[data-source-surface] .cm-content`**, not at the surface — the surface is where the listeners are, so dispatching there never travels through CodeMirror and the capture-phase registration and `stopPropagation` in `source-attachment-panel.ts` become unobservable (that is precisely what the jsdom test can do and this one must not); CodeMirror answers a dropped file by reading it through a `FileReader` and inserting its bytes as text *and selecting them*, which is asynchronous and self-erasing — so the drop is not checked against the document at all but against the event: `sendFiles` registers a witness listener on `.cm-content`, which runs if and only if CodeMirror's own did, and reports whether the event ever reached the target phase; and a management action is awaited by **its own status sentence** before the next one is clicked, because a mutation holds the Git safety lock for its whole operation and that lock is taken *without waiting*, so a second request arriving inside the first is refused rather than queued (`vaultgit`'s preflight `TryLockPath` → `KindBusy` → `noteops.classifySafetyError` → `CodeConflict` → `409`; note that `vault.IsTxnLockBusy` is a different thing — a five-second path-lock wait that has timed out — and is not what refuses here), which reads as a silently ineffective action. `fixture.js` also owns the shared `gitStatus(vault)` predicate, whose `MACHINE_LOCAL` exclusion list (`.bnotes/index/`, `.bnotes/locks/`, `.bnotes/source-saves/`, `.bnotes/sync/`, `.bnotes/uploads/`) must stay in step with `internal/vaultgit/scope.go` — a **new** `.bnotes/` file is deliberately not covered and fails there. Excluding `.bnotes/uploads/` takes the staging tree out of every `gitStatus` assertion, so `editor-journey.spec.js` reads it directly (`stagedLeftovers`) after each save and after a cancel: `Store.Forget` swallows its failures by design, and nothing else in this suite would see bytes left behind. Page-level logic stays in `internal/web/static_src/*.test.ts`. This directory is plain ESM JavaScript, so `npm run lint:web` (which is a ratchet scoped to `static_src`) does not see it — `npm run lint:e2e` applies the same ESLint rules here and `npm run test:e2e` runs it first. The suite is **deliberately outside `just ci`**: it needs a browser binary `npm ci` does not install (`npm run test:e2e:install`), and a CI step that skips when a dependency is missing is a gate that has stopped gating.
- `bn serve` — local `just build`/`just install` binaries remember this checkout path, rebuild web assets here before serving, and serve static assets from `internal/web/static` on disk. The serve-time build prefers the native `node_modules/esbuild/bin/esbuild` binary to avoid requiring `node`/`npm` when dependencies are already installed; unstamped binaries fall back to current-directory checkout detection, then embedded assets.

Run a single test: `go test ./internal/cli -run TestFind_TagFilter` (standard Go test selectors). Integration tests in `internal/cli/integration_test.go` use golden files under `internal/cli/testdata/`.

Go module is `github.com/sglavoie/sglavoie_brainnotes` (note: the binary is published as `github.com/sglavoie/brainnotes/cmd/bn` per the README, but the local module path differs — keep imports using the local module path).

## Architecture

Layered packages, each with a focused responsibility. Commands compose primitives from the lower layers — keep the boundaries clean rather than reaching across them. One-line map below; the full per-package contract, with the invariants each one is required to hold, is in `docs/internals/architecture.md` — **read it before adding a package or moving responsibility between existing ones.**

- `cmd/bn/main.go` — thin entrypoint, delegates to `internal/cli.Execute`.
- `internal/cli` — Cobra command tree; `root.go` loads config into the command context, `notes.go` centralizes multi-note positional/stdin handling, `target_resolution.go` is the shared NFC-aware single-note resolver.
- `internal/config` — TOML loader for the vault-local `brainnotes.toml`, which *is* the vault-root marker: resolving the root and locating the config are one operation. An optional `brainnotes.local.toml` overlays it with the keys that name **this machine** (editor, listen address, agent command); `ownership.go` is the table saying which file owns which key, and misplacement is rejected only once the vault is enrolled in synchronization — every legacy single-file config is a portable file full of local keys. An absent overlay and an empty one are distinct states, all the way into `Fingerprint.Composite`. Saved views are a `[[views]]` array of tables validated **shape-only** — `config` cannot import `queryexpr` without a cycle, so a view whose query rotted still loads and every layer above must render it disabled with its error.
- `internal/vault` — root path + config; `Walk` skips hidden dirs, configured ignores, and the templates dir (template files hold unrendered placeholders that are not valid YAML and must never be walked). Also owns locking and `FileTxn`, including the fsynced recovery intent under `<vault>/.bnotes/txn/` that lets a killed process's transaction be rolled forward on the next `Open` or the next mutation.
- `internal/frontmatter` — parse/rewrite YAML frontmatter. `Map` preserves insertion order on parse, but `Marshal` **always emits keys alphabetically sorted** — intentional and load-bearing for stable diffs.
- `internal/wikilink` — Obsidian-style `[[Target#Heading|Alias]]` parsing/rewriting. **Code-block aware**: links inside fenced, indented, or inline code are masked out.
- `internal/query` — composable `Predicate`s over `*vault.Note` for `find`, plus the path-aware wikilink graph reused by recall ranking. `GraphMetrics` adds bounded graph traversal (degree, connected components, hop-bounded BFS) and the six graph predicates lower onto `Reachable`. `And` with no args matches everything.
- `internal/queryexpr` — the vault query expression language (lexer, AST, parser, `ParseError`). A sibling of `internal/query`, never files inside it: it may import `query`, `config`, `schema`, `frontmatter`, `vault`, `wikilink`, `textnorm` and nothing above them.
- `internal/recall` — deterministic contextual retrieval, no persistent index; ranking, context bundles, and the `<vault>/.bnotes/recall.json` state store.
- `internal/agent` — shared argv-only process runner. No shell, provider SDK, persistence, or implicit network behavior.
- `internal/template` — discovery and rendering for `bn new`; case-insensitive lookup, `.Vars` from repeatable `--var key=value`.
- `internal/web` — HTTP server, page handlers, and mutating APIs. `capabilities.go` derives one `Mode` (`local`/`read-only`/`hosted`) in `NewServer` and every handler asks `s.caps` instead of re-reading an option; `requestGuard` applies the refusals, headers, and body bound ahead of every handler. `static_src/` is strict TypeScript bundled by esbuild into the committed `internal/web/static/app.js`, so Go builds need no Node. The `/edit` page — the raw-Markdown editor (`editor_page.go`, `templates/editor.html`, `static_src/source-*.ts`) — **bundles CodeMirror from npm** rather than vendoring it like the Cytoscape chain, which is why `app.js` is 1.6 MB and esbuild warns on its size; `static_src/source-editor-view.ts` is the only module that imports it, so everything the editor *decides* stays testable under jsdom against a fake `SourceSurface`.
- `internal/web/cssbuild` — concatenates the stylesheet parts under `internal/web/static_src/css/`, in the order `index.css` lists them, into the committed `internal/web/static/app.css`. Deliberately a **concatenation rather than a CSS bundle**: the parts are the source of record, and a bundler re-serializes them (esbuild drops every comment and rewrites `[aria-busy='true']` to `[aria-busy=true]`, which CSS contract tests assert against the generated file). The manifest order **is** the cascade — `tokens.css` first, `responsive.css` last — and drift is caught by a plain Go test, so a stale stylesheet fails `go test ./...` with no toolchain involved.
- `internal/cockpit` — the shared Daily Fix Cockpit core (queue, state, fixer, review context) consumed by both `bn doctor` and the web cockpit APIs, so CLI and web stay identical.
- `internal/noteops` — the shared note-mutation layer used by both CLI commands and the web APIs; `preview.go` defines the canonical `NotePreview` model every `--dry-run` and every web preview renders through. `source.go`/`source_save.go`/`source_ledger.go` are the only write whose unit is the **whole file**: bytes in, bytes out, never through `frontmatter.Marshal` (which sorts keys), pinned to the **revision** the edit was read at, with no replan — a whole-file save is not commutative, so a conflict is a typed `*SourceRevisionError` for a person, while a duplicate submission replays a per-`save_id` record kept outside `vaultgit.InScope` and a note already holding the bytes converges. `journal.go` is the one path a mutation begins and ends through: `BeginOperation` runs the storage-location guard and the `vaultgit` preflight **before** any recorder, lock, directory, or temp file exists, and `Finalize` writes the undo manifest first (it is what authorizes committing a deletion) and snapshots exactly its paths second. Both must happen for an operation to be a success, so a snapshot that fails after the bytes landed is a `*SnapshotError` / `CodeSnapshotFailed` — a **distinct HTTP 500** that says the change is on disk and further writes are blocked, and never claims a rollback. A no-op captures, finalizes, and commits nothing, so it cannot leave an empty commit.
- `internal/properties` — the reusable property index behind the web workbench. Deliberately does not depend on `internal/web`.
- `internal/pins` — the shared pinned-list core; plans assignments only, never writes. It is a **leaf package**: it must not import `internal/noteops`, because `noteops` → `query` → `pins` would close a cycle.
- `internal/index` — a persistent cache of note bytes in `<vault>/.bnotes/index/`, so a repeated vault load stats each note instead of re-reading it. It saves the read and **not** the parse: a warm load still parses a fresh `*vault.Note` (and so re-runs `frontmatter.Parse`) for every walked note. Another **leaf package**: it may import `vault`, `config`, `frontmatter` and nothing else — it produces `[]*vault.Note` and stops. It walks via `vault.Walk` (never a hand-rolled `filepath.WalkDir`), trusts a cached entry only when size and mtime match *and* the mtime is older than a 2s non-configurable `staleWindow`, and builds a fresh `*vault.Note` per snapshot. It **self-heals silently** on any unusable state file — the deliberate inverse of `internal/recall`'s fail-closed store, because the index holds no user intent — so an index failure is never a request error and a failed disk write is ignored.
- `internal/vaultgit` — the internal Git safety engine: snapshots the vault into a local Git history after every change and pushes it to a private remote. No user-facing surface and it never reads or writes a note — it stages exact paths, builds a tree, and moves one ref. Six invariants: a deletion is committed only when an *uncommitted* `internal/journal` record proves it; a local safety failure latches `blocked.json` and fails closed; remote availability is never a correctness input; the user's index is untouched (private `GIT_INDEX_FILE` seeded from HEAD); no note content reaches an argv, a commit message, or a log, and the four sites where a note *path* does are each positional rather than option-parsed; and every snapshot is bracketed by a fsynced `intent.json` so an interrupted snapshot is distinguishable from one that never started, refusing mutations until recovery proves the recorded commit reached the branch or a person clears it. Only the external-change scan (`CommitPending`) may leave an addition out, and only one it genuinely cannot read; a snapshot of caller-named paths fails closed instead, and a path the engine *can* read that Git refuses to stage is a repository failure and is fatal everywhere. `OpenHistory` is the package's read-only second door: a `History` takes no lock, writes no state, and reads only committed objects, so asking what there is to export cannot move the autosave schedule a `Manager` would republish. Contract in `docs/internals/architecture.md`, locking in `docs/internals/locking.md`.
- `internal/vaultstate` — the one write path for durable sidecar state (`.bnotes/brief.json`, `cockpit.json`, `recall.json`): guard → preflight → path-continuous replacement → a snapshot staging that exact path and nothing else, under a fixed operation token the calling package chooses. A vault with no Git history keeps the write and skips the snapshot. The generated index and the lock files are deliberately excluded — derived state with no user intent, and committing either would put a commit on every read-shaped operation.
- `internal/vaultsync` — the versioned wire protocol (`brainnotes-sync-v1`, compared exactly and never parsed as an ordering) and enrollment state for two-way synchronization between two replicas of one vault. It decides what a package *is*, who a vault accepts one from, and what a receipt means; transport is Syncthing's and applying belongs above. A **leaf package**: `config`, `vault`, `textnorm` only — never `vaultgit`, `journal`, `index`, or `noteops`, because what may travel must not depend on what the content history tracks. The portable scope is deliberately **narrower** than `vaultgit.InScope`: `.bnotes` is excluded wholesale, so this machine's undo journal and sidecar state stay on this machine. `CollisionKey` (NFC → fold → NFC) makes a case-only or normalization-only clash a producer-side `ErrPathCollision` rather than a silent overwrite on the case-insensitive side. `Accept` asks three separable questions in a fixed order — is it a package (`Validate`, format token first and alone), is it ours (`CheckEnrollment`: wrong vault, unknown peer, stale or ahead epoch), are the bytes here (`VerifyPayloads`) — so a misrouted package costs no hashing and an unlisted extra file reads as a transfer still running. A package is immutable by exclusive `os.Mkdir` with payloads fsynced before the manifest that names them, and a **receipt means durable possession of every package result** — backed by a named local recovery entry when the package wrote content, or explicitly marked converged when every result was already present — never a completed file transfer. Retirement additionally requires `brainnotes-backup-coverage-v1` evidence for the exact manifest digest, published only after the private deployment snapshot verifies, so acknowledgment alone cannot discard the last locally recoverable payload.
- `internal/vaultexport` — the producer side: it turns this vault's **committed** Git history into `vaultsync` packages and durably remembers how far it got. The one place `vaultgit` and `vaultsync` meet, so neither may import it. One commit is one operation, identified by `vaultsync.DeriveOperationID(vaultID, commit)` — the single deliberate exception to "an operation identity is never re-derived", because a pass that published and died must re-derive the same name rather than mint a second identity for a change the peer may already hold. Uncommitted edits stay pending by construction (`vaultgit.History` reads objects, never the working tree) and the autosave timing is untouched. The cursor, sequence, path ledger, and import ledger are **one** record at `.bnotes/sync/export.json`, written through `vault.GuardMutation` + `vault.WriteStateFile` and derived from `vaultsync.StateDir` so it stays out of what travels — which is why this package is *not* in `internal/audit`'s approved list. A sequence and package identity are reserved **before** publishing, so an interrupted pass resolves to exactly one of three outcomes: reused, adopted (the manifest landed and is the commit point), or burned and reported. A first export pins its commit rather than re-reading the tip, or an edit to an already-sent path would never travel. A deletion travels only with an `internal/journal` record **in the same commit** proving the exact bytes removed, `Options.AuthorizeDeletions` being the caller's per-pass override and never persisted. `RecordImport` must be durable *before* the applying commit, or the peer's own change echoes back to it. A rewritten history, a changed epoch, a changed branch, or a foreign identity all **halt**; `Reset` re-baselines, keeping the identity, the sequence, and the import ledger. Two paths that are one name on a folding replica never both travel — one file there, or one of them a file and the other a directory: `vaultsync` refuses both pairs inside one manifest and `collisionIndex` refuses them *across* packages, by asking the path ledger what it already sent and `vaultgit.History.EntryKinds` what the commit still holds under each rival — the object kind, not a yes or no, so a file legitimately replaced by the directory a later path needs is not refused forever. That is the one halt no edit at the tip clears, because the clash is in a commit that already happened; `Reset` drops the path ledger with everything else, but it re-baselines from the current tree, so two names still live there are refused again by the baseline.
- `internal/vaultimport` — the consumer side, and the mirror of `vaultexport`: it turns a peer's `vaultsync` package into this vault's own history. `Drain(root, Options)` is the door a command calls — the whole incoming channel in causal order, with what it held back and why — and `Apply(root, packageDir, Options)` is the single-package primitive underneath it. It re-answers none of `vaultsync`'s questions — it starts at `Accept`, so a malformed, misaddressed, unenrolled, stale-epoch, or still-arriving package is refused before any of the vault's content is touched and under `vaultsync`'s **own sentinels, unwrapped** — and it writes no byte outside `vault.FileTxn` + `noteops.BeginOperation`/`Finalize` + the `vaultgit` snapshot. Two things do run *before* `Accept`, and both are about earlier runs rather than this package — the import guard is taken (so a package delivered during another import is `ErrImportBusy` before it is looked at) and an interrupted attempt is resolved, which can itself write notes, so "touches nothing" is a claim about the package and not about the call. Payload digests are verified a **second** time as they are read, because the transport is still writing while this runs. One package is one local operation: two operation boundaries is `ErrMultipleOperations`, because an ordinary receipt names one recovery entry and the import ledger maps one journal entry to one peer operation. A precondition failure is `ErrConflict` and leaves the contested content alone — `FileTxn` stages and checks everything before touching a destination and captures the journal only after, so the note, the recovery history, the content history, and the package in the channel are all as they were; resolving it is `Preview`/`Resolve`, described at the end of this entry. The **exception** is a pin that fails *after* staging (`FileTxn` re-checks requirements around every change): the content is compensated back and the un-finalized, manifest-less entry directory it leaves — which `journal.ListEntries` cannot see and `Prune` will never collect — is removed by `unwind`, which runs the same in-process resolution a crash gets before returning the failure. Both configuration layers are pinned for the whole commit — the portable one unless the package is itself changing it (same-path decided by `vaultsync.CollisionKey`, not bytes), the machine-local overlay always, *including its absence*; this package supplies the pins and `vault` decides when they are checked. The order `Commit` → `Journal.EntryID()` → `vaultexport.RecordImport` → `Finalize` is forced from both ends — provenance written after the snapshot lets the peer's own change echo back to it, and `EntryID` is empty until the first `Capture`, so reading it after `Commit` is what proves an entry exists to record against — which is what `EntryID` on `journal.Recorder` and `noteops.Journal` exists for. The identity itself is knowable earlier: this package mints it with `journal.NewEntryID` and pins it onto the recorder (`WithIDGenerator`, appended last so it overrules a caller's generator) *before* the transaction starts, because the attempt record has to name the entry before the first byte moves; when `RecordImport` itself fails the entry is finalized anyway and both failures are reported, naming entry + operation + origin so one call repairs it. `journal.LoadEntry` reads the entry back before the receipt is minted (defence in depth — a successful snapshot already loaded it; load-bearing only where there is no content history), and every acknowledged hash is read from this disk rather than copied from the package. A **receipt** that could not be minted returns the `Result` **with** the error (applied, undoable, `Receipt` nil) — and so does a `settle` that could not save the import record, or a `republish` that could not put an already-minted receipt back in the channel, both with `Receipt` **non-nil**: `Result.Receipt` is set whenever this vault *has* an acknowledgment, `ReceiptPath` only when the bytes are where the peer reads them, and that field rather than the error is what tells "the peer was never told" from "the peer was told and the step after that failed"; the two ordinary post-commit failures (provenance, snapshot) return nil because each names its entry in the error itself, and `finalize`'s remaining ones are defensive. A `*vault.TxnCleanupError` is the one `Commit` failure treated as success here — carried out as `Result.Cleanup` rather than abandoning bytes that are already durable; classification is an **ordering**, because `*TxnRollbackError` and `*TxnRecoveryError` nest the conflict that caused them and `IsTxnConflict` is `errors.As` (see `classifyCommit`). Concurrency: a **wait-free whole-import guard** (`import.lock` in `vaultsync.StateDir()`, via `vault.TryLockPath` — never `vault.LockPaths`, which would deadlock against a transaction escalating to the exclusive vault guard) serializes imports, so a second one is refused as `ErrImportBusy` before the package is read rather than failing later at the snapshot. It is also the **liveness test** recovery needs: an unresolved attempt beside a *free* guard means the writer is dead. A snapshot can still be refused by a `vaultgit` lock somebody else holds, and `*vaultgit.SnapshotError` unwraps to `KindBusy`, so ask `IsSnapshotFailure` before `IsBusy`. **Crash-consistent and idempotent**: `Apply` writes an fsynced attempt record before the first byte moves and runs `Recover` ahead of every import; the undo manifest is the discriminator, so everything before it rolls back and everything after rolls forward, and each forward step is a no-op when it already happened (including *adopting* an already-published receipt rather than re-minting one). `snapshotNeeded` asks the content history before re-committing, because an entry that deleted a note carries the only authorization for that deletion and a second commit would latch `blocked.json` over an "unexplained" deletion. `journal.Started` — the entry *directory*, created by the first `Capture`, which `FileTxn` runs before it applies anything — is what tells a rollback that nothing landed; comparing the paths cannot, because a package whose stated expectations were wrong is precisely the one that got refused. A redelivery is **answered from the import ledger, never re-applied**, and the original receipt is republished rather than a new one minted — the one exception is a package that was applied and never successfully acknowledged, held to every check a first acknowledgment is held to. A **conflict is decided before the transaction exists** (`inspect` runs ahead of `plan`), because a transaction reports only the first precondition that failed and never *how* it failed — so all six kinds are named here in the vocabulary of their remedy (`ConflictKind`: filename collision first, since it is true whatever the expectation says; configuration next, since declarations govern notes the package does not carry; then delete-edit, edit-delete and concurrent edit), an identical outcome is `converged` rather than contested, and a rename source whose destination disagrees is a `ConflictDivergentRename` (the pairing is recovered from the package by `renamePairs`, never trusted from a label). A hold is durable in `State.Conflicts` and keeps the remote branch, the local branch and the baseline content-addressed under `.bnotes/sync/conflicts/<package>/<sha256>`; the baseline is best-effort (the package for a rename, `vaultgit.OpenHistory` for an uncommitted local edit, digest-only beyond that). A hold is **not** an `Attempt` — it touched nothing, and recording it as pending would make every later import refuse. Dropping one is `release` (the record stops naming the bytes, and is saved) then `discard` (the bytes go), never the reverse. `Attempt.Converged` is load-bearing for recovery: a converged path reads as applied, so without the record a rollback would restore content the import never wrote; a wholly converged package produces no entry but still publishes a receipt, marked converged and recorded in `Record.Converged` without inventing a recovery entry. `Drain` sorts the channel by origin, sequence and identity — never by the filesystem or `CreatedAt` — and holds a package for one of `HoldUnreadable`, `HoldDependency` (exact position, not a high-water mark), `HoldPredecessor` (only operations carried by packages **still in the channel**, or the first package a peer sends back would deadlock) or `HoldOrder` (a `CollisionKey` overlap with a strictly earlier package) — decided before attempting — and reports `HoldConflict`, `HoldRejected` or `HoldFailed` on one that was. A reason names a **class of remedy, not a place**: `rejected` (unknown format, malformed manifest, non-portable path, multiple operations, wrong vault, unenrolled origin, stale or ahead epoch) and `ErrIncompletePackage` → `HoldUnreadable` are each asked of the scan's failure *and* of the application's, because the manifest half is caught by `ReadManifest` and the enrollment half only by `Accept`. A **`Result` outranks the error it came with** — the `result != nil` arm precedes every classification, since an acknowledgment can fail with `ErrUnsupportedFormat` (a newer build's receipt in this vault's own outgoing channel) *after* the content is durable, and classifying on the error would report a committed package as permanently rejected and drop it from the report entirely. Verdicts are cleared and re-decided each pass, so the partial report a mid-pass refusal returns carries no stale wait and names the packages it never reached `HoldNotAttempted`; `Held.Conflict` is nil-checked even under `HoldConflict`; `Drained.Applied` counts redeliveries and converged packages that wrote nothing; and `Drained.Unfinished` reads `Result.Receipt`, not the error, to say whether the peer was never told or was told and the step after that failed. A conflict holds its own operation and its dependents and nothing else; the pass takes the import guard once and iterates to a fixed point, so a chain arrives in one drain and a cycle stalls rather than spins; `Drain` errors only about the *vault*, never about a package. The single refusal that blocks the vault is a **rollback that would cross a newer edit**: `ErrStrandedImport` keeps every artifact and **blocks every further import** until a person resolves it. Roll-forward has no counterpart — an acknowledgment that cannot be minted fails the message, not the vault, and the attempt is settled with no receipt. Because that price is the whole import path, a rollback that has already put the content back records `Attempt.Restored` before removing the entry and the attempt: a restored path reads exactly like one never written, so a human edit landing on a finished-but-untidied rollback would otherwise read as neither version forever. That record covers every step after it — including discarding the entry directory, which is a recursive removal and not one write — but **not** the instant between the restoration and itself: a content transaction and a state file cannot be made one write, and the other order would have the next pass skip a restoration that never happened. `OutcomeDiscarded` is therefore a statement about what a pass did, not a promise that no destination was ever written. `vaultgit.CommitJournalEntry` is idempotent for the same reason and in the same spirit — an entry HEAD already holds is a no-op, checked **inside the safety lock**, because `snapshotNeeded` is only a cheap pre-check and the autosave watcher can commit the same finalized entry in between. **Resolving a hold is `Preview` then `Resolve`, and it is two commits** (`resolve.go`, `revision.go`). `Preview(root, packageID, Choices)` answers a `Plan` naming every path the decision touches — including the ones a choice *derives*, like the `Alpha (conflicted copy <digest>).md` keep-both writes beside the note — with both branches pinned as `vault.FileExpectation`s and nothing written; the four choices are `KeepCurrent`, `AcceptIncoming`, `KeepBoth` and `ManualMerge` (per-path, `Choices.Default` for the rest), and one the conflict cannot take — keep-both on a configuration conflict, a manual merge with no bytes supplied — is `ErrResolutionUnavailable`. `Resolve(root, packageDir, plan, opts)` applies the held package **as an ordinary import first** (same transaction, provenance, entry, receipt), because `vaultsync` verifies a receipt against this disk before minting it, so a vault that wrote the person's choice instead could never acknowledge and the peer would redeliver forever — then records the choice as a **second journaled revision** under the `sync-resolve` token, *not* recorded as an import, so the exporter publishes it with the peer's operation as `Predecessors` and the peer's own content as `ExpectSHA256`. The peer therefore holds exactly what the revision expects and applies it with nothing to decide; convergence is one round trip for every choice, and zero `vaultexport` changes were needed. Between the two commits the vault holds the peer's version **deliberately**: that is what puts the rejected version in the content history (`HEAD~1`) and in the recovery history, where undoing the resolution restores it. Because that window is real, the plan — its staged content and its journal entry identity — is durable *before* the application starts, and `finishResolutions` runs ahead of every import, drain, and resolution: a crash after the application rolls the revision **forward**, and one before it landed **abandons** the promise and leaves the hold exactly as it was, resolvable again from a fresh reading. A plan the vault has moved past is `ErrStalePreview` with nothing written — a late local edit, a hold that is gone, or a competing resolution that won the race — and staleness is judged by re-asking *every* fact the plan was built on, including this vault's own version of each path, since that is the one that moves. `Resolution.Applied` is set whenever the call applied the package, so a non-nil `Resolution` beside an error means applied-but-not-yet-revised, which is the one partial outcome and is the recoverable one; the lone exception is an application that failed after committing, whose own in-process recovery can finish the resolution on the way out and leaves the error with no `Result` to carry. A crash between the revision's commit and its manifest is taken back out by `unwind` before the re-drive plans — the roll-forward means untouched-looking content may be one lock away from arriving — and only three sentinels (`unkeepable`: `ErrConflict`, `ErrResolutionUnavailable`, `ErrCorruptState`) abandon the promise, because this runs ahead of every import, drain, resolution and recovery, so keeping one over a failure that will not clear stops the vault synchronizing at all. All three are raised **before** the revision writes anything, which is what makes dropping the promise safe — there is no half-made change the promise was the last record of. Two things are deliberately not on the list: the unwind's own racing refusal (transient, retried) and any failure raised *during* the unwind, which is `ErrStrandedImport` — the answer this package already has for a rollback it cannot safely make, keeping every artifact and refusing every later import until a person looks. `Recovery.AbandonedBecause` carries the reason per package, because "your edit was newer" and "this vault's staged copy of your merge is damaged" are both abandonments and a name on a list cannot tell them apart; `Apply` and `Resolve` run the same pass and throw the `Recovery` away, so the same map is carried onto `Result.AbandonedResolutions` and `Resolution.AbandonedResolutions` (the person who resolves a conflict a second time is usually the one whose first attempt was dropped, and they never call `Recover`). The abandonment is recorded before `abandonResolution`'s own failure is acted on and only when `clearResolution` actually cleared the promise: a cleared promise is gone from the state file, so nothing would rediscover it, while an uncleared one is decided again next pass and must not be announced twice (`abandonResolution` returns whether the promise is gone — vacuously true for a plan that revises nothing or one a prior pass already dropped, false only when `clearResolution` could not save the state file; `abandonmentOf` announces the reason only when it is). When the pass itself *fails*, every entry point but `Recover` returns a nil report, so `withAbandonments` folds the same names into that error — a cleared promise is the one fact the vault stops holding, so "ask it later" is not an option and the error is the last carrier. `gone` is the errno classifier that keeps a permanent read failure from wedging the vault: `syscall.Errno.Is` maps `fs.ErrNotExist` to ENOENT **only**, so ENOTDIR, EISDIR and ELOOP are named explicitly, while EACCES is deliberately excluded because a permission can be given back. The one thing `unwind` will not take back is a path the autosave watcher committed in the meantime: removing it would be a deletion nothing authorizes, and `vaultgit`'s preflight then refuses *every* mutation, so the file is left where that watcher put it and the re-drive finds that step satisfied. Resolving an operation also releases its **descendants**: a package held `HoldPredecessor` behind the conflict drains on the next pass.
- `internal/vaultsyncd` — the **companion** that runs synchronization on a schedule with nobody typing a command, plus the **status model**. It owns no protocol and writes no note: `Run` is the loop, `Once` is one bounded pass, `Read` is the whole observable surface, and only `cmd/bn-vault-sync` imports it. A pass is **three units in one goroutine in one order — import, export, retire** — and that ordering is a *lock* decision: `vaultimport` holds its import guard across a drain that calls `vaultexport.RecordImport`, which takes the export state lock `vaultexport` holds across a pass, so two of them concurrently approach one lock from opposite directions and the loser **fails** (path locks have a bounded acquisition budget) *after* the peer's change is committed. Import precedes export so an applied commit is in the export ledger before the exporter sees it and cannot be published straight back; retire takes no subsystem lock at all. A pass reads status once **before** the units and again **after** them — `passState.imported` forces the export to run when an application committed mid-pass, or a resolution revision would sit for a tick. **Delivery is never reported as application**: `StateTransportPending` covers everything up to "being applied right now" and only a verified receipt retires a package, while `StatePeerApplication` counts packages on this disk that are *not* yet this vault's. Ten states, reported as a set with a `Headline()` ordered by urgency and a `NeedsPerson()` that is `-check`'s exit 1. Failures are durable per worker in `companion.json` (streak + `NextAttemptAfter`), so a vault whose exports have been failing never looks idle; the backoff doubles to a ceiling and is a **delay, not a latch**; a **skip** never *lengthens* a streak, and one that proves there was nothing to do — decided before the worker runs (unenrolled, no history, nothing to publish, blocked content history), or refused by the worker as unenrolled/unmanaged/unborn — **clears** it, because a streak is otherwise only ever cleared by a success and a worker that failed and then stopped being asked would carry exit 1 forever. `bn sync` running by hand is the one skip that leaves the streak alone: a busy vault is a worker that never got to look. The producer halts that leave nothing to measure — a cursor from an earlier enrollment epoch, one on another branch, one the branch was reset behind — are named as `Problem`s rather than inferred from the streak, and a status carrying a problem runs the export anyway, so clearing hides nothing. The record holds *only* scheduling state, so an unreadable one is discarded and started again rather than refused. One companion per vault via `vault.TryLockPath` on `.bnotes/locks/vault-sync.lock` (never `LockPaths` — it escalates to the guard the transaction escalates to from inside), refused as `ErrAlreadyRunning` with no `Pass` rather than queued. **`Read` takes no lock of any kind** and turns a fact it cannot determine into a `Problem` rather than an error. A **converged** package publishes an explicit “this changed nothing” receipt after every package result is observed on disk, so it claims no recovery entry and the sender retires it through the ordinary handshake.
- `internal/audit` — no production code. `TestNoUnannotatedDirectWrites` parses every production file and fails when one writes to the filesystem outside the approved persistence packages (`vault`, `vaultgit`, `vaultstate`, `journal`, `index`, `backup`) without a `//bn:direct-write <reason>` marker naming the guarantee already in force. `gofmt` treats `//bn:` as a directive, so the marker is one line at the end of its comment group. Tests are exempt; widening the approved list is a decision about where safety lives, made in that map with a reason.
- `internal/vaultfixture` — verification infrastructure, imported only by tests. One statement of the isolation rule (`IsolationError`: refuse a real vault by name, refuse anything outside the system temp directory, refuse anything outside the asserted sandbox), plus disposable Git-backed vault `Pair`s, the `Epoch`-anchored `Clock`, and loopback-only listeners. `internal/cli`'s fixtures call the rule rather than copying it; `internal/vaultsync`'s tests are the first consumer of the `Pair`/`Clock` helpers, which were built ahead of the two-vault synchronization work — `ReserveLoopbackAddr` is consumed by `internal/synctransport`, which reserves the two addresses each Syncthing process is told to listen on — its sync port and its private API — before handing them to a child that binds them itself (`ListenLoopback` and `LoopbackHost` have no caller outside this package's own tests). Not in `internal/audit`'s `approvedPackages`: its writes carry `//bn:direct-write` markers naming the containment check ahead of them.
- `internal/syncthingbin` + `internal/synctransport` — the **real transport gate** (`just test-sync-transport`), and the only place this repository runs somebody else's program against a vault. `syncthingbin` pins **one** Syncthing release (`v1.30.0`, paired with config schema **version 37** — moving either without the other is a change to both), fetches the official archive, refuses it unless it matches a recorded SHA-256, records the digest of the binary it extracted beside it and re-hashes a cache hit against that record, caches outside every fixture (the cache directory is read at package init, *before* `vaultfixture.Isolate` rewrites `HOME`), and re-runs `--version` on whatever it returns; `go install ...@version` is unusable here because Syncthing's module carries replace directives. `synctransport` starts **two processes** — separate homes, separate databases, generated identities, explicit `tcp://127.0.0.1:<reserved port>` peer addresses, and discovery, relays, NAT, auto-upgrade, usage reporting and crash reporting all off — plus a private loopback API with a per-instance key for pause/resume/status/revert. The configuration is **written, not patched**: starting from `syncthing generate` would make the guarantees a list of things somebody remembered to turn off. Each device serves exactly **two folders**: its own `.bnotes/sync/outgoing` **sendonly**, and its peer's arriving as `.bnotes/sync/incoming` **receiveonly**. A live vault directory is never named — every path goes through `vaultfixture.IsolationError` before anything is created, and `TestRealTransportNamesOnlyStagingDirectories` asks the *running processes* rather than the file; `TestRealTransportRunsTheConfigurationItWasGiven` asks them for the schema version and the closed doors (`Containment`), because a release that does not know the schema migrates the file and keeps the folders, which would leave every other assertion true of a configuration nobody wrote. **No send-receive folder anywhere**, which is what makes retirement mean something: a receive-only folder that loses a file locally records a *local deviation* and keeps being offered the bytes, so a receiver deleting a package it applied retires nothing and `POST /rest/db/revert` pulls it straight back from the owner. Scenarios live in `internal/vaultsyncd/realtransport_test.go` behind the `synctransport` build tag — same `world`, same enrollment, same passes, transport swapped — covering reordered delivery, a disconnect, a restart on the same database, an incomplete package, an altered package, and sender-owned cleanup. The tag is on the **test files only**, so gofmt, `go vet` and the ratchet cover the harness on every ordinary run; `.golangci.yml` **and** `scripts/metrics_complexity.py` both set `run.build-tags`, so the gate and the recorded floor judge the same file set. A missing binary **fails, never skips**, and provisioning happens in the justfile rather than in a test so one download serves a whole tagged run.
- `internal/mutationmatrix` — no production code either. One table drives every real production entry point (CLI through the Cobra tree, HTTP through `internal/web`, `noteops`, restore, durable state) through the same assertions: a refused location fails before any artifact exists, an allowed one mutates, a no-op leaves no empty commit, a success is **exactly one** commit of only its own paths, an unrelated working-tree edit is not swept in, and a failed snapshot is reported honestly and blocks the next mutation. A new mutating command is one row away from coverage; a row that cannot be written means the command bypassed the seam.

## Implementation notes

- **Property semantics are config-driven** through one unified model: each `[frontmatter.properties.<name>]` section declares `type` (`string`/`wikilink`/`date`/`datetime`/`int`/`float`/`bool`/`list`), `items` (required for lists, naming the element kind — lists do not nest), optional `required`, and an optional `allowed` allow-list. There are no implicit runtime defaults, so the starter config spells out `categories`, `tags`, `topics`, `org`, `type`, `parent`, `area`, and `pinned`. `bn set k=a,b,c` splits on comma only for a property declared `type = "list"`, and auto-`[[ ]]` wrapping happens only for a `wikilink` type or a list with `items = "wikilink"`. Undeclared properties remain legal and are left alone by lint/repair. Tests rely on this — when adding new property semantics, extend `PropertyDefinition` rather than hard-coding key names.
- **Type coercion in `bn set`**: `true`/`false` → bool, integer → int, `YYYY-MM-DD` → date, else string. `--type date|int|bool|raw` forces a type.
- **Stdin convention**: `-` as the sole note arg means "read paths from stdin". For `bn unset` with multiple notes, use `--` to separate notes from property names. `-0` enables NUL-separated I/O end-to-end (paths in *and* paths out from `bn find`).
- **`PersistentPreRunE` skips config loading** for `completion`, `help`, and `init` so they remain usable outside a vault, and for any command carrying the `skipConfigLoad` annotation (`root.go`), whose value is the reason the exemption is taken. The two mechanisms are not interchangeable: the name list only works for cobra's own commands and top-level ones, since a nested `migrate` would also match a future `bn vault migrate`, so a subcommand says so on itself. `bn config migrate` is currently the only annotated command — it repairs a vault whose keys are misplaced, which is exactly the vault an enrolled loader refuses — and the cost of the exemption is that it gets no `*config.Config` and must resolve the vault root itself. Plain `config` deliberately does *not* skip: it reports the resolved vault, so it needs the load to have happened.
- Frontmatter rewrites must round-trip cleanly — preserve `Body` verbatim and only rewrite the frontmatter region. Tests under `internal/frontmatter/testdata` and `internal/cli/testdata` (golden files) catch regressions here.
- **`--dry-run` output has one canonical format** across every mutating command (`set`/`unset`/`replace`/`repair`/`relink`/`rename`/`move`). Each changed file is rendered by `internal/noteops`'s `RenderNotePreview` (`internal/noteops/preview.go`): a `--- <relpath>` header, then one line per change — `path: <old> -> <new>` for a rename/move, `frontmatter[<key>]: <old> -> <new>` for a property change, and `body:<line>: <old> -> <new>` for a body line. The same `NotePreview` model backs the web preview APIs, so CLI dry-run and web previews cannot drift. Preview-before-apply is mandatory for cockpit file changes: the web `/api/fixes/apply` requires a one-use `preview_id` from `/api/fixes/preview`, and bulk note actions require `/api/notes/bulk/preview` first.
- **Body diffs in `rename` / `move` dry-run** run the whole-body rewrite first and then diff line-by-line. Per-line rewriting would break `wikilink.Parse`'s code-fence masking, because a fence opener on one line is invisible to the next line's parse — the dry-run would report phantom changes for masked links that the apply path (which uses whole-body rewrite) correctly leaves alone.

## Deep reference

These invariants used to live inline here and are load-bearing. Each file is short; open the matching one **before** you touch that area, not after a review flags it.

- Writing a note, taking a lock, or committing a `vault.FileTxn` → `docs/internals/locking.md` (the mandatory `vault.GuardMutation` storage-location preflight, atomicity model, the path-preserving native replacement and its per-volume self-test, swap-then-judge compare-and-swap, per-path flock, the shared vault guard and escalation). **An overwrite must never vacate its destination**, and there is no fallback that does; on darwin a vault under File Provider storage refuses every mutation outright, with **no override**. Read that file before touching any write path, and route any new one through `noteops.BeginOperation` (journaled note mutations) or `vaultstate.Save` (durable sidecar state) rather than calling `GuardMutation` by hand — those are the two places the guard and the Git preflight run together, ahead of every artifact. A production write that genuinely cannot go through either needs a `//bn:direct-write <reason>` marker or `internal/audit` fails, and a new mutating command needs a row in `internal/mutationmatrix` or it is not covered end to end.
- Changing `bn related`, `bn context`, `internal/recall`, or the recall sidecar → `docs/internals/recall-context.md` (read/write boundary, context privacy boundary, selection invariant, state recovery).
- Adding or changing any mutating web API route → `docs/internals/web-write-classes.md` (preview-gated vs. narrow-unpreviewed, the property/capture/pin classes, the property intelligence cache, the history-and-recovery class and the receipt that gates a forced restore).
- Adding a web route that writes, starts a process, or serves vault bytes — or branching anywhere on "is this server local" → `docs/internals/serving-modes.md` (the `capabilities` table and its independent dimensions, the guard's allowlist/capability/origin refusals, the two single exec doors that refuse again, the per-profile body bounds and private caching headers, and the active-media rules). **Never re-derive a deployment from an option flag**: ask `s.caps`.
- Changing any `/api/synthesis/*` route, the `/synthesize` page, or `internal/noteops/synthesis.go` → `docs/internals/synthesis.md` (read-only context pair, preview/apply write class, frontend module split and persistence rules).
- Changing the `/graph` page, `internal/web/graph.go`, or any `internal/web/static_src/graph*.ts` module → `docs/internals/graph-view.md` (faithful directed payload with every reduction client-side, display params that never reach the fetch, the load-bearing isolate → min-degree → collapse order, fetched vs. displayed element sets, the vendored layout chain and its `cose` fallback, screen-space label culling).
- Adding a package or moving responsibility between packages → `docs/internals/architecture.md`.
- Adding a subcommand to `internal/cli`, or decomposing an oversized `New*Cmd` → `docs/internals/cli-command-shape.md` (thin constructor, `<cmd>Options`, one `validate()` for the flag matrix, one named function per mode in `<cmd>_run.go`, rendering in `<cmd>_output.go`, and which orderings are behaviour). `set.go`/`set_run.go` and `search.go`/`search_run.go` are the worked examples.
