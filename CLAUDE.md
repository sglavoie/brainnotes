# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`bn` (Brain Notes) is a small Go CLI for editing and querying a plain-Markdown notes vault. It targets fast, vault-aware operations (frontmatter queries, wikilink-aware rename/move, templated note creation) that complement an editor rather than replace one. The README is the canonical user-facing spec — keep behavior aligned with it when changing commands.

## Common commands

The repo uses `just` for development tasks (see `justfile`):

- `just build` — build the `bn` binary in the repo root via `go build -o bn ./cmd/bn`.
- `just install` — `go install ./cmd/bn` (puts `bn` in `$GOPATH/bin`).
- `just test` — `go test ./...`.
- `npm ci` — install pinned frontend tooling before changing TypeScript source or running frontend checks.
- `just web-build` — bundle `internal/web/static_src/main.ts` into committed `internal/web/static/app.js`.
- `just web-check` — run frontend typecheck, Vitest/jsdom tests, and the browser bundle build.
- `just lint` — fails on `gofmt -l .` output, runs `go vet ./...`, then runs `just web-check`.
- `just ci` — the full validation envelope: `gofmt -l` check, `go vet ./...`, `go test ./...`, frontend typecheck + Vitest, and a bundle-drift check that hashes `internal/web/static/app.js`, rebuilds it, and byte-compares the result against those on-disk bytes. That compares the bundle against its own source rather than against `git`, so it passes on an uncommitted tree and fails only when the checked-in bundle is genuinely stale. Run this before declaring work complete (`scripts/health.py` runs exactly this).
- `just fmt` — `gofmt -w .`.
- `bn serve` — local `just build`/`just install` binaries remember this checkout path, rebuild web assets here before serving, and serve static assets from `internal/web/static` on disk. The serve-time build prefers the native `node_modules/esbuild/bin/esbuild` binary to avoid requiring `node`/`npm` when dependencies are already installed; unstamped binaries fall back to current-directory checkout detection, then embedded assets.

Run a single test: `go test ./internal/cli -run TestFind_TagFilter` (standard Go test selectors). Integration tests in `internal/cli/integration_test.go` use golden files under `internal/cli/testdata/`.

Go module is `github.com/sglavoie/sglavoie_brainnotes` (note: the binary is published as `github.com/sglavoie/brainnotes/cmd/bn` per the README, but the local module path differs — keep imports using the local module path).

## Architecture

Layered packages, each with a focused responsibility. Commands compose primitives from the lower layers — keep the boundaries clean rather than reaching across them.

- `cmd/bn/main.go` — thin entrypoint, delegates to `internal/cli.Execute`.
- `internal/cli` — Cobra command tree. `root.go` wires persistent flags and uses `PersistentPreRunE` to load config into the command context (extract with `ConfigFromContext`). Each subcommand lives in its own file; `related.go` owns ranking/output/interactive selection, `related_feedback.go` owns explicit sidecar writes, and `context.go` owns deterministic bundle export plus optional agent execution. `target_resolution.go` is the shared NFC-aware single-note resolver for links/backlinks/related/context. `notes.go` centralizes multi-note positional handling: it resolves paths from args, globs, or stdin (`-` triggers stdin; `-0` toggles NUL separation) and enforces in-vault containment.
- `internal/config` — TOML loader for the single vault-local `brainnotes.toml`. That file is the vault-root marker, so resolving the vault root and locating the config are the same operation: `--vault` → `$BNOTES_VAULT` → an upward search from the working directory, each of which requires the directory to actually contain `brainnotes.toml`. `LoadOptions` injects the flag, working directory, and environment lookup so precedence is testable without touching real process state. `Vault`, `SourcePath`, and `VaultOrigin` are runtime-only fields (`toml:"-"`); there is no `vault` key. `DefaultIgnore` (`.git`, `.obsidian`, `Attachments`, `Archive`, `Trash`) is always merged in. `[related]` controls only the metadata property list; fixed ranking weights are not configuration. Top-level `[agent]` is a literal argv plus timeout shared by context research and, when no legacy cockpit override is set, daily review.
- `internal/vault` — `Vault` is a root path + config. `Walk` skips hidden dirs, configured ignores, and the templates dir automatically (template files contain unrendered placeholders that are not valid YAML, so they must never be walked). `Notes()` loads everything in memory — fine for the documented working size (~300 notes); switch to streaming `Walk` if scaling beyond a few thousand. `ResolveByTitle` does case-insensitive stem lookup and returns an ambiguity error listing all candidates.
- `internal/frontmatter` — parse/rewrite YAML frontmatter. `Map` preserves insertion order during parse but `Marshal` **always emits keys alphabetically sorted** — this is intentional and load-bearing for stable diffs. Values are Go-native types (string, int, float64, bool, time.Time, []any, map[string]any). Wikilink-typed properties are auto-wrapped in `[[ ]]` on write.
- `internal/wikilink` — Obsidian-style `[[Target#Heading|Alias]]` parsing and rewriting. **Code-block aware**: links inside fenced, indented, or inline code are masked out so rewrites never touch documentation samples or code snippets. Used by `rename` (rewrite all forms when title changes) and `move` (rewrite folder-prefixed forms only — bare `[[Title]]` links resolve by title alone in Obsidian and are deliberately left untouched).
- `internal/query` — composable `Predicate` functions over `*vault.Note` for the `find` command's frontmatter dimensions (tag/category/status/type/has/missing/folder/age/orphan), plus the path-aware wikilink graph reused by recall ranking. `And` is the identity-with-no-args combinator; queries with no flags match everything.
- `internal/recall` — deterministic contextual retrieval with no persistent index. Extraction preserves exact note bodies/source spans while building NFC-normalized weighted title/heading/prose fields and configured metadata pairs. `BuildRanker` combines fixed text/graph/metadata/recall weights and returns stable reasons/mode filters. `BuildContextBundle` keeps the source body complete, admits ranked related excerpts under one selection shared by Markdown and JSON, and enforces the byte cap against both renderers. `StateStore` owns flock serialization for `<vault>/.bnotes/recall.json` and holds the sidecar path lock across every fresh read-modify-write; read-only queries stay lazy, explicit writes prune stale records, and corrupt/invalid/symlinked state fails closed.
- `internal/agent` — shared argv-only process runner. Callers own context timeouts; stdin/stdout remain byte-exact; diagnostics are bounded and sanitized. There is no shell, provider SDK, persistence, or implicit network behavior. `bn context --agent` sends its canonical Markdown preview, while the web daily-review path sends only its separately redacted review payload.
- `internal/template` — discovery and rendering for `bn new`. Template lookup is case-insensitive and tries `<name>`, `<name>.md`, `<name> Template.md`. Render helpers: `now`, `today`, `dateFormat`, `slug`, `title`, `lower`/`upper`, `default`, `env`, `wikilink`. The `.Vars` map holds repeatable `--var key=value` pairs.
- `internal/web/static_src` — strict TypeScript source for first-party browser behavior. `esbuild` bundles it into `internal/web/static/app.js`, which stays committed so Go builds and installs do not require Node. `internal/web/static/cytoscape.min.js` remains vendored and is not bundled.
- `internal/web/server.go` serves embedded static files by default, but accepts an injected static filesystem. `internal/cli/serve.go` uses a `sourceCheckoutRoot` value stamped via justfile `-ldflags` first, then current-directory checkout detection, and injects disk static assets after a successful web build so the current `bn serve` process sees freshly generated browser JavaScript.
- `internal/cockpit` — the shared Daily Fix Cockpit core. `BuildQueue` scans the vault and groups hygiene issues (frontmatter parse errors, schema violations, broken link targets, duplicate titles, orphans, dead ends, long-tail property values) plus opt-in advisory rules (`sensitive_content`, `missing_review_date`, `stale_status`, `wip_limit`, `hub_needs_synthesis`, `capture_backlog`) into a deterministic, content-addressed `Queue` of `Task`s, each advertising the `Action`s that can fix it. Advisory tasks are triage-only (no fix action, never mutate notes); `sensitive_content` surfaces only a redacted line/detector-category location and never the matched value. `StateStore` persists per-task workflow state (done/snoozed) in `<vault>/.bnotes/cockpit.json` and migrates readable records from the legacy `<vault>/.bnotes/review.json` on first load. `Fixer` plans and applies fixes through `internal/noteops`. `LimitDaily` caps the queue to `cockpit.daily_limit` for the daily view, and `BuildReviewContext` builds the deterministic, redacted snapshot shared by `bn doctor --review-context`, `GET /api/daily-review/context`, and the optional local `POST /api/daily-review/agent` (argv-only, stdin-fed, opt-in — no provider dependency). Both `bn doctor` (`internal/cli/doctor.go`) and the web cockpit APIs (`internal/web/cockpit_api.go`, `internal/web/cockpit_agent.go`) consume this one core so CLI and web stay identical.
- `internal/noteops` — the shared note-mutation layer used by both CLI commands and the web APIs. `preview.go` defines the canonical `NotePreview`/`PreviewChange` model that every mutating command's `--dry-run` and every web preview render through, so the two views can never drift. `capture.go` holds the quick-capture primitive behind `bn capture` and the web quick-capture box: `PreviewCapture`/`ApplyCapture` append one fixed-format `- YYYY-MM-DD HH:MM <text>` bullet to the configured inbox note under the configured heading, splicing bytes (never re-marshaling frontmatter) so every pre-existing byte survives — the write is strictly additive, so even the heading-absent path only appends a separator, the heading, and the bullet rather than collapsing trailing blank lines — bootstrapping the note inline when it is absent, and — uniquely among noteops writes — re-reading and re-planning up to 3 times on a `vault` transaction conflict before returning `CodeConflict`, which is safe only because an append is commutative. `capture_heading.go` owns the single line-oriented heading scanner and exports `CountSectionBullets` so `internal/cockpit` counts exactly the section the writer would append to.
- `internal/properties` — the reusable property index behind the web workbench. `typed.go` defines `TypedValue`, the transport form a caller sends when it wants a value written under a declared kind. `value.go` classifies a frontmatter value into a discriminated `Value` (`kind`/`text`/`value`/`items`/`supported`); anything YAML can hold but frontmatter text cannot safely reproduce (null, mapping, nested list) becomes `KindUnsupported` with a label and no reproducible text. `index.go` walks notes once to build per-property coverage, observed kinds, distinct logical values, note rows, and `internal/schema` violation counts, counting each logical value at most once per note so repeated list items never inflate statistics. `infer.go` proposes a `[frontmatter.properties.<key>]` block only for an unconfigured property whose observed values unanimously support one kind, and never infers `required` or `allowed`. The package deliberately does not depend on `internal/web`.
- `internal/pins` — the shared pinned-list core behind `bn pin`/`bn unpin`, `bn find --pinned`, `query.Pinned()`, the `/pinned` page, and the web pin endpoints. `Classify` maps a raw `pinned` value onto `NotPinned`/`Ranked`/`Unranked`: only an absent key and the YAML boolean `false` are unpinned, so a hand-written `pinned: true` or `pinned: "high"` is a pin carrying no rank that sorts after every ranked pin. `List` orders a vault's pins and silently skips a note it cannot read, cannot parse, or that falls outside the root, so one hostile note cannot hide the whole list. `PlanAppend`/`PlanMove` return `Assignment`s only — the package never writes — and fall back to a whole-list renormalize (`Plan.Renormalized`) when the float gap between two ranks is exhausted; `midpoint` and `nextRank` stay unexported so no caller can bypass that fallback. It is a **leaf package**: it must not import `internal/noteops`, because `noteops` imports `internal/query` and `query` imports `pins`, so that edge would close a cycle. In `internal/web`, note-pin identifiers are `notePin*`/`pinnedNotes*` because `pinnedConfig`/`configPin` already mean *configuration* pinning there.

## Implementation notes

- **Atomicity model**: file rewrites use temp-file + rename per file. There is no cross-file transaction — if `bn rename` or `bn move` errors mid-apply, prior writes stand. Mention this caveat in user-facing messages when relevant; rely on `git diff` for recovery.
- **Writer serialization**: every `bn` writer takes an exclusive `flock`-style lock per note path (`<vault>/.bnotes/locks/<sha256-of-vault-relative-path>.lock`) around the write. `internal/vault/lock.go` owns the primitive; `vault.LockPaths` is the entry point for writers outside a transaction, and `FileTxn.Commit` uses the same code so lock naming and ordering cannot drift between the two. Locks are always taken in sorted path order, which is what makes multi-path callers deadlock-free. This exists because replacing a destination renames it into custody first, leaving the path transiently vacant — without the lock a second writer creates into that vacancy, wins the path, and forces the custody holder to surface a `TxnRecoveryError` with the note's only prior copy stranded in a `.txn-custody-*.tmp` for a human to merge. Serializing `bn`-vs-`bn` writers demotes that to an ordinary staging conflict callers already replan. Covered writers: `FileTxn.Commit`, `Note.Save`, `noteops.RenameFile` (both ends), `moveToTrash` (both ends, spanning the existence check so it cannot go stale), `CreateStubFromBrokenTarget`, and `bn new`. `bn init` deliberately does not lock — it writes the vault marker before a vault exists to lock in.
  - The lock must be `flock` (owned by the open file description), never an `fcntl` record lock (owned by the process), or in-process writers such as the web server's goroutines would silently not contend; a fresh descriptor per acquisition is required for the same reason. That also makes the locks **non-re-entrant**: a caller holding a path lock must not call into anything that locks the same path, or it waits out the full budget against itself — and, because of the shared vault guard below, must not nest a write large enough to escalate either. Keep new locking at the individual write, not around a whole multi-note operation — a vault-wide `bn rename` touches hundreds of notes, and holding hundreds of descriptors would hit `ulimit -n` and lock the whole vault.
  - Every writer first takes `<vault>/.bnotes/locks/vault.lock`, **shared**, and then its per-path locks. That guard exists so lock acquisition can escalate: a transaction planning more paths than `vault.MaxLockedPaths()` takes `vault.lock` **exclusively** and no per-path locks at all, since one exclusive guard already excludes every other `bn` writer using a single descriptor however many paths the set covers. `vault.MaxLockedPaths()` is therefore an escalation threshold, not a transaction-size limit — it is derived from the process descriptor limit (`RLIMIT_NOFILE` minus a 128-descriptor reserve minus the one guard descriptor, capped at 4096) only to decide when per-path locking stops paying for itself. It deliberately has **no floor**: a threshold above what the process can actually hold makes a set below it take one lock per path and die on `EMFILE` during acquisition instead of escalating, so on a process whose limit is under the reserve the threshold is `0` and every write escalates. **There is no cap on how many notes one atomic write may cover**; `noteops.SetFrontmatterAtomic` refuses no set for its size. That matters because an ordering that spans notes — a whole-list pin renormalize — rewrites every note in the list, and the pinned list is uncapped, so any fixed boundary leaves a list that renders fine and can never reorder. What escalation costs is concurrency for that one commit: every other writer in the vault waits on the guard, and an escalating writer that never finds a gap between ordinary writers exhausts its wait and gets a retryable `*TxnLockBusyError`.
  - Custody stays regardless, because no lock binds an external writer like Obsidian. A wait that exceeds the budget returns `*TxnLockBusyError` (`IsTxnLockBusy`), which is deliberately **not** a `TxnConflictError`: nothing was read or staged, so the caller's plan is still valid — `noteops.classifyTxnError` still reports it as `CodeConflict` because "retry" is the right advice. Locking is unsupported outside darwin/linux/windows, where the older unserialized behavior stands. Lock files are never unlinked — deleting one another process holds would let a third create a new file at the same name and lock nothing.
  - `Note.Save` needs a root to name its lock file, and a bare `vault.Note{Path: ...}` literal has none, so **`Save` refuses a rootless note** rather than silently skipping both the lock and the containment check. Build any note that will be written through `vault.NewNote` or `Vault.Notes`. `Save` is also a compare-and-swap: inside the lock it verifies the destination still holds the hash `Load` read, so a concurrent edit between `Load` and `Save` is a `TxnConflictError` instead of a lost update. Two deliberate carve-outs — the check applies only while `Path` still equals the path `Load` read (retargeting `Path` to save elsewhere is a supported pattern the loaded revision makes no claim about), and an unreadable destination (mode `0000`) counts as unverifiable rather than refused.
  - Still unserialized, by design or by omission: external writers (no lock to take), and the journal's pre-write `Capture` reads in the rename/move/trash flows, which happen outside the lock.
- **Property semantics are config-driven** through one unified model: each `[frontmatter.properties.<name>]` section declares `type` (`string`/`wikilink`/`date`/`datetime`/`int`/`float`/`bool`/`list`), `items` (required for lists, naming the element kind — lists do not nest), optional `required`, and an optional `allowed` allow-list. There are no implicit runtime defaults, so the starter config spells out `categories`, `tags`, `topics`, `org`, `type`, `parent`, `area`, and `pinned`. `bn set k=a,b,c` splits on comma only for a property declared `type = "list"`, and auto-`[[ ]]` wrapping happens only for a `wikilink` type or a list with `items = "wikilink"`. Undeclared properties remain legal and are left alone by lint/repair. Tests rely on this — when adding new property semantics, extend `PropertyDefinition` rather than hard-coding key names.
- **Type coercion in `bn set`**: `true`/`false` → bool, integer → int, `YYYY-MM-DD` → date, else string. `--type date|int|bool|raw` forces a type.
- **Stdin convention**: `-` as the sole note arg means "read paths from stdin". For `bn unset` with multiple notes, use `--` to separate notes from property names. `-0` enables NUL-separated I/O end-to-end (paths in *and* paths out from `bn find`).
- **`PersistentPreRunE` skips config loading** for `completion`, `help`, and `init` so they remain usable outside a vault. `config` deliberately does *not* skip: it reports the resolved vault, so it needs the load to have happened.
- **Recall read/write boundary**: ordinary `bn related`, every `bn context` form, and `bn context --agent` never write recall state, the undo journal, or Markdown. Only successful `related -i` selection, `related feedback`, and CSRF-protected `POST /api/related/item` actions write `<vault>/.bnotes/recall.json`; that sidecar is runtime state and is not recoverable through `bn undo`. No related workflow writes Markdown or creates an undo-journal entry.
- **Context privacy boundary**: a context packet intentionally contains the complete source body plus selected exact excerpts. `--agent` receives exactly the inspectable Markdown bytes and prints stdout verbatim; the configured executable may transmit them, but `bn` itself adds no provider or network client. Do not reuse the web daily-review claim that bodies are redacted—the two agent inputs are intentionally different.
- **Context selection invariant**: Markdown and JSON must select the same related notes and source spans even though JSON escaping can be larger. Budget candidate changes against both serializers, never truncate the source body, and keep all excerpts tied to exact `Document.Blocks` locations.
- **Recall state recovery**: missing state is a valid empty read and is created lazily; missing-note records and expired snoozes remain untouched by reads and are pruned on the next explicit write. Never auto-repair or overwrite corrupt, unsupported-version, invalid-record, or symlinked state.
- Frontmatter rewrites must round-trip cleanly — preserve `Body` verbatim and only rewrite the frontmatter region. Tests under `internal/frontmatter/testdata` and `internal/cli/testdata` (golden files) catch regressions here.
- **`--dry-run` output has one canonical format** across every mutating command (`set`/`unset`/`replace`/`repair`/`relink`/`rename`/`move`). Each changed file is rendered by `internal/noteops`'s `RenderNotePreview` (`internal/noteops/preview.go`): a `--- <relpath>` header, then one line per change — `path: <old> -> <new>` for a rename/move, `frontmatter[<key>]: <old> -> <new>` for a property change, and `body:<line>: <old> -> <new>` for a body line. The same `NotePreview` model backs the web preview APIs, so CLI dry-run and web previews cannot drift. Preview-before-apply is mandatory for cockpit file changes: the web `/api/fixes/apply` requires a one-use `preview_id` from `/api/fixes/preview`, and bulk note actions require `/api/notes/bulk/preview` first.
- **Property intelligence cache**: `internal/web`'s `vaultState` caches one `*properties.Index` keyed on the snapshot serial plus the configuration generation, so a note reload or a `brainnotes.toml` reload rebuilds it and nothing else does. The cached index is shared and must stay immutable — `properties.Build` copies what it needs from notes and never mutates its inputs.
- **Property workbench save model**: `/api/properties/value` is the workbench's only unpreviewed write, and it is deliberately narrow — one note, one property, either a whole-value replacement or a single list addition, gated on the caller echoing the note's current hash. It is *not* the server's only unpreviewed property write: `/api/notes/frontmatter/set`, `/api/notes/frontmatter/unset`, and the three `/api/pins/*` routes are the same single-note single-property class, differing only in that they rely on the write's own revision precondition instead of a client-echoed hash. Everything else (unset, list removal, multi-note changes, bulk value replacement, property rename, repair, and every schema edit) must go through `/api/properties/preview` then `/api/properties/apply`. Property receipts carry the configuration generation as well as the note hashes, so a `brainnotes.toml` change invalidates outstanding note receipts rather than letting a plan built against old declarations apply. A fatal blocker (`parse_error`, `not_found`, `key_conflict`, `config_conflict`) suppresses the receipt entirely so the whole selection is refused; `repair_skip` is advisory and leaves the receipt intact. When adding a property action, decide which side of this line it falls on rather than adding a third path.
- **Unpreviewed web write classes**: `/api/capture` is the deliberately-unpreviewed *body* write (the other unpreviewed Markdown routes — `/api/properties/value`, `/api/notes/frontmatter/set`, `/api/notes/frontmatter/unset`, `/api/pins/*` — write properties). It is narrow for different reasons: one note, strictly additive, so it cannot destroy existing bytes, and a confirm step would defeat the entire point of a quick-capture box. Its safety comes from the `vault.FileTxn` precondition pinning the revision the append was planned against — not from a client-echoed hash, because the box never loaded the note and has no hash to send. A conflict surviving `ApplyCapture`'s 3 internal replans returns `409`; the browser resubmits. The CLI keeps the canonical `--dry-run` preview, so the unpreviewed path is web-only. `POST /api/related/item` is a distinct unpreviewed, non-Markdown class: it is CSRF-protected, resolves both note identities through the current graph, and writes only serialized runtime state in `<vault>/.bnotes/recall.json`, never Markdown or the undo journal. Do not invent a further write class: a new Markdown or configuration write still belongs on one of the two file-write sides — preview-gated, or narrow with a precondition that refuses a stale plan — while runtime-state writes must remain confined to a documented sidecar boundary with route-appropriate validation.
- **Pin write class**: `/api/pins/set`, `/api/pins/remove`, and `/api/pins/reorder` (`internal/web/pins_api.go`) are the `/api/notes/frontmatter/set` class (`internal/web/manage.go:223`) and share its prologue verbatim through `beginPinnedNotesRequest`: CSRF, writability gate, fresh snapshot, resolved note. `/api/properties/value` cannot be reused for a pin because its replace op hard-fails when the property is absent, which is exactly the first-pin case. Every rank is written with an explicit `type=float`, so pinning works in a vault whose `brainnotes.toml` declares no `[frontmatter.properties.pinned]` block. Reorder is the one exception to "one note": a rank-exhaustion renormalize rewrites the whole list through `noteops.SetFrontmatterAtomic` in a single transaction, routed on `plan.Renormalized || len(writes) > 1`, because half a renumbering is a scrambled order rather than a partial one. The browser posts note keys and never a rank — the server takes the midpoint of the neighbouring ranks as they are on disk — so a stale page cannot write an order it computed against a list that has since moved. Neighbour resolution and pin planning fail differently and must stay documented that way: a neighbour key that names no note in the vault fails in `noteops.ResolveExistingRouteNote` as `CodeNotFound` (404), while a neighbour that still exists but is no longer pinned, or a pair that no longer straddles one gap, fails in `pins.PlanMove` (`ErrNeighborMissing`/`ErrStaleGap`) as `CodeConflict` (409). Validating the gap against a fresh snapshot is not enough on its own, because two reorders of *different* targets into one gap modify neither neighbour and would both commit the same midpoint; `pinnedListRequirements` therefore turns the validated list into commit preconditions, adding a `noteops.WithFrontmatterRequire(ExpectHash(...))` for every pin the plan does not itself write. Required paths are never locked, staged, or journaled and are verified in `FileTxn.stage` before `journaler.Capture`, so the losing reorder returns 409 with no note change and no journal entry. `/api/pins/set` and `/api/pins/remove` deliberately carry no such requirements — they do not interpolate between existing ranks.
- **Body diffs in `rename` / `move` dry-run** run the whole-body rewrite first and then diff line-by-line. Per-line rewriting would break `wikilink.Parse`'s code-fence masking, because a fence opener on one line is invisible to the next line's parse — the dry-run would report phantom changes for masked links that the apply path (which uses whole-body rewrite) correctly leaves alone.
